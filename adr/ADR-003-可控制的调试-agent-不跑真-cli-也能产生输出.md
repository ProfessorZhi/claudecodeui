## 背景

排查 transcript 贴底漂移、流式增量这类"输入输出形状"的问题时，今天没有可控的复现手段。
能端到端产生一次真实输出的路径只有一条：拉起真 CLI 进程，让它按自己的节奏吐字。这带来三个后果：

- **不可控**：行什么时候出现、一次吐多少字节、中间隔多久，都由模型与网络决定。想让"每 200ms 追加一行、连追 20 行"这种形状重演一次，做不到。
- **不可复现**：同一个缺陷要观察第二次，得再撞一次同样的节奏。观测到的几何读数随内容长度、字体度量、设备像素比而变，无法作为判据的阈值。
- **覆盖缺口**：既有的浏览器侧替身只替换了 `window.WebSocket`，注入的也只有 `stream_delta` / `stream_end`。它完全跳过后端 —— runtime、按 provider 的归一化、`seq` 与重放、`complete` 触发的 REST 重取、权限帧，都不在链路上。更关键的是，**被外部 CLI 写入、app 仅旁观的会话**（chokidar 观察 → `session_upserted` 广播 → 客户端 REST 重取整行）这条摄入路径**零 e2e 覆盖**。

本 ADR 记录一次现场观察，作为立此文档的直接动因，并把"类"与"现场数字"分开登记：

**观察到的类（缺陷的形状，可复现的目标）**：在跟随意图仍然成立（"Scroll to bottom" 按钮全程未出现）的前提下，每追加一行，视口就比底部多留一段距离；累积若干行后跟随不再自行修复，因为跟随判定把"底部已经移走"读成了"用户把视口拿回去了"，于是拒绝再 pin。

**现场数字（一次会话、一台设备、一种内容配比的读数，不是阈值）**：每行多留 50–130px；约 20 秒累积到 552px；每个新行首帧高度恰为 240px，下一帧落到真实高度 24–71px。240px 这个数来自 `.chat-message.assistant` 的 `contain-intrinsic-size: auto 240px`（`src/index.css`）—— 也就是说首帧高度是一个**占位高度**，与内容无关。

这里的因果链是：占位高度 → 首帧把视口推离底部 → 容差为 1px 的跟随判定读成"用户操作" → 放弃 pin。它同时说明**为什么纯几何断言不够**：几何读数是占位高度与内容长度共同作用的结果，换一种内容配比就变了；而"这一行到底有没有真的长大"是形状问题，不随内容配比变。后续判据必须把这两者分开断言。

## 决策

### 决策 1：两个面、一个引擎

调试能力分成两个面，**共用同一个场景引擎与同一份场景文档**：

- **应用内一等公民的调试 Agent** —— 它出现在会话列表里，能被选中、能开会话、能产生真实输出，与其它 provider 在 UI 上无从区分（这是刻意的：无从区分才意味着它走的是同一条链路）。
- **dev-only 控制面** —— 一个 HTTP 面，用来装载场景文档、推进场景时钟、读取引擎自检结果。

"一个引擎"是不可协商的部分。两个面如果各自持有一套产出逻辑，那么"调试 Agent 产生的输出"与"控制面驱动的输出"就会分叉，前者无法被后者复现，控制面也就失去了它唯一的价值。引擎的实现位置是**后端**：因为产出必须经过真实的 runtime 与归一化（见决策 4），任何跑在浏览器里的引擎都必然是第二套实现。

**代价：** 调试 Agent 会出现在用户的会话列表、项目列表、用量统计里。需要在 UI 上给它一个稳定的显示名，并且接受"用户可能对着它说话"。控制面本身带来一个新的 HTTP 攻击面（由决策 6 的门控兜住）。

**被否决的替代：** 只做控制面、不做应用内 Agent。否决理由是它无法覆盖"用户从 UI 进入调试会话"这条路径，而这条路径恰好会经过 provider 选择、会话创建、WS 订阅这几处最常出问题的地方；一个只能在测试里被驱动的产出源，会在这些地方与真实 provider 分叉。

### 决策 2：调试 Agent 用运行期 provider id，刻意不进 `LLMProvider` 联合

`LLMProvider` 是**产品声明**，不是内部枚举：它的成员出现在设置页、模型菜单、权限页、技能页，并且是编译期穷尽性检查的键。把调试 Agent 加进联合，就等于宣布"这是一个产品 provider"，随后必须把它从每一个用户可见面上摘回去 —— 代价表如下（每一条都是编译强制或用户可见的）：

| 位置 | 形状 | 加进联合后被强制做什么 |
| --- | --- | --- |
| `server/shared/types.ts` | 联合定义（服务端） | 加成员 |
| `src/shared/types.ts` | 同名重复联合（前端） | 加成员，且必须与服务端保持一致 |
| `provider.registry.ts` | `Record<LLMProvider, IProvider>` | 加键，否则编译失败 |
| `provider-capabilities.service.ts` | `Record<LLMProvider, ProviderCapabilities>` | 加键；随后必须在 `listAllProviderCapabilities` 里再摘掉，否则调试 Agent 出现在 capabilities API 的返回里 |
| `session-synchronizer.service.ts` | `Record<LLMProvider, number>`（两处） | 加键；调试 Agent 会出现在同步统计里 |
| `useChatProviderState.ts` | 多处 `Record<LLMProvider, …>` 与 `PROVIDERS` 字面量 | 加键；模型/effort/权限模式的回退表都要多一条 |
| `src/shared/constants.ts` | `Record<LLMProvider, UserPreferenceKey>` | 加键 |
| `sidebarProjectFormatting.ts` | `PROVIDER_LABELS: Record<LLMProvider, string>` | 加键；否则侧栏该会话**被显示成 Claude**（不是"无标签"，见下方"代价"末段） |
| `ProviderSkills.tsx` | **另一个联合** `SkillsProvider` 上的 `Record<SkillsProvider, string>` | 不强制 —— 见下方"代价" |

除这九处之外还有若干用户可见的字面量数组（`useChatProviderState.ts` 的 `PROVIDERS`、`selectedProvider.ts` 的 `PROVIDERS`、`useProviderAuthStatus.ts` 的 `CLI_PROVIDERS`、`ModelsContent.tsx` 的 `PROVIDER_IDS`、`AgentsSettingsTab.tsx` 的内联数组）。它们**不在**上表里，因为它们本身就是 `LLMProvider[]` 类型的**值**而不是穷尽映射：加进联合不会让它们编译失败，只会让调试 Agent **静默缺席** —— 这比编译失败更糟，因为没有编译器提醒你漏了哪一处。

因此本决策取相反方向：注册表按**运行期 id** 收键。`provider.registry.ts` 的解析入口签名接受的是 `string`，所以"表里多一个键"在类型上本来就合法；不合法的是**读**的地方 —— 那些地方拿到的 `string` 要喂给期望 `LLMProvider` 的映射。做法是**一次显式的 id cast**，就落在读侧那一处。仓库里已有这个手法的先例：`sidebarProjectFormatting.ts` 的 `getSessionProvider` 把存储中的 `string` 用 `provider as LLMProvider` 收窄，并在不认识时回退到 `'claude'` —— 调试 Agent 走的是同一条路，只是它不在回退名单里，而是被显式认出来。

**代价：** 类型系统不再保护"调试 Agent 被漏掉"这件事。上表之外的任何一处新增的 provider 字面量数组，都不会因为调试 Agent 而报错；它只会在运行期表现为"某个面看不到它"。缓解措施是决策 3 的**结构性关闭**：真正的门控读的不是"联合里有没有它"，而是"registry 里有没有键"，所以漏掉一个 UI 面只影响调试 Agent 自己的可见性，不会污染产品 provider。另有一处真实代价：`ProviderSkills.tsx` 持有**第二个联合** `SkillsProvider`，调试 Agent 不在其中，因此**它没有技能页**。这是接受的设计 —— 调试 Agent 的能力来自场景文档，不来自技能。

**"漏掉一个面"的最坏形态不是缺席，是错标。** 上表把 `sidebarProjectFormatting.ts` 那一行的代价写成"否则侧栏该会话无标签"，实测偏轻：`PROVIDER_LABELS['debug']` 确实是 `undefined`（提供商文字位为空），但会话行**同时**经过 `src/shared/ui/LLMProviderLogo.tsx` —— 那是一条 `cursor`/`codex`/`opencode` 之外的落穿链，末尾 `return <ClaudeLogo />`。于是调试 Agent 的会话在侧栏带 **Claude 头像**、无障碍名读作 "Claude"，打开后每条消息也带 Claude 标签。缺席只是看不见；错标是**主动断言了一个错误的来源**，而"无从区分"正是决策 1 立论所依赖的东西。评审需决定：接受它显示为 Claude，还是给它一个明确的身份。（实测记录见"现场验证记录"c。）

**被否决的替代：** 顶替 claude runtime（让 `claude` 这个 id 在门控开启时解析到调试实现）。它的代价是**整个 claude 面变成合成的**：所有 claude 会话 —— 包括用户真实的历史会话与真实的新会话 —— 都会落到调试实现上，调试场景与真实产物无法在同一次运行里并存，"对照"这件事本身消失。而且它把门控的语义从"多了一个 provider"变成"换掉了一个 provider"，门控一旦误开，用户损失的是主路径而不是一个附加面。

### 决策 3：env 门控，默认关闭，且**关就是结构性关**

门控变量（`DEBUG_AGENT` 等）默认关闭。**关闭时不是"接口返回 403"，而是"这个东西不存在"**，四个面同时不存在：

- registry 里**没有键** —— 任何按 id 解析的路径拿到的是"未知 provider"，与拼错一个 id 无从区分；
- 路由**未挂载** —— 路由器根本没被 attach，所以没有任何请求能落到控制面的处理函数上；
  **但"未挂载"在本仓库不表现为 404。** `static-assets.module.ts` 的 SPA catch-all 对**任何无扩展名的路径**渲染 `dist/index.html`，而它挂在所有 `/api/*` 之后，因此一个未挂载的 `/api/...` 路径返回的是 **`200 text/html`**（前端壳），既不是 404 也不是 403。只有**带扩展名**的路径才 404。这条差别是承重的：它决定了"关就是结构性关"**能不能用状态码判**（现场读数与三条出路见"现场验证记录"a）；
- watcher **没有根** —— 调试 Agent 的 fixture 根不被观察，也就不会有任何 `session_upserted` 因为场景推进而广播出去；
- capabilities **没有条目** —— 它不出现在任何能力查询的返回里。

"结构性关"的必要性来自决策 2：既然类型系统已经不保护遗漏，那么"关闭"就不能依赖各处记得检查一个布尔值。**关闭态的判据必须是"整个对象不存在"，而不是"某个检查返回 false"。**

**代价：** 门控在进程启动时求值，因此切换需要重启后端。测试要么在启动前设好变量，要么起第二个进程。另外，四个面各自独立地读门控，存在"只关掉三个"的配置错误空间 —— 由决策 3 对应的后续任务的取假变体专门覆盖这一点。

> **现场验证对这四条各有一条读数，其中两条与本节文字有出入，评审需定夺**（详见"现场验证记录"）：
> registry（无键，与拼错 id 逐字相同）与 watcher（无根）两条与本节一致；
> 路由那一条见上（不是 404，是 SPA 的 200）(a)；
> capabilities 那一条方向不同 —— `PROVIDER_CAPABILITIES` 是**闭集字面量**，不随 registry 增长，
> 所以它**开着也没有条目**，即"关闭态没有条目"这条断言**恒真**、不构成关闭的证据 (b)。
> 第二类（该面的机制描述、以及开启态它**应该**是什么样）本 ADR 不擅自改。

**被否决的替代：** 运行期可切换的门控（一个 HTTP 端点打开/关闭调试 Agent）。否决理由是它把"关闭"重新变成了一个检查，而不是一个结构；而且一个能打开调试 Agent 的 HTTP 端点，在关闭态下也必须存在，这本身就违背了"关就是不存在"。

### 决策 4：必须写**真实形态的 transcript**，且帧只能来自真实归一化

调试 Agent 不能只发帧。它必须把内容写成**真实形态的 transcript 文件**（claude 方言的 JSONL，落在 provider 自己的项目目录布局下），并且**行 → 帧的转换必须交给真实的归一化实现**（按 provider 的 `normalizeMessage`，以及 `server/shared/utils.ts` 的 `createNormalizedMessage`）。

理由是这条链路上最容易被忽略的一环：**`complete` 会触发一次 REST 重取**。如果调试 Agent 只发帧不落盘，那么实时看到的与重取回来的历史就是两份不同的东西 —— 而"实时与历史不一致"正是本 ADR 要排查的那一类缺陷的同族。一个自己就会制造这类不一致的调试工具，不能用来排查这类缺陷。

这条决策同时给出**禁止第二套词表**（决策 7）的静态守卫：因为调试模块只被允许**构造方言行**，它不需要、也不允许知道任何帧字段名。守卫测试的做法是：在调试模块的源码范围内断言不存在事件字面量（如 `stream_delta`、`stream_end`、`session_upserted` 等），并断言它 import 了归一化入口。这是一条**耦合表**：调试模块 → 归一化入口 → runtime → 客户端，任何一环被绕过，守卫就红。

**代价：** 调试 Agent 必须理解 claude 的 transcript 目录编码与 JSONL 行形状，包括会话 id、cwd 编码、行内的消息结构。这份知识会随 claude 方言变化而过时 —— 而它恰恰是这里**唯一**应该随方言变化的东西（帧词表不变），所以这个代价落在正确的位置上。另需接受：写文件意味着磁盘副作用，因此必须配合 fixture 根隔离（见决策 5 与"fixture HOME 隔离与清理"）。

**被否决的替代：** 在调试模块里直接构造归一化后的消息对象（跳过 JSONL）。否决理由是它绕过了"方言行 → 归一化"这一段，而这一段正是 provider 之间差异最集中的地方；绕过它，"调试 Agent 走的是同一条链路"这句话就不成立了。

### 决策 5：两条摄入路径都要能驱动，含外部写入路径

产出必须能经由**两条**摄入路径到达客户端，且两条都要能被场景驱动：

1. **app 自己的会话路径** —— 调试 Agent 作为一等公民产生输出（决策 1）。
2. **外部写入路径** —— 有人（或某个脚本）直接往 transcript 文件追加行，app **仅旁观**：文件观察者发现变化 → 广播 `session_upserted` → 客户端按 REST 重取整行。

第 2 条是今天的零覆盖区，也是本 ADR 背景里点名的那条路径。驱动它的开关走既有的旁路语义（`sync: false`），即"不要替这个会话做同步，只观察"。**判据必须给足时间预算**：观察者的轮询间隔是 6 秒（`sessions-watcher.service.ts` 的 `interval`），项目更新的去抖是 500 毫秒（同文件的 `PROJECTS_UPDATE_DEBOUNCE_MS`），两者串联后的最坏情形接近 6.5 秒并受调度抖动影响。因此任何断言"外部写入在 N 秒内可见"的判据，**N 不得小于 8 秒**。这是**安全上界，不是下界**：观测延迟的相位与 6 秒轮询无关，实测 4 个样本落在 1.7–3.1 秒（见"现场验证记录"d），所以 N 取 5 秒的判据**不会**红 —— 说它"必红"是错的。留 8 秒的理由是它把最坏情形（轮询刚好错过 + 去抖）也包住；写成更小值是**在赌轮询相位**，而不是更严格的判据。

**代价：** 涉及真实文件观察者与轮询，测试因此比纯进程内测试慢（每条外部写入断言至少 8 秒），且对文件系统事件的时间抖动敏感。另外第 2 条路径的正确性依赖"目录仍然存在"这类边界（`pruneOrphanedSessions` 只在本目录仍存在时才删除索引行），fixture 的清理顺序必须尊重这一点。

**被否决的替代：** 只驱动第 1 条路径。否决理由是它无法覆盖 `session_upserted` → REST 重取这一段 —— 而这段没有 runtime 参与，是两条路径里唯一不被第 1 条路径覆盖的部分。

### 决策 6：控制面走 HTTP + 既有 `authenticateToken`，**门控才是安全边界**

控制面是一个挂在既有鉴权中间件下的 HTTP 路由，复用服务入口已经使用的那一个 `authenticateToken`（服务端入口对 provider 路由就是这么挂的）。不新增 WebSocket 通道，不新增 CLI 脚本。

- **不新增 WS 通道**：控制面是"装载场景、推进时钟、读自检结果"这类请求/应答式操作，没有服务端推送需求；新增一条 WS 通道意味着新增一套握手、鉴权与重连语义，收益为零。
- **不新增 CLI 脚本**：脚本会绕过鉴权中间件，把控制面变成"本机任何进程都能驱动"的面；而且脚本一旦存在，它就会成为第二个入口，与 HTTP 面争夺"谁是控制面"。

**安全边界是门控，不是鉴权。** 这句话要说清楚：`authenticateToken` 保护的是"已登录用户"。而调试 Agent 在**关闭态下**对已登录用户也必须不存在 —— 它不该出现在任何用户的 capabilities 里，也不该有任何路由可打。鉴权回答"你是谁"，门控回答"这个东西是否存在"。二者都不能替代对方：门控开着但没有鉴权，等于把产出源交给任何能连上端口的人；有鉴权但门控只是一个布尔检查，则任何一处漏检都会把它暴露给已登录用户。

**代价：** 复用 `authenticateToken` 意味着控制面在测试里需要一个有效凭据，测试必须先铸造再回收（铸造/回收走既有的脚本入口）。另外，把门控当作安全边界，意味着**门控求值失败必须往"关闭"倒**（fail-closed）：变量缺失、取值不认识、解析异常，一律按关闭处理。

**被否决的替代：** 用一条本机回环地址 + 独立端口提供免鉴权控制面。否决理由是"本机"不是安全边界（同机其它用户与任何本地进程都在这个边界内），而免鉴权面一旦被误开就是无凭据的产出源。

### 决策 7：禁止第二套事件词表 —— 调试模块只构造方言行

调试模块的职责边界是**构造方言行**。帧只能来自 `normalizeMessage` / `createNormalizedMessage` 这条真实路径。因此：

- 调试模块的源码范围内不出现任何帧字段名或事件名字面量；
- 调试模块 import 归一化入口，由一条守卫测试固定住这个 import（拿掉它，守卫红）；
- 场景文档描述的是**行**与**几何/意图**，不是帧。场景里的 `expect` 断言的是"服务端归一化之后应该出现什么"，而不是"我直接发了什么"。

**代价：** 场景作者无法通过场景文档直接表达某一种帧形状（例如"发一个带特定字段的权限帧"）。想覆盖那类形状，只能去构造一条**在方言里确实会归一化成那种帧**的行。这在短期内会让某些场景写起来更绕，但它换来的是：每一个被观察到的帧都能追溯到一条真实的方言行，反过来每一条方言行都能被真实归一化解释。

**被否决的替代：** 允许调试模块在场景里直接声明帧（"发帧模式"）。否决理由是它会立刻产生第二套词表，而第二套词表与真实归一化的输出之间没有任何机制保证一致；一旦分叉，用调试 Agent 观察到的行为就不再是关于产品的证据 —— 这正是本 ADR 要建立的东西的对立面。

## 场景文档 schema

场景文档是引擎的唯一输入。字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `version` | 整数 | schema 版本，当前为 `1`。引擎遇到不认识的版本必须拒绝装载，不得猜测。 |
| `id` | 字符串 | 场景标识，用于自检结果与产物命名。 |
| `dialect` | 闭集 | 方言。v1 只有 `"claude"` 一个取值。闭集是刻意的：新增方言是一次需要论证的扩展，不是随手加一个字符串。 |
| `home` | 闭集 | fixture 根的取法。v1 只有 `"fixture"` 一个取值 —— **没有**"用真实 home"这个取值，真实 home 由构造被排除在外。 |
| `transcript.mode` | 闭集 | `"appended"`：调试 Agent 自己写文件（走决策 5 的第 1 条路径）。`"external"`：由场景之外的写入者追加，app 仅旁观（走第 2 条路径，`sync: false`）。 |
| `t0` | 整数 | 场景时钟原点（绝对毫秒时间戳）。`at` 相对于它。 |
| `steps[]` | 数组 | 按 `at` 非降序排列的步骤。 |
| `steps[].at` | 整数 | **绝对**毫秒（相对 `t0`）。用绝对毫秒而不是"相对上一步的间隔"，是为了让场景文档在编辑后仍然逐字可 diff：插入一步不会移动后续所有步骤的时间。 |
| `steps[].op` | 闭集 | 见下。 |
| `expect` | 对象 | 引擎在场景结束后的自检块。 |

`op` 的闭集：

- `"row"` —— 向 transcript **追加一整行**（新的消息行）。行数 N → N+1。归一化后应出现一条新的消息（新 id）。
- `"grow"` —— **就地重写最后一行**，让它的内容变长。行数 N 保持不变，行的字节长度变化。归一化后是**同一**条消息（同 id）内容变化。
- `"scroll"` —— 观察者侧动作：设置跟随意图，或把视口移到某个位置。
- `"wait"` —— 只推进场景时钟，不产出。

**`row` 与 `grow` 的分界**（这是整个 schema 里最容易写错的一处，因此单独写明）：`row` 改变**行数**，`grow` 不改变行数、只改变**字节数**。这条分界的意义在于，任何只数行数的断言都对 `grow` 完全失明 —— 而"就地增长"恰恰是流式输出最常见的形状。反过来，任何只看几何的断言都对两者的区别失明（两者都会让内容区变高）。**所以一个能区分"真产出"与"只发帧"的判据，必须同时断言行数/内容与几何两者**；只断言其中一侧，就等于给另一侧留了一个空洞。

> **现场验证补充（范围问题，评审需定夺，见"现场验证记录"e）：** `row` 与 `grow` 都走"写方言行 → 真实归一化"这条路，
> 而 `stream_delta` **只**由 SDK 实时形状（`type:'stream_event'` 且 `event.type === 'content_block_delta'`）产出，
> 从不落进 transcript。于是决策 7 + 决策 4 合起来意味着：**按本 schema 构造的产出源永远产不出 delta 帧**，
> `grow` 产出的是**同一条消息 id 的整条 `text` 帧**而非增量帧。
> 这不否定 `row`/`grow` 的分界（它对"行数 vs 字节数"仍然成立），但它决定了后续任务 7 的范围：
> 若漂移由**已有行内容变长**驱动，`grow` 覆盖得到；若由 **delta 帧**驱动，本机制按构造覆盖不到。
> 这是"漂移的成因是哪一种"这个事实问题，需以现场读数回答，本 ADR 不擅自收窄。

`expect` 自检块的三个子块，缺一不可：

- `expect.rows` —— 行数变化（`{"delta": N}`）；
- `expect.content` —— 内容断言（`{"mustContain": [...]}`、`{"lastRowGrew": true}`）。**这一块是把"只发帧"钉死的地方**：只发帧的实现不会在文件里留下任何可断言的内容。
- `expect.geometry` —— 几何断言，写成**区间**而不是点值（`{"bottomGapPx": {"max": 8}}`）。写成点值会把现场数字固化成阈值（见"回放的保真与不保真"）。
- `expect.followIntent` —— 场景结束时应有的跟随意图（`"follow"` / `"detached"`）。

## 回放的保真与不保真

引擎有两种运行模式，两者的承诺**不同**，必须分开写：

**驱动模式（drive）** —— 场景文档 → 真实产出 → 观察。这是权威模式。

**回放模式（replay）** —— 输入是一份场景文档加上一次驱动运行留下的产物（transcript 字节 + 帧序列），把它重新喂回链路。它**保真**的是：

- 帧的**序列、顺序与负载**：与录制时逐帧相同；
- `seq` 与重放语义：同一份序列得到同一份 `seq` 分配；
- `complete` 触发的 REST 重取结果：与录制时相同；
- 归一化结果：同一份方言行得到同一份归一化消息。

它**不保真**的是：

- **墙钟时间**：回放按自己的节奏推进，帧之间的真实间隔不重现。因此任何关于"节奏/间隔/累积时长"的断言不适用于回放。
- **渲染几何**：视口几何是 DOM、CSS 与字体度量共同作用的结果。回放的帧序列相同，但换一个构建、换一种字体度量，同一个占位高度与同一段内容会得到不同的几何读数。**几何断言属于驱动模式，回放模式不得承担几何断言。**
- **模型侧与网络侧**：real CLI 的分词节奏、thinking 块、限流与错误语义都不重现。回放不覆盖这些，也不假装覆盖。

最后一条不保真是"现场数字 vs 类"这条区分的直接后果：正因为几何读数不可跨构建保真，后续判据里的几何阈值必须由运行导出或写成区间，**不得**把本 ADR 记录的任何现场数字抄成常量。

## fixture HOME 隔离与清理

调试 Agent 必须有一个自己的 home，规则如下：

- **根来自门控变量**，不来自 `os.homedir()`。这是承重的：claude 会话同步的 home 是 `path.join(os.homedir(), '.claude')` 这样的**类字段**，它读的是进程的 `HOME`。若调试 Agent 复用它，fixture 就会落到真实 home 里。
- 仓库里已有这条路径出事的记录：`session-synchronizer.service.ts` 的注释明确写着，一次"指向了真实 `~/.claude` 的测试运行"留下的 transcript，因为观察者只对 `add` / `change` 反应而不对 `unlink` 反应，在侧栏留下了一个永久条目，点开是空的 "Untitled" 会话。fixture 隔离不是洁癖，是这条已发生过的故障的修复面。
- **fixture 根必须建在测试自己的临时目录下**，且清理必须是显式的、在 teardown 里执行的整目录删除。
- **必须有一条断言证明真实 home 未被写入**：不只看 fixture 根被清理了，还要正面断言真实 home 在这次运行中没有新增（不存在性断言或修改时间断言）。
- 清理顺序要尊重 `pruneOrphanedSessions` 的边界语义：只有当**所在目录仍然存在**时，索引行才会被删除。因此"先删 fixture 根再断言索引被清理"是错的顺序，正确顺序是先让索引收敛、再删根。

## 边界与不做的事

- **本 ADR 不实现任何东西。** 不实现引擎、不实现 provider、不实现控制面、不写任何代码、不改任何现有文档。实现与判据化在评审通过后另行立案。
- **不修正 `docs/architecture/02-realtime-stream.md` 里已被证伪的断言。** 该文档断言流式与否"取决于 provider"，并把 Claude 与 Codex 划到不流式一侧。这次现场观察与该断言的关系（是否一并修正）留作**评审时的开放问题**，不在本 ADR 内裁决。
- **不写本机绝对路径。** 现场读数的来源以"一次会话、一台设备、一种内容配比"描述，不落具体路径。
- **不点名任何未完成任务 id。** 后续工作只以本 ADR 的"后续任务草案"描述，评审通过后另行立案。
- **不给阈值。** 本 ADR 只登记"类"与"现场数字"，任何判据的阈值由运行导出或写成区间。
- **不做多方言。** v1 只有一种方言；`dialect` 取值是闭集，扩展需要单独论证。

以上每条"不做"都配有取假变体（见下节）：边界如果没有取假变体，它就只是一句声明，不是一条判据。

## 后续任务草案

八条。每条给出判据与**取假变体** —— 取假变体指的是"刻意做一个假实现，这条判据必须因此变红"。判据若在假实现下仍然是绿的，它测的就不是它声称要测的东西。

### 后续任务 1：场景引擎骨架与 `row` 路径

- **判据：** 装载示例一那类场景文档，走真实 runtime 产出帧，并断言 `expect.rows` 与 `expect.content` 双双成立；同时断言 REST 重取得到的历史与实时所见一致。
- **取假变体：** frames-only —— 只发帧、不写 transcript 文件。该变体必须让 `expect.content` 红。

### 后续任务 2：外部写入路径（`sync: false`）驱动

- **判据：** 装载示例三那类场景，在**不小于 8 秒**的观测窗口内，断言外部追加的行经由 `session_upserted` 广播后出现在 REST 重取结果里。**判据必须自己排掉一个干扰源：装载场景这一步本身就会产生一次 `session_upserted`**（观察者把刚写下的种子文件读成 `add` 事件，最多迟一个轮询周期才广播）。因此"等到一个 upsert 就放行"是**盲判据** —— 它会被装载那一次满足，外部写入根本没被证明。判据要按三步写死：(i) 先等到**没有新 upsert** 且静默超过一个轮询周期，把装载那一次排空；(ii) 再追加，并要求一条**新的** upsert；(iii) 以观察者自己的日志行（`change event for provider …`）作**正面控制**，证明这一条确实走了观察者而不是别的路径。
- **取假变体：** 绕过网关 —— 不经过文件观察者与广播，直接把行插进数据库或直接改客户端状态。该变体必须红（它没有经过观察者，因此 `delivery.path` 断言与 (iii) 的正面控制都不成立）。**注：这一条取假变体是本 ADR 里唯一实测骗过了一版判据的** —— 现场第一版只断言"出现了一个 upsert"，在真实实现下绿、在"绕过网关"下也绿（因为装载那次替它顶了）。

### 后续任务 3：`grow` 就地增长 op

- **判据：** 装载示例二那类场景，断言行数 N 不变、最后一行的字节长度增加，且归一化后是**同一条**消息 id 的内容变化。
- **取假变体：** 把 `grow` 实现成新行（N 增加）。该变体必须红 —— 它会让 `expect.rows` 的 `delta` 断言失败。

### 后续任务 4：控制面 HTTP 与鉴权

- **判据：** 门控开启时，携带有效凭据的请求可用、缺凭据的请求返回 401；门控关闭时，**该路径不以控制面的应答作答**。
  **不能写成"返回 404"** —— 本仓库的 SPA catch-all 让未挂载的 `/api/...` 路径返回 `200 text/html`，所以写 404 的判据**在实现完全正确时也必红**（现场读数与三条出路见"现场验证记录"a）。可用的写法有三种，择一：给控制面路径加扩展名（带扩展名的路径确实 404）；在 `/api` 下、SPA 之前加一个 404 兜底；或断言"不是控制面的 JSON 应答"。
- **取假变体：** 门控关闭但仍挂载路由。该变体必须红。**注意这条取假变体在"判据写 404"时是失效的**：关闭态的真实状态码就是 200，假实现与真实现输出**相同**，红不了。判据必须先按上面改正，取假变体才有鉴别力 —— 这是"判据写错会连带废掉它的取假变体"的一个实例。

### 后续任务 5：门控的结构性关闭

- **判据：** 门控关闭时，四个面逐一断言：registry 无键（按 id 解析失败）、路由未挂载、watcher 无根（场景推进不产生广播）、capabilities 无条目。
  **其中两条按现文写会失效，须按"现场验证记录"(a)(b) 改写：**
  「路由未挂载」**不能落成状态码断言**（未挂载的 `/api/...` 返回 SPA 的 `200`，不是 404 —— 见后续任务 4 的同一条更正）；
  「capabilities 无条目」**恒真**（那张表是闭集字面量，开着也没有条目），因此它**不构成关闭的证据**，按本 ADR 自己的标准属于假判据 ——
  要么从四面里去掉，要么换成一条真正随门控变化、在假实现下会红的断言。
- **取假变体：** 只关掉其中三个面（例如保留了 registry 键但摘掉了路由）。该变体必须红 —— 它是"四个面各自独立读门控"这个代价的正面覆盖。**注意：** 若"路由"那一面按现文写成 404 断言，本取假变体同样失效（关闭态真实现与假实现的状态码相同，见后续任务 4）。

### 后续任务 6：禁止第二套词表的静态守卫

- **判据：** 在调试模块的源码范围内断言不存在帧/事件字面量，并断言它 import 了归一化入口；两者在同一份耦合表里锁住。
- **取假变体：** 在调试模块里手写一个 `stream_delta` 字面量。该变体必须红。

### 后续任务 7：贴底漂移的可复现判据（几何 + 内容双断言）

- **判据：** 在示例一那类场景下，跟随意图全程成立，断言累积漂移落在由运行导出的区间内，并断言"跟随不再自行修复"这一失败模式不出现。几何阈值由运行导出或写成区间。
  **范围前提待定（见"现场验证记录"e）：** 本机制按构造产不出 `stream_delta`，`grow` 给的是同一条消息 id 的整条 `text` 帧。若本条要复现的漂移由 delta 帧驱动，则示例一/二**覆盖不到**它，本条判据须先收窄到"内容变长驱动的那一半"，或另辟路径；这个前提应由评审以现场读数判定，不能默认成立。
- **取假变体：** **只断言几何**（去掉内容与行数断言）。该变体必须红 —— 这正是"纯几何断言挡不住 frames-only"这一点：只发帧的实现同样会改变几何占位，几何单一断言会对它放行。这条取假变体是本草案里最重要的一条，因为它是唯一能同时守住决策 4 与决策 7 的判据。

### 后续任务 8：fixture HOME 隔离与清理

## Adjudication

**状态：通过（附五项裁决）。** 评审人 **yale**，2026-09-22。本小节记录的是**评审人的结论**，不是文档作者的自我评价。

**结论：通过。** 按「后续任务草案」推进，但范围收窄：八条里 **1–6、8 立实现任务**，**第 7 条移出本范围**（裁决 C）。

### 裁决 A：调试 Agent 必须有自己的显示身份

采纳「现场验证记录」c 的判断：接受 UI 上的**错标**是不可接受的。决策 1 的立论是「无从区分才意味着它走的是同一条链路」，而当前实现给出的不是无从区分，是**冒名** —— 侧栏与消息都自称 Claude。一个用途是产生可信证据的调试面，其产物自称另一个 provider，会污染读证据时的第一判断。

**实现要求：** `PROVIDER_LABELS`（`sidebarProjectFormatting.ts`）放宽并加一键；`LLMProviderLogo`（`src/shared/ui/LLMProviderLogo.tsx`）在落穿链之前插入该 id 的判断。**不把它加进 `LLMProvider` 联合** —— 决策 2 反对的是加进联合，不是给它显示身份；两处落点的 props/索引本就接受 `string`（`PROVIDER_LABELS` 的类型需从 `Record<LLMProvider, string>` 放宽）。

### 裁决 B：capabilities 由「四面」降为「三面」

采纳「现场验证记录」b：`PROVIDER_CAPABILITIES` 是**闭集字面量**，不随 registry 增长，因此「关闭态没有条目」**恒真**，按本 ADR 自己的标准属于假判据（判据若在假实现下仍绿，它测的就不是它声称要测的东西）。

**裁定：** 决策 3 的「四个面」改为**三面**（registry 无键、watcher 无根、路由未挂载），并在决策 3 内明确记录 capabilities 由闭集字面量天然免疫、不构成关闭的证据。**不**为了这一面去增加门控耦合。

**未决并转交实现：** 既然它不进联合，开启态它也没有 capability 记录，前端 `getProviderCapabilities('debug')` 会拿到 `undefined` —— 该路径的行为（应回退还是应显式处理）**本次未实测**，由实现任务的判据承担。

### 裁决 C：后续任务 7 移出本 ADR 的范围

1. 「现场验证记录」e 已证：本机制**按构造产不出 `stream_delta`**（它只由 SDK 实时形状产出，从不落 transcript）。若那类漂移由 delta 帧驱动，示例一/二覆盖不到。
