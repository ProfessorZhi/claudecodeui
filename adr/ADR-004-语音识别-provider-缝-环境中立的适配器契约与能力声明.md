## 背景

语音输入链路今天只支持一种识别服务：OpenAI-compatible 的 `/audio/transcriptions`。配置面（`baseUrl` + `apiKey` + `sttModel`）看起来通用，但**协议形状被硬编码在四处**，所以换一个形状不同的服务不是配置问题，而是请求根本发不出去。

### 一、四处硬编码，且两跳不同

先分清两跳，否则下面的描述会自相矛盾：

- **客户端 → 服务端（仅代理路径）**：multipart 字段 `audio`，**不带** `model`；模型与密钥走 `x-voice-*` 请求头。
- **客户端 → 识别服务（直连路径）** 与 **服务端 → 识别服务（代理路径）**：字段 `file` 与 `model`，`Authorization: Bearer`，路径写死 `/audio/transcriptions`。

| 处 | 位置 | 硬编码了什么 |
| --- | --- | --- |
| 1 | 客户端直连分支的**请求构造** | multipart `file` + `model`、`Authorization: Bearer`、写死路径 |
| 2 | 客户端直连分支的**响应解析** | `res.json()` 后取 `.text`；**非 JSON 响应会抛异常** |
| 3 | 服务端代理分支的**请求构造** | multipart `file` + `model`，URL 由配置 base URL 加写死路径拼成；没有 `language`、没有 `prompt`、没有 `response_format` |
| 4 | 服务端代理分支的**响应解析** | 只认 `{ text }`；**非 JSON body 被当作转写文本原样返回** |

第 2 与第 4 处**容忍度不同**，这一点比"数量是四处"更重要：同一个上游异常（例如网关返回 HTML 错误页），在直连路径上是报错，在代理路径上会被当成一段转写文本填进 composer。**两条路径已经分叉**，这正是本 ADR 要消灭的那类不一致的现存实例。

另有一处不对称：代理路径的 base URL 只认服务端环境变量，**没有任何 `x-voice-base-url`**，因此代理路径的端点不可由请求指定（这是**有意**的安全约束，见决策 7）。

### 二、为什么能力面不是"预留字段"，而是承重的

本仓库已经实测过若干条轴，每一条都对应一个真实效应，而不是推测：

| 轴 | 已测结论 |
| --- | --- |
| 提示词偏置 | 中文 + 出货裁剪下**有害**：句读由 2.31 掉到 1.25，标识符逐字存活由 33.3% 掉到 22.2%；英文未裁剪时才 +0.63 |
| 语言参数 | 已明确不采用：真实使用是混合语种，误判比不判更糟 |
| 换模型 | 换成 `whisper-large-v3` 无收益证据，两语种 CER 都更差 |
| 计费单位 | Groq 有 10 秒/请求下限；裁剪省下的 25.5%（中文）/ 13.3%（英文）就是对着这个下限算出来的 |
| 停顿线索 | 裁剪把**中文**句读打到 −89%，而 CER 只 +0.52pp —— **CER 对标点损失失明** |

最后两行构成一条设计级结论：**裁剪删掉的停顿，正是标点线索**。在按秒计费的服务上"裁了省钱"，在多模态大模型上"留着可能换回标点"。因此"裁不裁"必须成为识别器自己声明的属性，而今天没有任何地方能表达它。

### 三、验证通路的现状：缝已经存在，但在仓库外，而且与出货代码不是同一条

既往实验已经把"换识别器"的接口发明出来了：仓库外的实验工装（其位置登记在 `docs/experiments/README.md`）里，唯一碰 HTTP 的模块是 `groq.mjs`，其 `transcribe(filePath, { prompt, language, responseFormat, model })` 是全部契约，换服务只需实现同名函数而所有 runner 不必改动。该接口写在 `docs/experiments/2026-09-22-voice-punctuation.md` 的末节（该文标题即"对后续其它识别模型/服务实验的接口"），**不在** `README.md` 的工装表里——README 登记的是位置与协议，接口本身在实验记录里。

但它在仓库外。仓库内能离线跑的实验只有 `experiments/` 下的 runner（冻结 fixture、不联网、量的是出货模块）。而出货代码里的 ASR 调用是**内联在客户端 hook 与服务方法里的 fetch**，没有任何可 import 的纯模块。

结论：**今天无法在新识别服务上做任何"证明出货代码正确"的验证** —— 因为不存在一个既是出货实现、又能在命令行里直接调用的对象。

### 已有先例

`server/modules/providers/` 是本仓库"可插拔外部服务"的既定形态：`AbstractProvider` 的若干面 + `list/<id>/` 每服务一个目录 + 集中解析的 registry + 一份"How to add a provider"的 README。本 ADR 的适配器形状**沿用该先例的词汇与布局**，包括它的失败模式（见决策 7）。

### 与设计文档的分工

本 ADR 是一份更长的设计文档的**决策记录**：`docs/proposals/voice-asr-provider-seam.md` 承载完整论证（契约草稿、能力字段的逐条出处、文件布局、三处缺口的修改要求、分阶段实施）。本 ADR 从中取出**决策**，逐条补上代价与被否决的替代；设计文档保留过程与选项。

两者不一致时**以本 ADR 为准**（它是评审的对象），设计文档随评审结论一并修订。**本 ADR 的范围包含那份设计文档内的对应表述**——评审时两者一并看。

## 决策

### 决策 1：差异用"适配器缝 + 能力声明"表达，不用配置字段表达

引入一层适配器：每个识别服务一个纯模块，导出一张 `AsrCapabilities` 与一个 `transcribe(request, invocation)`。调用方按 provider id 从 registry 解析，注入全部环境依赖（`baseUrl`、`apiKey`、`model`、`timeoutMs`、`fetchImpl`、`signal`）。

`invocation` 与 `request.hints.context`（发给模型的会话上下文）是两回事，命名上不得复用同一个词。

能力声明的字段与**每个字段为什么存在**：

| 字段 | 存在的理由 |
| --- | --- |
| `acceptsMime` | 不同服务接受不同容器；出货链路今天会在裁剪后把音频重编码为 WAV，而录音默认是 webm/opus。**匹配按基类型**（见决策 4 缺口一） |
| `maxInlineRequestBytes` | 内联上限因服务而异。**注意这是整个请求的预算，不只是音频**：官方对某多模态服务的表述是"最大请求 20MB（含提示词与所有文件）"，因此提示词与上下文与音频共享同一预算（与决策 6 相撞） |
| `oversize` | 超限后的行为必须是显式声明（第一版只允许 `reject`），不能靠"上游会报错" |
| `honors.{prompt,language,context}` | 声明"发了有没有用"；声明为 false 时适配器必须**拒发**而不是静默丢弃 |
| `billing` | 秒 / 音频 token / 请求。决定省时长读数怎么折算，进而决定裁剪的性价比 |
| `pauseCues` | 停顿对该识别器是破坏性、中性还是有用。**驱动是否裁剪** |
| `style` | 能否给出书面化文本（见决策 5） |
| `oneShot` | 第一版只允许 `true` |

**代价：** 多一层间接。今天的服务方法是"读配置 → 拼请求 → 解析响应"一段直线代码，拆开后要跨三个文件才看得见一次调用。另一处代价是新服务不再能靠"填 baseUrl"接进来 —— 必须写一个适配器文件。这是**有意的**：正是因为"填个 URL 就能接"这个错觉，才让今天这条缝不存在。

**被否决的替代：** 继续用配置字段表达差异（例如加一个协议开关分支，或在服务方法里按 provider 名分支）。否决理由是分支会落在**两处**（直连分支与代理分支各一份），而两处一旦分叉，用户在"配了 baseUrl"与"没配 baseUrl"两种情形下会得到不同行为 —— 上面背景第一节第 2、4 处的容忍度差异就是这种分叉的现存实例。适配器缝的价值不在于少写代码，而在于**同一个实现同时服务两条路径**。

### 决策 2：适配器必须环境中立；落点由边界探针决定，且探针的四个障碍必须先解决

适配器要同时用于浏览器（直连）、Node 服务端（代理）、命令行三处。因此它必须是环境中立的纯模块。

**落点候选是仓库根 `shared/`**，依据是两套编译配置的 include 事实（这不是偏好，是可核对的）：

- 根 `tsconfig.json` 的 `include` 含 `shared`；其 `types` 只有 `vite/client`，`lib` 只到 `ES2020` + DOM。
- `server/tsconfig.json` 的 `include` 含 `../shared/**/*.ts`，`rootDir` 为上一级，产物落进 `dist-server/shared/`；其 `exclude` 含 `../src`。

**但"唯一被两套 tsconfig include"远不等于"能被两侧导入"。** 评审实测出四个障碍，任一个都能让探针红：

1. **前端 lint 禁止相对导入，且没有任何别名能到达仓库根 `shared/`。** 前端 override 对 `src/modules/**` 与 `src/shared/*.ts` 施加 `no-restricted-imports`（正则匹配以 `./` 或 `../` 开头的说明符），等级 error，提示语是"使用 `@/` 源根别名"。而 `@` 映射到 `src`，`package.json` 里没有 `imports`、也不是 workspace 布局，**不存在通往仓库根 `shared/` 的别名**。三条路全堵：相对导入 ⇒ 该规则报错；`@/shared/asr/…` ⇒ 落进 `src/shared/asr/`（错树）；裸写路径 ⇒ `importx/no-unresolved`（同一 override 里也是 error）。旁证：今天 `src/modules/**` 与 `src/shared/**` 里的相对导入数为 **0**，即该规则真的在生效、且一直被遵守。
2. **`.js` 说明符与"裸 node 跑 CLI"不可兼得。** `server/tsconfig.json` 是 NodeNext + 发射式构建，因此其内部相对导入**必须**写 `.js`（服务端 TS 一律如此，全仓无一处 `.ts` 说明符）。而裸 node 对说明符做字面解析、**不把 `.js` 映射到 `.ts`**：实测在暂存目录里，`b.ts` 存在而 `a.ts` 写 `import … from './b.js'` 时，裸 node 报 `ERR_MODULE_NOT_FOUND`；同一文件用 `npx tsx` 运行则通过。
3. **`shared/` 不在 lint 路径里。** `npm run lint` 的路径列表是 `src/ server/ scripts/`，**不含 `shared/`**。因此登记 `boundaries/elements` 买到的是"不被 `no-unknown` 判红"，**不是**"被 lint 覆盖"——两者不是一回事。`experiments/` 同理（既不在 lint 路径、也不在任何 tsconfig），所以 CLI 也不受静态检查。
4. **`.ts` 那半从未被证明过。** `shared/` 今天唯一的文件是**纯 JS** 的 `networkHosts.js`，消费者是构建配置与服务端入口。两侧都能解析 `.js`，**不蕴含**两侧都能解析 `.ts`；而上面三个障碍恰好都住在 `.ts` 那一侧。

由此得出结论：**探针不是"跑一下看看"，而是必须先解决上面第 1、2 条**。可选路径只有两条：

- **(a) 为仓库根 `shared/` 创造一条别名**，且必须三处同时（根 `tsconfig.json` 的 `paths`、`vite.config.js` 的 `resolve.alias`、oxlint 的 resolver 配置），并把 CLI 改为 `npx tsx` 运行；
- **(b) 落回 `src/shared/asr/`**，即决策 3 的后备方案。

**本决策同时修正一版原稿的错误约束。** 原稿第一条硬约束写"只用相对导入，禁止 `@/`"——这条**在前端侧恰好是错的杠杆**：前端 lint 禁止的正是相对导入。正确的表述是：**导入形式必须是两侧都接受的那一种**，而两侧都接受的形式**目前不存在**，需要由路径 (a) 创造出来。这是本次评审最有价值的一条产出：一个从"服务端编译要求"推出的约束，在另一侧正好是反的。

修订后的硬约束（违反必然在其中一侧失败）：

1. **导入形式必须两侧都接受** —— 当前不存在，需由路径 (a) 的别名创造；在此之前探针必红。
2. **相对导入的说明符扩展名由服务端构建决定（`.js`）**，因此 CLI 必须以 `npx tsx` 运行（实测：裸 node 对 `.js` 说明符失败）。备选是给 `server/tsconfig.json` 加 `allowImportingTsExtensions` 与 `rewriteRelativeImportExtensions`（实测 tsc 退出 0，且把 `./b.ts` 重写为 `./b.js`、产物裸 node 可跑），但它**改动的是全局构建配置**，波及面远大于一个 CLI 的启动方式。
3. **不碰 node 内建** —— 根侧 `types` 只有 `vite/client`，`process`、`Buffer`、`node:*` 无类型。这正是 CLI 入口不能放进 `shared/` 的原因。
4. **也不要用 ES2021+ 的库特性** —— 这是上一条**对称的另一半**，原稿漏了：服务端 `lib` 是 `ES2022` 而根侧是 `ES2020`，所以 `replaceAll`、`Array.at`、`Error.cause`、`structuredClone` 在服务端编得过、在前端侧**编不过**。同一条机器判据，低一层。
5. **`isolatedModules` 开着**：类型再导出必须写 `export type`。
6. **环境依赖一律注入**：既满足第 3 条，又让同一个适配器在三处同构可测。

"两套 tsconfig 同时编译同一份文件"是环境中立性的**机器判据**：它必须同时满足 `lib: DOM` + `moduleResolution: Bundler` 与 `lib: ES2022` + `NodeNext` + `types: node`。

CLI 因此放在 `experiments/` 下（与既有 runner 同形，但**启动方式改为 `npx tsx`**）。提升为操作面命令（`cloudcli …` 子命令）留待验证闭环之后。

**代价：** 若走路径 (a)，要动三个配置文件（两套 tsconfig 之一、Vite 配置、oxlint 配置），而别名是全局性的——它会让仓库根 `shared/` 从此成为一个前端可达的依赖面，需要纪律约束（谁可以往里放东西）。另需接受：即便登记了，`shared/` 仍**不在 lint 路径**里，除非同时改 `npm run lint` 的路径列表；否则"被 lint 覆盖"这件事在本 ADR 里只能登记为**未达成**，不能写成达成。

**被否决的替代：** 放在 `server/modules/voice/providers/`（与既有 provider 布局最一致）。否决理由是它与决策 7 冲突：直连模式下浏览器持有密钥并直接调用识别服务，服务端不在链路上；适配器若只住在 `server/`，浏览器就必须有第二份实现 —— 而那正是本仓库已经付过代价的失效（一次判据量的是工装里的副本而不是出货模块，与出货实现 16 条里 6 条不一致）。

### 决策 3：边界探针是一个闸，后备方案必须连同"服务端不可达"的后果一起写死

决策 2 的落点依赖一个**尚未验证**的组合：前端模块导入仓库根 `shared/` 下的新模块。因此第一步必须是一个边界探针，以实证为准：

1. 最小模块落在候选落点，从 `src/modules/**` 与 `server/modules/**` 各导入一次；
2. `npm run typecheck` 退出 0（两套配置同时编译同一份文件）；
3. `npm run lint` 退出 0，且 lint 路径列表**确实包含**该目录（否则这一步只证明"没被判红"，不证明被覆盖）。

**后备方案 (b)：线协议实现只能有一个家，即 `src/shared/asr/`。** 不允许的路径是"在服务端目录下再写一份线协议实现"。

**但后备方案有一个一版原稿没有承认的后果，必须写在这里：它会让缺口一与缺口三变成不可实现。** 因为：

- `server/tsconfig.json` 的 `exclude` 含 `../src`，且服务端的 `@/` 映射到 `server/*`，所以**服务端消费不到 `src/shared/asr/`**；
- 而缺口一（MIME 白名单由 `capabilities.acceptsMime` 决定）与缺口三（健康检查返回 provider 列表与各自能力）**都是服务端路由的改动**。

也就是说，后备世界里"服务端侧不新增 provider"这句话，实际含义是**服务端无法按 provider 断言能力**，因而缺口一、缺口三只能退化为"服务端保持现状"。它同时正面击中决策 7 的要求（两条路径都必须把 provider 解析到同一份适配器）。

因此：**缺口一、缺口三对应的后续任务是有条件的**（仅在路径 (a) 成立时成立），它们的判据必须写明这个前提，而不能写成无条件。原稿把"代价"只写成措辞风险，是低估。

**代价：** 决策 2 的落点与决策 3 的后备方案会分叉出两种后续形态（服务端能不能接新 provider 取决于探针），后续任务的措辞因此必须显式标注条件，而不是笼统写。另外探针本身是一个一次性判定 —— 它的**读数**可以判据化（见后续任务草案），但它的**结论**（落点是否成立）是人读的。

**被否决的替代：** 先按服务端目录开工、等真需要浏览器侧时再处理。否决理由是那时会被迫二选一：要么把已经写好的服务端适配器搬走（并重写它的所有判据），要么接受两份实现。两条路都比先花一次探针贵。

### 决策 4：三处既有缺口由能力声明驱动修复，但"单一计算点"这个说法是错的

本次勘查发现三处既有缺陷。它们不因新 provider 才存在，但新 provider 会把它们从"缺陷"变成"错误"，因此纳入本 ADR 范围。

**缺口一：转写路由没有 MIME 白名单。** 上传只受大小限制，MIME 只做 `|| 'audio/webm'` 兜底。仓库内已有先例形状（资源模块的上传过滤器）。修法：白名单由所选 provider 的 `acceptsMime` 决定，**不新增第二个全局常量**；拒绝必须发生在读取上游**之前**，返回语义码且不消耗一次上游请求；客户端必须能拿到 `acceptsMime`。

**这里有一条一版原稿漏掉的匹配语义**：浏览器首选录音 MIME 是**带参数**的（`audio/webm;codecs=opus` 是候选列表首项），而服务商公布的是**基类型**（`audio/webm`，无参数）。按公布列表做**精确匹配**会把**出货录音器自己的输出**判为不支持——正是缺口一要防的那件事，只是机制不同。因此白名单必须**按基类型匹配（剥离 `;` 之后的参数）**，且判据要覆盖这条。

**缺口二：25MB 上限与 provider 的内联上限互不知情，是两个真相源。** 原稿写"有效上限必须是 `min(全局硬上限, capabilities.maxInlineBytes)` 的**单一计算点**"——**这个说法是错的，因为它不是单点**：

- multer 在**handler 之前**按 `LIMIT_FILE_SIZE` 拒绝，且它**无从知道 provider**——它只能取一个与 provider 无关的界；
- per-provider 的 `min(全局, provider 预算)` 只能在**适配器里**、上传已被缓冲**之后**执行。

因此超限的 413 必须在**两层各自产生**（或让 multer 取"所有 provider 的最大值"、由适配器执行本 provider 的界）。判据读"切换 provider 后读数改变"时，必须读**适配器的拒绝**，而不是 multer 的。另需接受：小于全局界但大于本 provider 预算的请求，会**先被完整缓冲**再被拒——这是"两层"这个事实的必然后果。

超限的 HTTP 状态码从 400 改为 **413**：今天的 400 会让客户端以为是格式问题。

**缺口三：健康检查只反映服务端环境变量，是单一真相源。** 它今天答的是"服务端配了吗"，而客户端只能自行补偿（用"已水合且 baseUrl 非空"当作可用）。修法：返回**当前用户的有效配置**加上 provider 列表与各自的能力。

三处共同的形状是：**能力声明是唯一来源，客户端不再自行推导**（容器选择、裁剪判断、上下文开关都收敛到这一处）。

**代价：** 缺口三是行为变更（它今天给出的答案在一个真实用例下是错的），因此需要一条专门覆盖该用例的判据，而不是只测"字段还在"。缺口二的 413 是一个对外可见的状态码变更。缺口二的两层结构意味着"配置面"与"执行面"分离，用户看到的界与真正生效的界可能不是同一个数。

**被否决的替代：** 把三处各自就地修掉（在路由里写一个 MIME 数组、把 25MB 改成 20MB、给健康检查加一个 provider 字段）。否决理由是它们会在下一次接入服务时全部重新失效 —— 三个常量、一个写死的数、一个只会说"服务端配没配"的探针，都不会随 provider 变化。

### 决策 5：输出信封扩为 `{ text, style, transformations }`

provider **优先**返回书面化 / 去口头语 / markdown 的文本，除非某服务经实验确认做不到（现有 whisper 系即属此类）。`text` 是已处理好的文本，composer 直接可用；另有两个声明字段：`style`（`verbatim` | `written`）与 `transformations`（`punctuate` / `de-disfluency` / `written-style` / `markdown` / `identifier-canonicalized` / `self-correction-applied`）。

`transformations` 不是装饰，它有三个机器用途：给 UI 一个"这条被改写了吗"的依据；给指标一个**选轴的依据**；给"还要不要继续跑客户端那层确定性标识符修复"一个判据（已声明 `identifier-canonicalized` 的文本不应被二次改写）。

**这带来一个必须直面的后果：现有判据会失明或失义。** 出货的标识符度量量的是**逐字存活**（大小写与点号敏感），而一份书面化文本本来就不逐字等于口语原话。因此指标必须分轴：

| 轴 | 适用 | 说明 |
| --- | --- | --- |
| 逐字标识符存活 | `style: verbatim` | 现有口径不变 |
| 语义等价 / 下游可理解 | `style: written` | 新口径 |
| 句读 / 片段 | 全体 | 先蒙掉标识符内部的点再计数 |
| CER | 全体（辅助） | **已知对标点损失失明**，不得单独作闸 |
| 账单 | 全体 | 按 `billing` 折算 |

新口径必须有一条**能红的负对照**：**含文件路径与代码片段的句子在风格化之后必须逐字保留**。书面化最容易顺手把 `voice.service.ts` 改写成 `voice service ts`，这条负对照就是量它。两个方向都要能红：若惰性实现（风格化根本没发生）也让判据全绿，那就没有测量任何东西。

**代价：** "更好"的判定变复杂了 —— 一份被改写的文本可能逐字退化而实际更好。这意味着逐字轴不能单独作闸，且新轴很可能**只能靠人读配对文本**（与标点位置合理性的先例一致），因此它属于实验读数而**不是** CI 判据（决策 8 据此把它排除在判据集之外，后续任务 8 的措辞必须相应调整）。

**被否决的替代：** 保持单字段信封、把书面化放到客户端后处理。否决理由是那需要第二套提示词与第二次模型调用，且会把"书面化"变成与识别器无关的固定行为 —— 而它恰恰是识别器能力的差异之一（有的服务能顺带给出标点，有的不能）。

### 决策 6：上下文偏置默认关闭，按服务分别测

会话历史、当前可见对话、项目文件树可以作为上下文一并发给识别服务，但：

- 由 `honors.context` 声明，**未声明的 provider 一律不发**；
- 载荷必须有界且可审（固定形状、字节上限、开关在 UI 可见）；
- **默认关闭**，且启用前必须让用户知道音频与上下文会一起送到第三方；
- 把某个 provider 打开，**必须附带该 provider 自己的配对实验**。

**一条与决策 1 相撞的硬约束**：上下文进的是**同一个请求**，而多模态服务的内联上限是**整个请求的预算**（"含提示词与所有文件"）。因此上下文越长，音频的可用预算越小——`maxInlineRequestBytes` 必须是**请求级**字段，且发送前要扣除提示词与上下文的占用。原稿把它建模为"音频字节上限"，会让一个长上下文请求在音频侧被误判为可发。

不预设结论：提示词偏置已实测在中文 + 出货裁剪下有害（句读与标识符双双退化），所以"给了上下文就更准"是**假设**，不是结论。同时要记录一条纪律：该实验记录已明确禁止用输出侧的差异（空格、词形）去解释输入侧的变化 —— 那是把待解释的现象换了个说法。

客户端那层确定性标识符修复（候选来自项目文件树）**独立于 provider 保留**：它不消耗模型调用、可离线判定，与"把同样的信息以提示形式给模型"不是替代关系。

**代价：** 上下文会连同音频进入第三方，是实质的隐私面扩大；启用后每次识别都多付上下文 token，且如上所述会**挤占音频预算**。另外它引入一个持续的验证义务 —— 每接入一个服务就要重跑一次该服务的配对实验。

**被否决的替代：** 全局开关（一个"使用上下文偏置"的偏好，对全部 provider 生效）。否决理由是已有证据表明不同服务、不同语言、甚至同一服务的不同裁剪设置下结论相反；一个全局开关必然在其中一侧是错的，而且错得不可见。

### 决策 7：保留直连拓扑；provider id 的真相源在用户级配置，且必须定义"认不出来"时的行为

直连模式（浏览器持密钥、直接调用识别服务）保留。带来三个明确后果：

- 适配器必须环境中立（决策 2 由此而来）；
- 两条路径（直连 / 代理）都必须能把 provider 解析到同一份适配器；
- **浏览器持有密钥是既定设计而非缺陷**：服务端代理路径只是"用户没配 baseUrl"时的回落。这一点必须在设置页对用户可见。

配置轴今天已经有三条（服务端环境变量兜底 / 用户级语音设置 / 语音总开关的 UI 偏好），加 provider 会变成第四条。**必须明确：provider id 只在用户级配置里，服务端环境变量只提供"默认 provider id"。**

**未注册 / 拼错的 provider id 的行为必须定义**（一版原稿完全沉默，而它是可达状态：id 存在用户级配置里，会随版本与拼写漂移）。沿用既有 registry 的失败模式——未注册 id 一律 fail-closed，返回明确的不可用错误，**不得静默回落到默认 provider**。三个面各自的行为都要写进判据：直连分支、代理分支、健康检查。**静默回落是最坏的选项**：用户会以为在用新服务，实际在用旧的。

**一条必须显式保留的安全不变式**：代理路径的 `VoiceRequestOverrides` **刻意不含 base URL**，即"客户端不得控制服务端的出站目的地"。把 provider id 放进用户级配置**并没有**重开这条规矩——因为端点始终由适配器按 id 固定，用户选的是**哪份适配器**，不是**往哪里发**。这一点要写明，否则下一个读代码的人会把 provider id 误当成一个可被客户端扩张的字段。

**代价：** 新增 provider 必须在两条路径上都验证，不能只测一条。代理路径的入站字段与直连路径不同（见背景第一节的两跳区分），适配器与路由必须各自吸收这个差异而不是把它留给客户端。

**被否决的替代：** 取消直连、全部走服务端代理，从而让适配器只需存在于 `server/`。否决理由有两条：一是它会**删掉一项既有能力**（用户自带密钥直连自己的识别端点），二是有意绕开代理的部署（自建端点、区域限制）会因此失效。

### 决策 8：区分"进 AC"与"只进实验记录"

本 ADR 的后续工作里，有两类东西**不能**判据化为 AC：

- **配对质量实验**（同一批语料跑多个条件，看标识符 / CER / 句读 / 账单）。它联网、按条件数计请求、单次约数秒 × 数十条，远超判据运行的时长上限；且其中至少一轴按既有先例只能靠人读。
- **每个新 provider 的常驻验证义务**（决策 6 的配对实验、决策 1 的 `pauseCues` 变更）。它随 provider 数量增长，无法用一组固定判据表达。

这两类的载体是实验记录（沿用既有协议：配对比较不跨运行、必须有能红的负对照、被测实现必须是出货模块、报 `n`、串行执行、结果落盘缓存）。

**可以**判据化的是那些快、离线、确定的读数：命令行 `--dry-run` 的脱敏请求、`--offline` 的回放一致性、MIME 白名单的双向、超限状态码、健康检查的那个"环境变量未配置但用户配置了"的用例、不变量套件、以及边界探针的机器部分。**联网的"真跑"与需要 `style: written` 服务的读数不在此列**（后续任务 3、8 据此调整）。

**代价：** 质量结论不进 CI，因此质量回归不会自动被发现 —— 它依赖"每接入一个服务就写一份实验记录"这个人工义务。接受这个代价的理由是：一个联网、超时、靠人读的判据被塞进判据门之后，它的失败模式是"超时或不可判定"，而不是"发现质量退化"。

**被否决的替代：** 把质量读数也做成判据。否决理由是阈值不可导出（语料是合成的、样本量小、效应方向明确而幅度不确定），一个拍出来的阈值会在下一次语料变化时变成假判据。

### 决策 9：既有"服务端保持纯透传"是阶段性约束，现提议修订

语音相关的两个目标都把"不改服务端语音接口契约：保持纯透传"写进了非目标。该条目**当时的语境**是裁剪与标识符修复都在客户端完成，服务端确实不必参与 —— 它是一条真实约束，不是随手一写。

引入适配器缝之后，服务端必须参与分派。修订方式不是删除该条目，而是**降级它的适用范围**：直连分支保持纯透传不变，"纯透传"从"服务端契约"降为"直连分支的性质"。

**本 ADR 只提议，不执行** —— 但见下：该修订已由人裁定执行。

**执行记录（2026-09-22）**：本决策的修订已**实际执行**（人 yale 裁定「现在就改」，经被授权的 goal 写入路径）：GOAL-005 提交 `a8bb5428`、GOAL-006 提交 `d00f791d`，各为单文件 +2 行的纯追加，两个目标 `status` 仍为 `achieved`、`title`/`origin` 逐字未变、`## 退出条件` 小节与全部 AC 行未动。因此"纯透传"在本仓库的权威文本里已从「服务端契约」降为「直连分支的性质」。

**代价：** 两个已 achieved 的目标的正文会被改动。缓解方式是只追加修订记录、不改判据、不改状态。另需注意：本条修订在后备方案 (b) 下**依然成立**——直连分支仍要分派适配器，只是适配器换了住处。

**被否决的替代：** 不动既有目标，把修订意图只写在本 ADR 里。否决理由是那样会在仓库里留下两处互相矛盾的权威文本，而后续读目标正文的人（包括自动化的充分性判定）看到的是未经修订的那一份。

## 边界与不做的事

- **本 ADR 不实现任何东西。** 不写代码、不改任何既有实现、不改任何既有目标或判据。实现与判据化在评审通过后另行立案。
- **不新增依赖。** 引入服务商 SDK 属于适配器落地任务，且必须发生在边界探针（决策 3）之后。
- **不做 TTS 侧 provider 化。** 语音合成有同形的单一化（同样写死路径），但本 ADR 只把识别走通。
- **不做实时 / 双向语音。** `oneShot` 第一版只允许 `true`。
- **不做识别结果的持久化与审计。** 是否保存转写原文仍是一个未决问题。
- **不给新阈值。** 文中引用的 20MB、25MB、10 秒下限、−89%、25.5% 等均为**既有代码、官方文档或既有实验记录里的既成数字**，本 ADR 不新立任何阈值。
- **不写本机绝对路径。** 仓库外工装的位置以"其位置登记在 `docs/experiments/README.md`"指代。
- **不点名任何未完成任务 id。**
- **不裁决既有架构文档。** `docs/architecture/` 下与语音有关的断言是否需一并修正，留作评审时的开放问题。

## 后续任务草案

十条。每条给出判据与**取假变体** —— 取假变体指"刻意做一个假实现，这条判据必须因此变红"。判据若在假实现下仍是绿的，它测的就不是它声称要测的东西。

### 后续任务 1：边界探针与契约骨架（先决）

- **判据：** 最小模块落在候选落点，从 `src/modules/**` 与 `server/modules/**` 各导入一次；`npm run typecheck` 退出 0；`npm run lint` 退出 0，**且 `npm run lint` 的路径列表实际包含该目录**（命令需打印该列表并断言包含，因为"没被判红"与"被覆盖"不是一回事）；若走别名路径，三个配置点各自的登记内容都要打印出来。
- **取假变体：** ① 只登记 `boundaries/include` 而不登记 `boundaries/elements` ⇒ 必须因 `boundaries/no-unknown` 变红；② 用相对导入绕过别名 ⇒ 必须因 `no-restricted-imports` 变红；③ 该目录不在 lint 路径里却声称"已被覆盖" ⇒ 断言路径列表的那一半必须红。
- **若探针红：** 转决策 3 的后备方案；此时**缺口一、缺口三的任务转为不成立**，只能以"服务端保持现状"结案。

### 后续任务 2：把现有实现抽成第一个适配器（行为零变化）

- **判据：** 纯重构。既有服务端语音测试与前端语音配置测试全部保持绿；且**四处**硬编码点经适配器后产生的线上字节逐字节等于改动前录制的基线，**基线必须同时覆盖两跳**——客户端→服务端的入站请求（字段 `audio`、`x-voice-*` 头）与两条路径各自的出站请求（字段 `file`、`Authorization`、URL）。
- **取假变体：** ① 把**入站**字段 `audio` 改成 `file`（今天代理路径的入站字段名）⇒ 若基线只覆盖出站，本变体**恒绿**，故基线必须含入站那一跳；② 把直连分支的响应解析改成与代理分支同一种容忍度（例如让非 JSON 原样返回）⇒ 响应解析基线必须红。

### 后续任务 3：命令行（`--dry-run` / `--offline`；"真跑"不判据化）

- **判据：** `--dry-run` **零网络**（用一个被禁止联网的 fetch 替身断言：发生调用即红）且打印的请求不含密钥与音频字节；`--offline` 回放录制响应，产出与录制一致的文本；CLI 以 `npx tsx` 启动（命令本身即断言）。
- **取假变体：** ① `--dry-run` 实际发出了请求（替身记录到一次调用）⇒ 必须红；② 脱敏只脱了密钥没脱音频 ⇒ 必须红；③ `--offline` 其实走了网络 ⇒ 必须红。
- **不判据化：** "真跑在真实音频上取回非空文本"是联网 + 带凭据的操作，按决策 8 归入实验记录，不进判据集。

### 后续任务 4：不变量套件（对 registry 参数化，离线）

- **判据：** 五组各自成一条独立可红的断言：请求构造 golden（含"声明为不支持的提示参数必须**不发**而不是发空值"）、错误映射（401/403/429/5xx/超时/空响应/非 JSON 各归到哪个语义码）、大小分流、脱敏（密钥与音频字节不出现在返回值、错误消息、日志里）、MIME（不在 `acceptsMime` 内的输入在**发出请求之前**被拒）。
- **取假变体：** 把某个适配器的错误映射换成"一律返回上游错误"⇒ 401/429/超时三组必须红；把提示参数实现成"发空字符串"⇒ 第一组必须红。

### 后续任务 5：第二个适配器（多模态服务，仅内联）

- **判据：** 超过 `maxInlineRequestBytes` 的输入返回 `OVERSIZE` 且**未发出任何请求**（替身断言调用次数为 0）；**提示词与上下文计入同一预算**——构造一个"音频本身在预算内、加上长上下文后超预算"的用例，必须被拒；`honors.prompt` 为 false 时请求体不含提示字段。
- **取假变体：** ① 把超限音频直接塞进请求体 ⇒ 必须红（"调用次数为 0"这一半）；② 只按音频字节判定预算、不计提示词与上下文 ⇒ 上面那个用例必须红；③ 把响应解析写成宽松形式（把整个响应 JSON 当文本返回）⇒ 解析基线必须红。

### 后续任务 6：缺口一与缺口二（MIME 白名单、大小上限分层）（**有条件**：仅当决策 3 路径 (a) 成立）

- **判据：** 白名单**双向** —— 白名单内的输入绿、白名单外的输入红且返回不支持 MIME 的语义码；**带参数的 MIME（`audio/webm;codecs=opus`）必须被判为受支持**（按基类型匹配），且裸基类型同样受支持；超限返回 **413** 而不是 400；两条路径（直连 / 代理）产出同一个语义码；"切换 provider 后读数改变"读的是**适配器的拒绝**而不是 multer 的。
- **取假变体：** ① 把白名单写成恒拒 ⇒ "内绿"那一半必须红；② 按精确串匹配 ⇒ 带参数的那条用例必须红（这是出货录音器自己的输出）；③ 把上限写死回一个常量 ⇒ "随 provider 变化"必须红；④ 只改代理路径 ⇒ "两条路径同码"必须红。

### 后续任务 7：缺口三（健康检查反映用户有效配置，且认不出的 id fail-closed）（**有条件**：仅当决策 3 路径 (a) 成立）

- **判据：** 构造"服务端环境变量未配置、但用户配置了"的实例，断言 `configured` 为**真**；断言 provider 列表与各自能力齐备；断言**未注册的 provider id 返回明确的不可用错误且不静默回落到默认 provider**（三个面各一条：直连、代理、健康检查）；断言既有 `configured` 字段仍能被其唯一消费者读到且为真值。
- **取假变体：** ① 保留今天"只看环境变量"的实现 ⇒ 必须红（今天这个用例会答错）；② 未注册 id 静默回落到默认 provider ⇒ 必须红；③ 把 `configured` 改名或改语义 ⇒ 消费者那一半必须红。
- **不判据化：** "字段位置未变"不是可机检属性，不作为判据。

### 后续任务 8：风格化的双向负对照（实验读数，**不判据化**）

- **性质：** 按决策 8，本条产出的是**实验记录**而非 AC —— 它要求一个 `style: written` 的服务，联网且需要凭据。
- **要求：** 一条含文件路径与代码片段的句子，经风格化后其中的标识符**逐字保留**；同时记录"风格化确实发生了"的证据（`transformations` 非空且与实际改写一致）。两个方向都要能红：惰性实现让"确实发生了"失败；把标识符一起改写让"逐字保留"失败。

### 后续任务 9：裁剪 × 识别器能力的接线

- **判据：** `pauseCues: destructive` 走裁剪；**默认行为不变** —— 既有的"裁剪开/关配对下上传体时长下降"端到端判据保持绿；`capabilities` 的读取成为裁剪决策的唯一来源。
- **取假变体：** 把默认改成"不裁"⇒ 既有时长下降判据必须红；把裁剪决策仍留在客户端各自判断（不读能力）⇒ "能力是唯一来源"必须红。

### 后续任务 10：配对质量实验记录（实验读数，**不判据化**）

- **性质：** 按决策 8，质量数值不进判据集。
- **要求：** 实验记录含同一批语料上的配对比较、报 `n`、并带能红的负对照，且**报告负对照是否按预测方向移动**。记录的形状可以由人工核对清单约束，但**不得**把"提到了某个词"当作判据——文本匹配无法区分"做了负对照"与"写了负对照"。
