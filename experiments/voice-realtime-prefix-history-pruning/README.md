## 判据：交付给 Claude Code 的文本，不是 token，也不是转写

**realtime 模型的交付物是它写进 `session_send` 的 `message`** —— 那才是 Claude Code 收到的东西。于是：

- **token 计数不是判据**，只是成本口径。节省 X% 而交付文本变了，就不是更便宜的中继，是另一个中继。
- **转写差异不算缺陷**（owner 裁定）。同一段录音里端点 ASR 听成 "Live Voice第四十次"，模型交付的是 "Live Voice 第四次测试" —— **交付文本比 ASR 更忠实**，拿 ASR 当基准会给"听得比转写器准"扣分。本目录早期一版探针就是这么错的（tier 4 的 FOREIGN 判据），已作废。

在这把尺子下只剩两种失效形态，且都不依赖转写正确：

- **ECHO**：用户这一轮没说什么新东西，模型却把旧句子交付出去。基准是**更早轮次自己的话**。
- **编造**：用户没说话，模型照样交付。

| ⑤ 的分支 | 裁决 |

## 顺序颠倒能否稳定复现（arm 11 `order`，2026-10-15）

**触发样本。** 一次 spanB twin 跑批把 `[1]。[0]，[2]` 合成一条交付——合并没问题，**顺序颠倒**才是问题。

**做法。** 生产形状（真 silero 门控、16 kHz/20 ms 实时、上游 `server_vad`），除交付文本外还记录**会话本身**：用端点自己的 `conversation.item.created`/`previous_item_id`/`deleted` 帧建镜像，并在每次 `response.created` 时快照用户条目顺序（`A<k>`=第 k 句的音频条目，`T<k>`=它的文字替身）。打分离线（`analyze-order.mjs`，局部对齐定位每句话在交付文本中的位置），**每条标记都人工读过**。

| 批次 | 跑批 | 交付内顺序颠倒 | 跨交付顺序颠倒 | 会话快照顺序颠倒 |
|---|---|---|---|---|
| spanB keep ×3 | 3 | 0 | 0 | 0/17 |
| spanB twin-append ×3 | 3 | 0 | 0 | 11/17 |
| spanB twin-inplace ×3 | 3 | 0 | 0 | 14/17 |
| spanA/C/D keep ×1 | 3 | 0 | 0 | 0/11 |
| spanA/C/D twin-append ×2 | 6 | 0 | 0 | 8/23 |

**结论：不能稳定复现。** 本轮 12 次 twin 跑批 0 次颠倒；连同此前所有生产形状 twin 跑批，约 **1/24**。keep（今天的生产）0 次。

**但前提条件是系统性的：**

- **端点忽略客户端的 `previous_item_id`**。in-place 臂请求把替身插在 A0 之后，回来的 `conversation.item.created` 却是 `previous_item_id = A1`（末尾）。所以 in-place 在 DashScope 上不存在，两个 twin 臂实际都是追加。
- 于是只要下一句已经开口，替身就落在下一句的音频之后：快照里反复出现 `A1 T0 A2`。twin 的响应有一半以上是在这种顺序颠倒的会话上生成的，keep 一次都没有。
- 模型绝大多数时候自己把顺序纠正回来（快照 `A1 T0 A2` → 交付 `[0][1][2]`），偶尔照着会话顺序转发——那就是触发样本。

**对 ⑤ 的含义。** 在这个端点上，"删音频+补文字"不能保持会话顺序；颠倒的交付是低频但真实的风险，且没有 in-place 可用来消除它。

**附带观察（未作主判据，n 小）：丢句。** 排除两臂都没回应的片段末尾句后，keep 6 跑丢 1 句，twin-append 12 跑丢 5 句（spanB#1 两句、spanB#2/spanA#1/spanD#1 各一句）。twin-append 是"先删再插"，中间有一段该句不在会话里的窗口；先插后删的 twin-inplace 3 跑 0 丢。这只是机制猜测，未单独验证。

**花费：** ¥0.075951 + ¥0.052467 = ¥0.128418。traces：`tier1-order-2026-10-15T02-18-51-385Z.json`、`tier1-order-2026-10-15T02-20-57-969Z.json`。

## 生产设置 vs 探针设置（重要）

**生产（PID 507915，`node dist-server/server/index.js`，:3001，`/proc/<pid>/environ` 实测）只设了 `VOICE_REALTIME_UPLINK_VAD=silero` 一项**，其余全是出厂默认：

| 层 | 生产值 | 来源 | 探针用了吗 |
|---|---|---|---|
| 上游 `turn_detection` | `server_vad, threshold 0.5, silence_duration_ms 400` | `DEFAULT_TURN_DETECTION`；wire 上实测 `>> session.update ... turn_detection=server_vad threshold=0.5 silence=400ms` | ❌ **全部臂改成 `null`** |
| 上游采样率 | `pcm16` 按 **16 kHz** 读 | 浏览器 capture `sampleRate:16000`；本次实测 16k 的 ASR 与 audio tokens 都对得上生产 | ❌ **我重采样成了 24 kHz** |
| **上行 VAD 门控**（silero，开） | 20ms/16k 帧分类；语音后保留 `a=(400+200)/20+1=31` 帧(620ms)，onset 回放 200ms pre-roll，hold-open 上限 2000ms，**其余全部丢弃** | `voice-realtime-uplink-vad-gate.ts`；生产实测 `browserFrames=24434 sent=3273 dropped=21159` → **86.6% 的帧根本没离开服务器** | ❌ **完全没跑**（探针绕过 ws-proxy，100% 音频直达上游）|
| STS 静音尾抑制 | **关**（env 未设，全部 journal 里 0 条 `silence_tail`） | `voice-realtime-silence-tail.ts` | ✅ 两边都关 |
| 浏览器本地语音检测 | 连续 20ms 帧 + 停摆看门狗 | capture 路径 | ❌ 无浏览器 |
| 帧长 | 20 ms | 浏览器 | ❌ 我用 100 ms |

## 生产形状复验（arm 10）—— 推翻上面两条语义结论

上面所有臂都跑在**关掉上游 VAD、采样率错、绕过上行门控、手动驱动轮次**的会话上。`arm 10` 把三样都补齐：**真 silero 门控**（`createUplinkVadClassifier`+`createUplinkVadGate`，`silenceDurationMs:400`）、**16 kHz / 20 ms 实时节奏**（漂移 0–385 ms）、**上游 `server_vad` 自决轮次**（探针一次 `response.create` 都不发）。音频取 `164c3087` 的 18.0–30.5 s——真实会话、真实静默。

| 读数 | 合成臂（旧） | 生产形状（5 次跑批） |
|---|---|---|
| 交付错位（落后一句） | **3/3 跑出现** | **0/4 跑出现** |
| ECHO（旧句当新话再交付） | 出现 | **0** |
| 编造（激进剪枝） | 出现三条假话 | **0**（含激进臂） |
| swap 是否真删到音频条目 | 删错（删了自己的替身） | **5/5 `deleted`，目标全是 `input_audio`** |
| 音频上下文 | 归零 | **封顶不复利**：keep 累积到 98，twin 停在 49 |

| | 每次响应 audio tokens |
|---|---|
| keep | 35 → 49 → 70 → 84 → 98 → 98 |
| twin | 35 → 35 → 35 → 56 → 49 → 49 → 49 → 49 |
| aggressive | 35 → 35 → 14 → **0** → 35 → 28 → 28 → 28 |

交叉验证（生产形状下独立复现了前面的量）：首响应 text=**810**（早先 2400 字+极简工具 = 808）；810 + 460（生产工具对）= 1270 ≈ 生产实测 base 1258。

### 所以 ⑤ 的裁决要改

- **音频替身：未被证伪。** 生产形状下机制成立（条目 5/5 删除、音频上下文封顶不复利），5 次跑批零 echo、零编造、零错位。
- **交付质量差异：不可判。** keep 臂自己就只交付 3–5/7，harness 方差大于臂间效应。能判的只有定性失效，而定性失效全是 0。
- **"激进剪枝会编造"这条发现作废**——它只在合成形状下出现过。

**为什么合成臂会错**：手动 `response.create` 时，被删条目留下的悬空 user 条目成了模型眼中唯一待办；`server_vad` 下端点由**新语音**触发响应，模型答的是新音频而不是那条悬空文本。这是解释，不是已证的机制。

**教训**：合成 harness 产出了两个看起来很硬的定性失效，在补齐生产设置后双双消失。**"关掉 VAD + 手动驱动轮次"不是生产的一个近似，是另一个系统。**

### 交付轴上的三次定性失效

**1. 激进剪枝 → 编造并丢句**（5 句语料）

| 臂 | 交付 |
|---|---|
| keep | 5/5 逐字，零编造 |
| prune（连用户条目一起删） | 3/5。第 3 句正确交付后**又交付了三条用户从未说过的话**（`"请确认收到。"`/`"再转一次。"`/`"最后一句。"`），第 4、5 句完全没送达 |

**2. 替身机制 → 交付错位一句**（3 句语料，真值精确）

| 臂 | [0] | [1] | [2] | 静音轮 |
|---|---|---|---|---|
| plain | ✅ | ✅ | ✅ | 无 ✓ |
| swap（追加） | ✅ | ⚠️ `"今晚继续测。"`（截断） | ❌ 交付 **[1] 那句** | ❌ 补交 **[2] 那句** |
| inplace（插回原位） | ✅ | ✅ | ❌ 交付 **[1] 那句** | ❌ 补交 **[2] 那句** |

机制：把用户条目删掉再补一条，会话末尾就留下一个**没有答复的 user 条目**，模型下一轮把它当待办交付。`previous_item_id` 插回原位**不解决**。

**3. 静音交付 → 两臂都有，不是配方特有**：keep 3/3 交付 `"嗯。"`，twin 1/3。属既有行为，另案。

### 交付轴上的噪声（用来划判据标准）

8 句 × 2 次重复：

| 臂 | 交付句 |
|---|---|
| keep1 | 0,1,2,3,4,5 |
| prune1 | 0,1,3,4,6,7 |
| keep2 | 0(1 截断),2,3,4,5 |
| prune2 | 0,1,2,3,4,5 |

两臂都是 6/8，但**集合每轮都在变**，连 keep 自己都有一次截断交付。**合成多轮驱动在 8 轮时自身只有 75% 交付率，方差大于剪枝效应。**

所以判据标准是：**只认定性失效**。编造与错位在 6 次 keep/plain 跑批里**一次都没出现过**，而丢句数两边都有 —— 前者可信，后者不可判。

### 工具 schema 对交付的影响

同 3 句、instructions 逐字节相同，只换工具集：

| 工具集 | 交付 |
|---|---|
| 生产一对（1268 tok） | 3/3 逐字，静音轮干净 |

### 对照：删并同文重建是 token 中性的

401 → 401（Δ0）。所以替身操作本身不花钱；twin 臂里那 44~46 tokens 文本差是"音频条目比纯文字替身贵"，未完全归因，不计入收益。

## 已经确定、因此没有重测的

- `conversation.item.delete` 存在且生效（P0/S5，2026-10-10）。`voice-realtime-dashscope-transport.ts` 的 `TOOL_OUTPUT_MAX_CHARS` 头注释仍写着"本协议没有这个命令"——**与实测矛盾，是过期注释**。
- 没有提示缓存可蹭（P0/S6：`cacheFieldPresent=false`、`discountObserved=false`）。

## 还没确定的

- **`server_vad` 生产模式未测**：全部臂跑在 `turn_detection: null`。**上线前必须复验。**
- **剪 instructions 的行为未测**：token 效应实测，交付效应空白。
- **`session_interrupt` 瘦身未做行为验证**：−258 tokens，但函数调用对 schema 敏感。
- **替身被再转发的概率**：只在退出前观察到；换 `server_vad` 后需重看。
- 44~46 tokens 的文本差未归因。

## 副产品：① 的死因

生产 `session_send` 返回里写着 `"Do not call session_send again for it. Reply with the single word OK."` —— 那 195 次被压掉的 `OK` 收尾轮**是这条 instruction 要求的**。这解释了 `server/index.ts:701` 那次回滚为什么长成"下一句回文本"：**收尾轮去掉了，"回一句 OK"的要求还在**。要重开 ① 得把这条 instruction 与收尾轮一起改再测。
