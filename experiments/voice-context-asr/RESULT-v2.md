# 结果 v2：识别之后的歧义检测与重打分（试点，n = 74 合成片段 + 20 真实录音）

按 `PREREG-v2.md` 判定。**偏差先说**：`PREREG-v2.md` 与脚本**没有在取数前提交**（工作区文件，取数时均未入库）；判据与预测是在看到小模型读数之前写入文件的，但「错误形态」一节是看过阶段 1 的 ASR 文本之后写的。模型阵容有换（见 PREREG-v2 §7）。数据与缓存在仓库外 `tc-verify/corpus/voice-context-asr/`；脚本在 `pilot/`。

## 一句话

- **「音近 × 词表」的确定性重打分（D1）能修复大部分误听和切分，但在同音陷阱句上必然把真的 `key` 改成 `quay`（6/7）——只能下划线，不能静默替换。**
- **小模型（0.5–2B 档）不够用**：1B/3B 的 JSON 解析率 19–50%；`ministral-3b` 解析率 99%、延迟 p50 0.75 s，但单独用会改写中文词（把「服务」改成 `restart`），要加「候选必须是词表词」的机械护栏。
- **最好的组合是「D1 只做形态修复 + 小模型在护栏下决定音近替换」：S 类修复 96%，M 类 69–72%，伤害 0，陷阱句替换 0/7，中性句改动 0/7，标记召回 96%。** 但小模型给出的概率**不可校准**：真 `quay` 与陷阱里的 `key`，`p(quay)` 分布重叠（0.1–0.3 vs 0.0–0.3），不能拿它排序「哪个 `key` 该被下划线」。

## 没有被证明的 / 局限

1. **n 很小**：M 类 36、陷阱句 7、中性句 7。陷阱 0/7 的 Wilson 95% 上界约 35%，**不能说「不会误伤」**，只能说这一批没有。
2. 合成语料，每个模板一个 TTS 音色；W 变体不代表 /kweɪ/ 的真实发音。
3. 词表只有 12 + 6 个词。大词表下 D1 的假阳性会升高（真实录音里已出现「Cloud Code → claudecodeui」，把一个本来对的词改成了错的）。
4. 小模型一次采样、温度 0；解析失败的样本在 hint / plain 之间不对齐，ministral 的 hint 优于 plain 部分来自解析率差异，不能当提示词收益。
5. **小模型概率不可校准**，所以组合里「下划线」与「是否替换」是两个独立开关，下划线的强弱不能用模型概率。
6. 音近度用 CMUdict + double-metaphone 骨架，没有真正的 g2p；`cantus` 等词的读音是手写的。
7. `PREREG-v2.md` 未在取数前提交（见开头）。

## 对提案的含义

- **词表驱动的重打分是对的方向，且便宜**：确定性、零延迟、V5 对照干净。`voice-correction-feedback-loop.md` §5.1 的 L2 应加「音近键」与「形态修复」两条。
- **静默替换只能限于形态类（S 类）**；音近类（M 类）进 UI 下划线 + 候选，由用户一键确认——这条与提案 §5.3 的纠正入口一致，并且是纠正闭环的数据来源（用户点的每一次都是一条 `heard → meant`）。
- 小模型有用但要有机械护栏（候选必须在词表内，与 S1-D 同一条原则）；0.5–2B 档里只有 `ministral-3b` 勉强可用，`llama-3.2` 的 1B / 3B 不行。
- 同音陷阱（`API key`、`enter key`）不能靠音近解决；它需要**用户词典里的反例**（用户把 `quay` 改回 `key` 的次数）或词组黑名单，这正是闭环要学的东西。
