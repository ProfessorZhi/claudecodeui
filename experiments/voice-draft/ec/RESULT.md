# E-C 结果：自我追问 → 核心诉求

按 `PREREG.md`（提交 `40695ced`，取数之前）判定。链的原文、证据包、音频与模型输出在仓库外 `tc-verify/corpus/voice-draft-ec/`；本文件只含聚合数字与不含对话原文的描述。标准答案：`gold-v1.json`（作者版，先于独立标注提交）、`gold-v2.json`（含三位独立标注员）、`gold-v3-inferable.json`（事后敏感性分析）。

## 数据与流程

6 条真实追问链（EC1 核对依据、EC2 逐步收敛、EC3 原则追问、EC4 条件推进、EC5 前提被推翻前、EC6 决策），核心诉求由**链后按时间序跨会话的后续动作**推出。口述脚本是把链内用户自己的问题改写成自问自答（不含助手的中间回答，不含链后动作），每条 5–8 个单元，两个音色 TTS，omni 无上下文听 3 次，`qwen3.8-flash` 一次调用输出 `{core_ask, premises, dropped, prompt}`。臂：C0 无上下文、C1 本链的链前助手输出（EC1 为空）、CW 另一条链的链前助手输出（负控制）、G0 脚本原文输入（不经 TTS / omni）。

**标准答案的独立性**：三位只看证据包、不看作者版的标注员，与作者版在 EC2–EC6 上的核心诉求一致；EC1 视野不同（作者版取紧接着的下一步「质疑依据、要看样本」，独立版取更远的走向「优先做 VAD、让上下文偏置生效」），都被后续动作支持，评分取作者版。

## 机械指标

所有臂可解析率 100%（126 次调用）；`prompt` 与口述长度之比：C0 0.94、C1 1.25、CW 1.02、G0 0.93（即没有压缩，只是整理）；延迟 p50 / p90：C0 7.5 / 10.7 s，C1 7.3 / 11.3 s，CW 8.1 / 13.1 s。

## 事后敏感性分析（不属于预注册，已明确标注）

初判后发现标准答案里有一部分来自链后动作、口述里并没有说出来（EC1 的「列出样本供他检查」，EC3 的「建 quay task」「客户端不存权限模式」的决定）。连 G0（没有识别误差）也只有 67%，说明标准答案比口述所含的信息多。于是把每条链的核心诉求限定为**口述自身能推出的部分**（`gold-v3-inferable.json`），三位评审员重新只判 `core` 一项：

| 臂 | 抓住 | 抓住 + 部分 | 未抓住 |
|---|---|---|---|
| C0 | **50.0%** | 100% | 0% |
| C1 | 33.3% | 91.7% | 8.3% |
| CW | 58.3% | 100% | 0% |
| G0 | 50.0% | 100% | 0% |

ASR 路径合并：抓住 47.2%（初判 30.6%）。两次判定同一份的 `core` 相同的有 30 / 42（71%），说明评审本身有明显的噪声。

按链（事后判定，每链每臂 2 份）：EC4、EC6 在所有臂都抓住；EC5 大多抓住；**EC1、EC2、EC3 几乎全是「部分」**，G0 也一样。

## 看到的失败形态

1. **把说话人的立场当成前提，而不是要质疑的对象（EC1）**：说话人的结论是「这些结论是样本质量不好造成的」，系统把它放进背景，主请求变成「还有别的原因吗」「谁管辖这件事」这类探路问题。
2. **把理解类的提问改写成修复任务（EC3）**：说话人在问「为什么说 Base URL 字段是死的」（他的设置明明可用），系统改成「请排查并修复这个字段」，立场相反；或只聚焦最后一个问题（权限模式），丢掉前面更大的主线（Settings 各项的存储位置与区分原则）。
3. **指错对象（EC2）**：要删的是手机上的 hint，系统写成键盘设备（视口 ≥ 1024px）的 hint，或把「合进 placeholder」写成「移到输入框上方」。
4. **识别错误进入提示并改变含义（EC5 等）**：`claude --bg` 变成 `Cloud IDE` / `Claude BG`；`CloudCLI` 与 `Claude CLI` 互换使进程形态说反；`Tap ➤ to send` 变成 `Tab + arrow`。
5. **编造多为「好心的补全」**：加上「请检查并修复」、「可能与 HMR 连接断开有关」、给出具体 commit 号等；G0 里同类编造只有 0.5 条 / 份，说明大部分编造是识别错误之后模型试图理解它造成的。
6. **上下文没有帮上忙**：本链的链前助手输出（C1）在初判里 core 抓住率低于无上下文（25% vs 33%），事后分析里 33% vs 50%；错误上下文（CW）反而不差（58%）。EC1 没有上下文，C0 与 C1 的输入完全相同，两组的判定也不同（初判 ½½ 与 ✗✗），可见同一输入下的采样噪声就足以产生这种差距，不应解读 C1 与 C0 的差异。但 C1 与 CW 的探路泄漏明显更高（25% 与 33%，C0 为 8.3%）。

## 解读

- 在这个设计下，「从自我追问里一次性找出核心诉求」**还没有做到**：事后（最宽松）口径下，没有识别误差的 G0 也只抓住 50%。系统能稳定处理的是**末尾有明确请求或决策**的链（EC4、EC6、多数 EC5），不能稳定处理**核心是一个立场、一个质疑、或一个理解问题**的链（EC1、EC3、部分 EC2）。
- 这是**提示词设计问题的概率更高**，而不是模型的上限：当前提示把核心诉求定义成「他想要 Claude Code 做或回答的事」，立场与质疑没有位置；多问题链没有「找出主线」的步骤。但本轮没有改提示词重跑，也就没有证据。
- 本轮没有看到「本链上下文」的收益；与 E-A、E-A2 一致：上下文主要用来校正识别出来的词与引用，而不是帮助找出核心诉求。

## 局限

- 只有 6 条链、每臂 12 份、同一用户同一项目；评审员是 Claude 系列，同一份 `core` 两次判定只有 71% 相同。
- 口述是我改写的自问自答，比真实自言自语整齐；链内的助手回答被拿掉，所以核心诉求只能取链内最终询问这一层。
- 标准答案（含事后版本）不是用户本人的标注；用户本人才知道自己真正关心什么。
- 只测了「所有单元都说完之后一次整理」，没有测增量。
