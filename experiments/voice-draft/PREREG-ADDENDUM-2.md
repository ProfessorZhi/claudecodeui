# 预注册补充 2：整份草稿重写，输出用 JSON 固定形状

写于运行之前（2026-10-03）。起因：用户指出草稿应当用 markdown 列表维护，并用 JSON 固定输出形状；`op` 可以作为说明性字段用于调试，但**不作为主要评价依据**。补充 1 的臂 r 输出的是纯文本，本补充新增 JSON 版本，二者并存，作为「输出格式」的对照。

## 输出形状（`response_format: {"type":"json_object"}`）

```json
{
  "draft": "- 条目一\n- 条目二",
  "parked": ["被搁置的想法"],
  "ops": [{"op": "add|modify|remove|keep|park|revert|noop", "note": "一句话说明（可空）"}]
}
```

- `draft`：更新后的**整份**草稿，markdown 无序列表，只含当前有效的要求。**评分只看这个字段。**
- `parked`：说话人说「先记着 / 这一版不做 / 以后再说」的想法，不属于本次任务；不进入最终 prompt，不参与泄漏判定。下一次更新时作为输入原样回传。
- `ops`：对本次更新做了什么的说明，供调试与可视化；不参与任何通过/不通过判定，只报告其分布与可解析率作为诊断。
- 解析失败或 `draft` 为空时，保留上一版草稿并记录失败（计入完整性）。

## 臂

| 臂 | 做法 |
|---|---|
| rj | 每段一次，输入 = 当前草稿 + 上一版草稿 + 当前暂存 + 最近 3 段原话 + 新段 + 项目文件清单；输出 JSON（上面的形状） |
| rj0 | 同 rj，但不给项目文件清单 |
| gj | 同 rj，输入是脚本原文（不经 TTS 与 omni） |

基线臂沿用补充 1 的 a2（一次整理）；补充 1 的 r / r0 / gr 是纯文本输出的对照。规则文字与补充 1 相同，除了暂存的措辞：改为「写进 `parked`，不要写进 `draft`」。模型与参数同前；识别结果沿用 `asr.jsonl`。

- 判定规则沿用 `PREREG.md` 的 S2 判定 1–8；被测臂 rj，基线 a2，上下文对照 rj0，原文对照 gj；规则 4 改为「JSON 可解析且 `draft` 非空的更新占比 ≥ 95%」。
- 人读审计：从 r、rj、rj0、a2 的 ASR 路径最终稿中各抽 10 份，共 40 份，每脚本 8 份，种子 `20261005`，盲评、乱序，规程同 `audit.md`，评审的键由 `required_*` 约束。
- 额外报告（诊断，不判定）：`ops` 的 `op` 分布；`ops` 与实际草稿差异的一致性（例如声称 `remove` 但草稿里内容仍在）的抽查比例。

## 已知风险（取数前登记）

- S1 里，两条很长的上下文曾让文本模型不输出 JSON；这里的输入也含约 2k token 的文件清单，要看可解析率。
- 把草稿塞进 JSON 字符串里要转义换行，模型可能写出带字面 `\n` 的单行文本；评分前会把字面 `\n` 还原为换行，并在结果里说明。
