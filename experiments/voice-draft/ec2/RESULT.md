## 解读

1. **类型结构确实解决了 E-C 最显眼的失败。** E-C 里「几乎全是部分」的 EC1 与 EC3，在这里假设保真 100% / 86%，问题保真 95% / 93%。例如 EC1 的「我认为这些结论是样本质量不好造成的」被渲染成「我的判断（假设）：我认为……请检验」，语气强度没有被削弱；EC3 的「为什么说 Base URL 字段是死的」没有再被改写成「请修复」。
2. **还没达标的有三类：**
   - **疑问句形态的假设（EC5、EC6，及 EC2 的「我倾向」）被写成事实或决定。** EC5 的「难道每次输入都换进程？」可以，「也就是说……进程形态完全不一样的？」「所以 claude --bg……的确会自动被停掉？」这种**求证式问句**却被渲染成「已知：……的确会自动被停掉」。假设忠实在 EC5 只有 38%，EC6 只有 14%。
   - **自问自答的问题仍被重新提出（37.5%）。** `self_answered` 字段在 EC1 的 27 次输出里一次也没有使用（0/27）；EC6 里「密钥要不要留在 config_json？要，……」这种句内自问自答也被拆成请求。
   - **类型边界的主观性：** 「探路」只有 41% 命中，大多被标成「问题」；这也是标准答案本身的边界，宽松口径合并后 76%。
3. **最近 2–3 轮对话以原文喂给小模型是有害的，且比 E-C 的单条上下文更糟。** 决定/约束保留从 94.4%（B）掉到 33.3%（C）；编造 0.58 → 1.08。典型：EC6 的 C 臂里，口述的六条决定全部不见了，提示变成对上下文里 Claude Code 的建议的复述（「已决定：先实现 AC-019……」），那是上下文里助手的话，不是说话人说的。W 臂里同类（口述被上下文取代）也出现。这是**上下文污染**，而且没有被现有的「只用来核对术语」这条规则阻止。
4. **仅逐字稿（B）略好于带整理稿（A），但差距不大：** 假设忠实 62.5% 对 56.3%，变成事实或命令 31.3% 对 43.8%，类型一致 65.0% 对 63.7%。阶段②的整理稿有害，但不是主因（样本小）。E-C 里我把大部分失败归因于阶段②，这个结论要打折。
5. **系统建议的隔离做到了：** 建议漏进提示 0%，每份 2.2 条。这条与用户的要求一致。
6. **渲染是逐段 1:1 的，没有压缩。** 例如 EC1 的输出有 9 条「已知/请检查/我的判断」，基本是每个口述段一条；探路问题没有被合并进相关检查。用户想要的「检查……；如果……那么是否应考虑……」这种压缩形态，目前只出现在 `suggestions` 里。

## 局限

- 6 条链、每臂 12 份盲评、同一用户同一项目；评审员是 Claude 系列，被测是 Qwen 系列。
- 类型标注是作者的，边界有主观性。
- 口述是我改写的自问自答，没有真人录音。
- 没有做「放进 Claude Code 单轮回答」的端到端验证。
- 同一输入的采样噪声没有量化（每臂只评了 rep 0）。
