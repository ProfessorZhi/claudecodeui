## 人读（被接受的每一条替换，D-full）

机械的「替换精度」是 36%，但那个口径只数「回复里的拉丁 token」，会把对的替换判错（例如整句 UI 文案的还原）。按预注册逐条人读，以「`to` 是否逐字出现在用户当时打的原文里」为准：

- 被接受的替换共 50 次（42 条唯一）：**44 次（88%）是把听坏的词还原成用户实际打的写法**，6 次错误（12%）。
- 还原得对的典型：英文 UI 文案整句还原；`AC101 → AC-101`；`false forms → false-forms`；`needs hook main → needs-human`；`ZROC → zrok`；`家具 → 夹具`；`#5173 → 5173`。一个共同点：多数是**带连字符、点、大小写的标识符与多词名**，omni 的整理稿恰恰在这类写法上出错。
- 6 次错误：
  - 用户自己说的通配路径（`server/modules/*/index.ts`）被替换成上一轮输出里一条具体路径（2 次）；
  - 用户新造的名字被替换成上一轮里相近的名字（`gap-session-fork-lineage-list` → `fork-lineage-ux`）；
  - 把用户说的 `claude cli` 换成上一轮里的 `CloudCLI`；
  - 把 `/work/quay` 的听坏写法换成上一轮里的 `worker`；
  - 中文词被换掉（`语义 → 语料`；用户打的就是「语义」，omni 听对了）。
  这些错误**都不被机械口径捕捉**：中文词不在拉丁术语集里。
- 净效果：50 次接受里 44 次改对、6 次改错，约 7:1；落到输出上，约 3.3% 的输出被引入了新的错误，与机械的 3.9% 接近。
- D-top3（只给最相近的 3 段）没有更好：fidelity_in 相同，回退和错换更多。缩小上下文并不能消除污染。
- 错误上下文（W）下 4 次替换全部错误，说明护栏能挡住大部分但不是全部。

## 解读

1. **有用，且能被机械校验保住大部分安全：** 术语保真从 62.8% 升到 72.4%，延迟 p90 2.3 s，一次校正调用约 ¥0.001。
2. **但没有达到预注册的安全线：** 3.3–3.9% 的输出被引入新错误（阈值 2%），伤害集中在三类：具体化、相近名字替换、中文词被改。这三类可以用护栏拦住：
   - `from` 与 `to` 都必须含拉丁字母（拦住中文词被换）；
   - `to` 不得比 `from` 长出一个路径层级或通配（拦住具体化）；
   - 同一个 `to` 在整份上下文里若有多个相近候选，就放弃。
   这些护栏是看过这批错误之后想到的，**必须换一批新案例验证，不能用这一批重判**。
3. **「还原用户已有的写法」比「纠正听错」更常见：** 多数收益来自把 omni 改写过的标识符还原成上一轮输出里的原样，而不是靠发音修复。因此用上一轮输出做校正，和 S1 的文件清单不同，不是在找近音词，而是在恢复原文的版式。

## 局限

- 60 个案例，同一用户同一项目；术语只覆盖拉丁字母与数字；中文词的识别错误不在度量里（上面的 `语义 → 语料` 是人读才发现的）。
- 回复是打字原文的 TTS，不是口述。
- 首次抽取的一处清洗缺陷见预注册末尾。
