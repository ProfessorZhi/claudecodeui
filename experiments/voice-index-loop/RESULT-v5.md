# 结果 v5：本地 SenseVoice —— 速度、置信度、CTC 候选打分，与 Omni 并排

按 `PREREG-v5.md`（提交 `1bf5cf1c`，任何 SenseVoice / Omni 读数产生之前）判定。语料、金标、词源、回放引擎、判定器沿用 v3 / v4。原文、音频、识别文本、置信度、逐帧分布**只在仓库外**（`tc-verify/corpus/voice-index-loop/`）。

## 一句话

1. **「更快」成立，「更好」不成立。** SenseVoice 的解码时间 p50 **0.11 秒**（实时因子 0.019），Omni 在同一批语音上客户端延迟 p50 **6.5 秒**（约 60 倍）。但识别后**有害错误的残留**：SenseVoice + 文本层 **9.0–9.6%**，Omni transcript **6.7%**，Qwen3-ASR **7.9%**（占标识符 token 的比例）——SenseVoice **不低于** Omni。按预注册的 J4，只能说「更快」。
2. **这三个识别器差别不大，共同点比差别大。** 在这批语音上标识符逐字写对的只有 21%（SenseVoice）/ 25%（Qwen3-ASR）/ 32%（Omni transcript），有害错误占标识符 7–10%。换识别器只动几个百分点。
3. **SenseVoice 的价值不在准确率，而在两样 Omni 没有的东西：**
   - **置信度能把有害错误排在前面**：区域级 AUROC **0.92**（全部错误 0.86）；θ = 0.6 时 68%（只标含拉丁字母 / 数字的段）至 75% 的有害错误落在低置信标记里；
   - **CTC 候选打分把候选召回抬高了**：有害错误前 15 位召回 **38%**，同一批文本上音近匹配是 21%，**两者取并 44%**。但它**不能自动替换**（见 S3）。
4. **Omni 的书面化改写把有害错误变多了**：Omni `instruction` 的有害错误 10.0%（66 个），比同一次调用的 `transcript` 的 7.3%（48 个）多。这支持「改写拆出来、放在用户确认转写之后」。

## S0 前端保真（J1：不通过）

自写 CTC 前端的贪心文本与 sherpa-onnx 的文本（去空白、标点、大小写后）逐字相同的比例：

| 集合 | 逐字相同 |
|---|---|
| v3 短消息 | 351 / 466（75%） |
| E6 长消息切段 | 214 / 461（46%） |
| 合成句 | 64 / 74（86%） |
| 真实录音 | 14 / 20（70%） |
| 全部 | 643 / 1021（**63.0%**） |

**低于预注册的 95%，所以 S2 / S3 的读数全部标为「前端不一致，仅供方向」。** 差别是零星的字（`GS` / `JS`、「星 / 信」），不是系统性偏移，但这表明自写前端与 sherpa 的特征仍有数值差别（我试过丢弃前缀帧、填充方式、`snip_edges`、频率范围、预加重、样本缩放，最好的组合是 80% 一致，取该组合）。S1 的文本取 sherpa 的转写（引擎事实），所以 S1 与 S4 不受影响。

## 速度（S1）

sherpa-onnx、SenseVoice-Small int8、4 线程、纯 CPU，共享主机上测（安静时段重测，主机负载 12–29 / 128 核）：

| | 读数 |
|---|---|
| 100 条（音频 p50 6.9 s、p90 20.3 s） | 实时因子 **p50 0.019、p90 0.022、max 0.028**；解码 p50 **0.13 s**、p90 0.33 s |
| 466 条（v3，早先一次） | 实时因子 p50 0.016、p90 0.020；解码 p50 0.11 s、p90 0.25 s |
| **Omni**（同一批 466 条，6 个并发） | **p50 6.5 s、p90 15.4 s、最长 48.4 s**；耗时 / 音频时长 p50 0.86、p90 1.83；每次调用中位 723 个 token |

Omni 有 6 / 466 次没有得到可解析的 JSON（1.3%）。Omni 的延迟含网络与并发排队，SenseVoice 是本机 CPU，这两个数字**不是同一种测量**，只能说量级。

## S1 / S4 并排（同一批 466 段，同一判定器，同一套 L2a + D1 静默系统）

| 来源 | 靶 token | 逐字写对 | 错误 | **有害（判定器）** | 系统处理后剩余有害 |
|---|---|---|---|---|---|
| Qwen3-ASR 1.7B（OpenRouter） | 668 | 167（25%） | 501 | 57（8.5%） | 53（**7.9%**） |
| **SenseVoice（sherpa 文本）** | 668 | 140（21%） | 528 | 65（9.7%） | 64（**9.6%**） |
| SenseVoice（自写 CTC 文本） | 668 | 139（21%） | 529 | 63（9.4%） | 60（9.0%） |
| **Omni transcript** | 661 | 210（32%） | 451 | 48（7.3%） | 44（**6.7%**） |
| Omni instruction（书面化） | 661 | 226（34%） | 435 | 66（10.0%） | 64（9.7%） |

- 「有害」= 判定器（`qwen/qwen3.8-27b`，v4 校准过二分一致率 85%）判 `wrong`；「剩余」= 经 L2a（形态修复 + 口语模板）与 D1 静默修复之后仍然错的有害 token。Omni 的 661 来自 460 条消息（6 条没有可解析输出）。
- 各来源的错误里，规则可容忍（形态 / 口语）的占比：SenseVoice 38%（202 / 528）、Omni transcript 69%（310 / 451）；判定器认为其中 98–99% 无害；**其余错误里判有害的比例**：SenseVoice 20%、Omni transcript 30%、Omni instruction 44%。
- **Omni instruction 逐字写对的 token 反而更多（34%）**，因为改写会把标识符包进反引号并整理成完整名字；但**有害错误也更多**（改写会把一个标识符改成另一个对象）。

## S2 置信度（J2：AUROC 通过；预算那一半不通过）

自写前端的 token 置信度（`max softmax`）；错误区域 = 靶 token 与识别文本的对齐区域。**前端不一致门没过，仅供方向。**

| 读数 | 结果 |
|---|---|
| 区域级 AUROC（低置信 ⇒ 错） | 全部错误 **0.857**；**有害错误 0.919**；规则可容忍错误 0.774 |
| θ = 0.5 | 2.37 标记 / 100 字符；召回：错误 45%、**有害 63%**；识别对的靶 token 被标 3% |
| θ = 0.6 | 3.90 标记 / 100 字符；错误 59%、**有害 75%**；被标 9% |
| θ = 0.7 | 5.27 标记 / 100 字符；错误 68%、有害 83%；被标 13% |
| θ = 0.8 | 6.70 标记 / 100 字符；错误 79%、有害 92%；被标 22% |
| 探索（非预注册）：只标含拉丁字母或数字的段，θ = 0.5 / 0.6 | 1.76 / 2.39 标记 / 100 字符；有害召回 59% / 68% |
| 与 D1 标记合用（θ = 0.6） | D1 单用：292 个标记，30% 不在错误上，有害找到 10%；**取交集**：146 个标记，24% 不在错误上，有害找到 5% |

- **预注册要求的「每 100 字符 1 个标记」预算做不到**：最保守的 θ 也是 2.4 个，所以「1 标记 / 100 字符下有害召回 ≥ 0.6」不通过。AUROC ≥ 0.8 通过。
- **P3 不成立**：取交集只把无关标记占比从 30% 降到 24%，同时把找到的有害错误砍了一半。
- 真实录音（20 条，295 秒，描述性）：你的 `quay` 被写成 `key`，置信度 0.48 / 0.41，**低于 0.6，会被标出**；`clo`（应为 Claude）0.36、`AP` `RC` 0.46 / 0.28 也被标出。这与前一个会话的观察一致。

## S3 CTC 候选打分（J3：差 2pp 不通过；应用那一半不通过）

窗口 = 连续低置信（< 0.85）token 的最大段，前后各扩 1 个 token；候选 = 该消息时刻的全部 PCU 实体；打分 = CTC 前向对数似然 − 假设的对数似然。**前端不一致门没过，仅供方向。**

| 对象 | 落在某个窗口里 | CTC top-1 / 3 / 15 | 音近 D1（0.6，K=15）top-15 | CTC 与 D1 取并（top-15） |
|---|---|---|---|---|
| 有害错误（63） | 98% | 17% / 27% / **38%** | 21% | **44%** |
| 全部错误（529） | 87% | 30% / 45% / 56% | 43% | 66% |
| 规则可容忍错误（200） | 77% | 32% / 47% / 57% | 68% | 77% |

- 加先验（项目 / 近期 / 用户历史）几乎不改变排序（有害 top-15 仍 38%）。
- **CTC 对有害错误的候选召回比音近高，两者互补**；但 top-1 只有 17%，**只能给候选，不能直接替换**。
- **预注册的应用阈值（LLR ≥ 0、2、4）一个替换都不触发**：假设本来就是贪心路径，候选的似然比永远是负数。这是我设计阈值时的错误。**探索（非预注册）**：放宽到 −2 … −14，修好的有害错误 0–1 个（共 63），而 ≥ −8 就开始把识别对的靶 token 改坏（5–7%）。**结论：CTC 分数不适合当自动替换的判据。**

## 判定

| 规则 | 读数 | 结论 |
|---|---|---|
| J1 S0 一致率 ≥ 95% | 63% | **不通过**；S2 / S3 降级为方向性 |
| J2 AUROC ≥ 0.8，且 1 标记 / 100 字符下有害召回 ≥ 0.6 | AUROC 0.92（有害）；预算达不到（最低 2.4 / 100 字符） | AUROC **通过**；预算**不通过** |
| J3 CTC 有害 top-15 ≥ 40%，且应用后修好 ≥ 15% 而改坏 ≤ 2% | 38%；应用阈值不触发（探索：修好 ≈ 0） | **不通过** |
| J4 SenseVoice + 文本层的有害残留 ≤ Omni（两个字段），且延迟 ≥ 5 倍快 | 残留 9.0–9.6% 对 Omni transcript 6.7%、instruction 9.7%；延迟约 60 倍 | **「更好」不成立**（只有「更快」成立） |

预测核对：P1 ✗（63%）；P2 ✓（实时因子 0.019；标识符 −4pp；有害 +1pp）；P3 部分（AUROC ✓；取交集 ✗）；P4 ✗（38% 对 40%，但高于音近的 21%）；P5 部分（Omni transcript 比 Qwen3-ASR 高 7pp ✓，耗时 / 时长 p50 0.86 ✓；**instruction 并不低于 transcript**，只是有害更多）；P6 ✗（残留不低）。

## 偏差与局限

1. **S0 不通过**（上面）。S2 / S3 读数用的是「自写前端的文本与置信度」，与 sherpa 约 63% 逐字一致；差别主要是零星的字，但**置信度与 CTC 的绝对数值不可全信**。
2. **预注册的 CTC 应用阈值设计有误**（LLR 恒为负），非预注册的负阈值探索已单独标出。
3. **E6 长消息切段（461 段）只跑了 S0 与速度**，没有做判定器判定与 S1 并排（时间所限），所以 S1 / S4 的并排只在 v3 的 466 段上。
4. `sv-summary.mjs` 第一次运行时因为静态导入顺序，所有来源都读了 Qwen3-ASR 的识别文本，打出了完全相同的 token 数；**发现后改成动态导入并重跑，本文用的是重跑的数字**。
5. **速度**第一次是在 onnxruntime 默认占满所有核的情况下测的（对自写前端的耗时有污染），之后限制为 4 线程并在更安静的时段对 sherpa 单独重测；两次的 sherpa 实时因子相近（0.016 / 0.019）。
6. Omni 一次采样、含网络与 6 路并发排队；6 / 466 次无可解析输出。耗时与 SenseVoice 的本机耗时不是同一种测量。
7. **判定器仍是模型**（v4 校准：二分一致率 85%），对 SenseVoice / Omni 的新错误没有重做盲评；判定器偏严，有害数偏多，对三个来源同样偏。
8. 仍是**真实文字 + 合成语音**（Edge TTS 读标识符的方式不是你的），所有来源的「逐字写对」都只有 21–34%，远低于真实口述；**这是相对比较，不是对你真实口述的绝对读数**。20 条真实录音只做描述。
9. CTC 的分词是「最少片段」近似，不等于模型训练时的 BPE 分词。

## 对方案的含义（供讨论，未回写提案）

- **本地 SenseVoice 作为默认识别器是合理的，理由是延迟、成本、隐私和置信度，而不是准确率。** 它的有害错误残留比 Omni transcript 高约 3pp，这一点要在方案里写明，不能说成「更准」。
- **置信度是新增的、Omni 没有的信号**：它把有害错误排在前面（AUROC 0.92）。但标记预算偏高（θ = 0.5 就 2.4 个 / 100 字符），要靠「只标含拉丁字母 / 数字的段」「与候选信号合用」和用户反馈来压噪声。
- **候选召回：CTC 与音近互补，取并 44%（对照单用音近 21–25%）**；但全部是「标出 + 给候选，由用户确认」，不能自动替换。
- **「改写拆出来」被数据支持**：Omni 的改写阶段使有害错误从 7.3% 升到 10.0%。
- **Omni 作为可选的云端「高质量」识别器保留是合理的**：它的 transcript 在标识符上是三者里最好的（逐字写对 32%、有害残留 6.7%），只是慢（p50 6.5 秒）且贵。可以让本地做默认、Omni 做「再听一遍」的按需选项。
- 下一步（未做）：把前端修到与 sherpa 逐字一致（拿到可信的置信度），对 E6 的 461 段做判定，并用你的真实录音做弱标注——这仍然是最缺的数据。
