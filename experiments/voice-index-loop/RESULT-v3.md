## 偏差与取数后发现的缺陷

1. **运行器分片**：`tts-asr.mjs` 加了 `SHARD`（6 个进程并行，语义不变）；13 条第一次失败的做了一次重试，最终 466 / 468。
2. **`wordPron` 原型污染缺陷**：词表里出现 `constructor` / `toString` 这类词时，`MANUAL[l]` 取到了 `Object.prototype` 的方法并崩溃。已改用 `Object.hasOwn`（影响 `voice-context-asr/pilot/phon.mjs` 与本目录 `match.mjs`）。**上一轮（`RESULT-v2.md`）的 74 条合成语料里没有这类词，读数不变。**
3. **别名键缺陷**：首轮 E3 用 `normKey` 做别名键，它会丢掉 CJK 字符，使 `AC 零零二`、`AC 零零五` 变成同一个键 `ac`，造成 64 次「冲突」并让这些别名永远 `pending`。已改用保留 CJK 的 `heardKey`，L1 也改为在整段文本上做子串匹配（不再只扫拉丁窗口）。**首轮（缺陷版）与修正版的 E3 并列保存**（`run-registered-first-pass.txt` / `run-corrected-keys.txt`）：缺陷版 A2 / A3 / A4 比值 0.93 / 0.90 / 0.95，修正版 0.91 / 0.87 / 0.88；E1 不受影响（无学习）。本文 E3 表用修正版。
4. **PREREG §3 的实体资格**：「纯小写词典词只有出自 U / C 才有资格」，实现为「必须是标识符形」（`isId`），C 里的 `Bash`、`Read` 这类工具名因此**不入候选**。这是比预注册更严的一条，避免 `read` → `Read` 的大小写静默改写。
5. **「harmful」口径**：系统改动没有与任何**标识符错误区域**重叠，就记为有害。靶 token 的形状规则没有覆盖的文字（普通词、数字）上的改动会被算进去，因此 70 / 308 偏高；伤害率另有「识别本来对的靶 token 被改坏」一条（1.8%），两者并列。
6. **分桶**（骨架首字母 + 骨架长度 ± 3）没有做「与不分桶对照」的核对，PREREG 要求「发现漏掉则登记」；本轮**没有做这个核对**，所以分桶是否漏候选**未验证**（`maxScored` 最大一个窗口 667 个候选，未超过 K = 200 的截断）。
7. 探索变体 X1–X4 是取数后加的，不进判定。

## 局限

1. **真实文字 + 合成语音。** 75% 的靶 token 被识别错，远高于你真实口述的错误率；TTS 读 `provider_models`、`GOAL-013` 的方式也不是你的方式。**这个实验量的是文本层的词源、匹配与学习机制，不是识别器。**
2. **一位用户、四个项目、数月历史**；理想用户总能发现并纠正所有错误。
3. **选择偏差**：只入选 ≤ 160 字、含标识符、不含路径的短消息；文件路径、长消息里的 task 名与文件名被排除，所以 **P 的贡献很可能被低估**（你最常念的文件 / task 名多半在长消息或路径里）。要回答「项目词源到底有没有用」需要把长消息按停顿切段后再测（下一轮）。
4. 项目快照按「消息时刻之前最近一次提交」还原，分支名无法还原，`cantus` 历史太短。
5. 只有一次识别采样；音近用 CMUdict + 骨架，没有真 g2p。

## 对方案的含义（供讨论，未回写提案）

- **U（你发过的词）是最大、也最便宜的词源**：把你每条发出的消息里的标识符自动进词典，就拿到了 41% 的找到率，不需要纠正动作。冷启动时从历史会话导入。
- **项目文件树不该是主力词源**（至少对这位用户的短口述）；会话词（C）对 U 已有的词几乎没有独家贡献（2%），它的价值在**新词**（刚被助手提到、你还没发过）——这一格本轮数据太少，不能下结论。
- **确定性模板规则（口语符号、编号、前缀）应进 L2a**，在这份数据上是最大的单项收益。
- **「越来越准」应拆成两个承诺**：*水平*（词源 + 规则决定，几周内就到位）与*斜率*（学习带来，较慢，且被「大量词只出现一次」限制）。向用户表述时不应承诺「用得越多越接近完美」，而是「你说过的词、助手提到的词、常见口语写法，会越来越稳」。
- 下一轮实验：(a) 长消息切段后重测 P 与 C 的真实贡献；(b) 加入口语模板作为预注册臂并加上真实录音；(c) 对「同一个词的多种误听写法」做音近聚类，看能否把斜率从 0.9 拉到 0.8 以下。
