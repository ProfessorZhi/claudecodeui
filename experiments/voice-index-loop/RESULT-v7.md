# 结果 v7：标点后处理——CT-Transformer 标点模型对 SenseVoice 自带标点

按 `PREREG-v7.md`（提交 `fb382738`，读数产生之前）判定。脚本 `sv/punct-eval.py`；原文与模型输出只在仓库外。

## 一句话

**不采纳。** 对同一批 466 条真实输入，SenseVoice 自带的标点（微平均 F1 0.671）比「去掉自带标点再用模型重加」（0.573）和「自带保留、只在没有标点处用模型补」（0.645）都好；模型还会**破坏带点号的标记**（IP 地址、文件名、版本号），40 处全部被拆开。

## 为什么模型反而更差（解读，未另行验证）

- SenseVoice 的标点来自**音频**（停顿与语调），标点模型只看**文本**；同样的文字，口述时停在哪里这个信息只有识别器有。臂 (c) 的召回比 (a) 高（0.648 对 0.631）但精度掉得更多（0.642 对 0.717）：模型补出的标点在用户的键入风格里多数是「过标点」。
- 金标是用户键入的标点（句末常不加句号、逗号少），模型按通用书面语习惯加，会被算成误报。读数是相对比较，不是绝对的书面质量。
- 句末：模型对几乎每条都加句末标点（444 条对金标 399 条），键入时用户常省略。

## 局限

1. 金标是键入标点，不是口述该有的标点。
2. E2 只评估对齐匹配处的空隙（覆盖 17,638 / 19,482）；识别错误处不评估。
3. 一位用户；中英混排、标识符多。
4. 点号被拆开的缺陷没有测试用占位符保护（先把带点号、连字符的标记替换成占位符、加完标点再还原）能否修复。这是可修的工程问题，但修好后臂 (b)、(c) 的 F1 仍低于 (a)，所以不改变判定。
5. 未评估数字与日期的书面化（逆文本规范化）、大模型改写。

## 对方案的含义

- **标点本身不接标点模型。** 保留 SenseVoice 自带标点。要改善，方向不是换模型，而是与用户的书写风格对齐（例如句末是否加句号），这是后处理偏好，不是识别问题。
- 模型文件 285 MB 已下载到 `sv-probe/`，不入库、不需要上线；实验后可删。
- 「更接近书面标准」里**更便宜的一块**没有测：中文与拉丁字母之间的空格（用户键入的 `检查 web server 进程` 与 SenseVoice 的 `检查web server进程`）、全角半角统一。它是确定性规则，可以直接用同一份金标量化「与用户键入格式一致的比例」。
