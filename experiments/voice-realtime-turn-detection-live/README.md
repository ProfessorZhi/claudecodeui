## 问题

人 yale 2026-10-15 的现场抱怨：**Live Voice 断句太快，半句话就被发出去一次 response。**
同一场连接的 journal + capture 把它量到了毫秒：44.45 s 连续说话被上游切成 **15 个 turn**，11 次 response、
其中 **5 次被 `turn_detected` 取消**（屏幕上就是那句 "The model's call was cut off because you started
speaking again"）。出货窗口 `silence_duration_ms = 400`，平台文档默认是 800。

此前只在**一段 15.7 s 合成片段**上比过（`experiments/voice-realtime-turn-detection/RESULT.json`，2026-10-10），
当时的决定写明了复验条件：**≥3 connections per arm、≥2 clips**。本轮提供**第二段语料**——一段真实的、当场被
抱怨的 44 秒。

## 语料与形状

- **音频**：`~/.cloudcli/voice-realtime-capture/7c01be7e-….wav`（连接 `7c01be7e`，会话 `3c308639`）。
  这是**原始麦克风流**（capture 挂在 forward 之前，含静音），16 kHz / 单声道 / 170.1 s。
- **窗口**：0 → 48 000 ms（上游自己的 timeline 把首段放在 0.733 s、末段 44.453 s，后接 ~3.5 s **真实**
  房间静音——不是数字填零，2026-10-14 测过零填比真实静音差得多）。
- **链路**：出货 instructions + 出货 tools + `respondToToolOutputs: true` + 出货 silero 上行门控。
  **臂间只有 `silence_duration_ms` 不同**，而且门控的头部保留窗 `a` **跟着它派生**（生产中就是这个耦合，
  见 `uplinkHeadKeepFrames`）——探针里同样耦合，否则测的是一条不存在的配置。
- **对照（免费）**：本场**生产 400 ms 的现场读数**就在盘上——capture 的 `timeline.jsonl` 记着上游自己的
  15 次 `speech_started/stopped/committed`，journal 记着 11 次 response 与 ¥0.0256。

## 这个人真实的句中停顿（无假设读数）

上游自己的 `speech_stopped` → 下一个 `speech_started`，14 个停顿：

```
170  182  191  214  263  298  314  410  416  490  614  658  674  838  (ms)
p50 = 410    p90 = 674    max = 838    mean = 409
```

**出货窗口 400 ms，停顿中位数 410 ms ⇒ 14/14 全部越窗。** 这不是「偶尔切碎」，是结构性必切：
在一口气说完三句话的节奏下，窗口比人的停顿还短。

## 结论

1. **切碎的代价不是钱。** 五档窗口在**同一段音频**上的花费是 ¥0.0078–0.0087，**只差 10%**——response 少了，
   但每段保留的真实尾音变长（`a` 从 31 帧涨到 71 帧），两者大致抵消。**不要用省钱来为调窗口辩护。**
2. **切碎的代价是：丢字 + 5~8 次被取消的 response。** 400 ms 下每 48 秒有 5–8 次
   `turn_detected` 取消（= 用户屏幕上那条 "cut off" 提示），800 ms 下降到 1 次，1000 ms 起为 0。
   听到的字数 208–215 → 224–225（**不要**读 800 的词：`fragmentsCovered` 是对**中继修好的**文本打分，
   而那份参考文本本身就是 400 臂的产物，构造上偏向 400）。
3. **1000 ms 落在这个人停顿的 max（838 ms）之上**：整段 44 秒坍缩成 2 个 turn，等于「不会在句中切开」。
4. **代价是交付延迟**：400 ms 下模型在停顿后 0.37–0.57 s 就交出一条消息（但是**半句**，而且随后常有重复/重发）；
   800 ms 下它在**整句说完后**约 1.2 s 交付。**换来的是一条完整的、不重复的消息。**

## 局限

- **回放不经过 ws-proxy**：合并窗（`VOICE_REALTIME_COALESCE_MS = 1000`）、忙时 hold、重复守卫都不在链路里。
  所以 `session_send` 次数与交付延迟是**探针 harness 的**读数，不是生产的；**commits 是上游自己的**读数，
  可以直接与现场比（s400 自检即为此）。
- **一条连接、一个人、一段 44 秒**。复验条件「≥2 clips」这一半仍未满足——需要第二段真实语料（不同话题/不同状态）。
- **`session_send` 用的是放宽的 descriptor**（`{ message }`），因为出货 descriptor 声明 `session` REQUIRED 而
  instructions 叫模型不要写，探针的 transport 会把那样的调用扣住，那样就测不到交付。工具名未变。
- **没有停在窗口更大的地方会怎样**：merge 掉跨想法的两句（「停一下」+ 1.2 秒后「算了继续」）在 1000+ 会变成
  一条消息。**本语料里没有 stop 词**，所以本实验**不能**回答「停止/打断是否仍可靠」——那需要另取一段含
  "停下它" 的语料（`86559798` 有）。
- 噪声片段本身的转写极不稳定（同一段音频跑出 `""` / `False.` / `Our response.`），与窗口无关。
