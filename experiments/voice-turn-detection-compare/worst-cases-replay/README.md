# Live Voice P0.15 — worst-case replay: which real samples do the two English turn detectors get wrong?

Task: `gap-voice-turn-detection-p0-15-worst-cases-replay` (parent P0.13: `gap-voice-turn-detection-p0-13-english-smart-turn-vs-turn1mini`).

## The question this answers

P0.13 measured **how well** Pipecat Smart Turn v3.2 and p99lab turn-1-mini endpoint English turns, and
published the result as aggregate rates plus a Pareto frontier. Its `RESULT.json` holds
`denominator` / `gate` / `frontier` / `dense` — and **no per-sample record at all**. Its audio, span
manifest and raw score caches lived under its own `.gitignore` (`data/`, `_cache/`, `.venv/`) and went
away with its worktree. So the question a person asks next — *which recording, and what did the model's
probability actually do right before it was wrong?* — had no answer you could read off a committed file.

This directory produces that answer **from a real re-run**: the audio and the ground truth are re-fetched
from the pinned revisions inside an independent worktree, both models are re-inferred here on CPU, and
every record is a measurement from this run. Nothing is back-derived from P0.13's aggregates. P0.13's
published numbers are used the other way round instead — as an integer-equality check on this run's
independent recomputation (see **Consistency** below). If the two ever disagree, the run says so loudly
instead of quietly reporting different numbers under the same label.

## The fixed operating point — deliberately NOT re-selected

| | threshold | actionDelaySeconds | timeoutSeconds |
|---|---|---|---|
| operating point | **0.13** | **1** | **3.5** |
| baseline (a plain timer) | 0 | 1 | 3.5 |

`threshold=0.13, actionDelaySeconds=1, timeoutSeconds=3.5` is the exact tuple P0.13's `CONCLUSION.md` §2b
reports for **both** models on the `merged` view. Reusing one tuple is what makes the two models'
per-span verdicts strictly comparable, and reusing *P0.13's* tuple is what makes the consistency check a
real check rather than a tautology. The threshold grid is intentionally not swept here: a fresh sweep
would land on some other row and the comparison would evaporate.

The `threshold=0` row is the "never consult the model, just wait" policy — mathematically a plain
VAD/timer. It is included so the report can answer whether either model is worth its cost (AC3), which is
the cheapest sanity check on a detector. At `threshold=0` every span fires on its first cell, so this
baseline detects every end-of-turn instantly and cuts every pause that outlasts `actionDelay`; the two
models must beat *that* to be worth anything.

| `.gitignore` | keeps `.venv/`, `data/` and `_cache/` out of the tree — the same hygiene policy P0.13 used. |

## Reproduce everything, in two commands

From the repository root (paths inside both scripts resolve from the script's own location, so the
working directory does not matter):

```bash
# 1. fetch + verify every byte (network; downloads ~330 MB once into data/, then verifies)
node experiments/voice-turn-detection-compare/worst-cases-replay/fetch-and-verify.mjs --all

# 2. re-infer both models and rewrite worst-cases.jsonl / RESULT.json / ERROR-REPORT.md
node_modules/.bin/tsx --tsconfig server/tsconfig.json \
  experiments/voice-turn-detection-compare/worst-cases-replay/extract-worst-cases.mts --shards 8
```

Then run step 2 once more with `--determinism-check`: a second process re-runs the pipeline from the pinned
manifests down the **same Smart Turn scoring path** the first one took (it mirrors the parent's cache state,
so a cold cache is re-scored in both and a warm cache is read by both) and the two `RESULT.json` documents
are compared field by field — identical apart from their wall-clock timestamps. That is the "one command
reproduces the same bytes" evidence AC4 asks for, and it is why step 2 is safe to repeat. How much that
covers therefore depends on the cache: cold, it includes the Smart Turn inference itself; warm, it covers
everything downstream of the scores. turn-1-mini's score file is the one input the child always reuses (it
carries the python run's wall-clock timing, which would make the child differ on a field that says nothing
about reproducibility); that model's output is covered by its own `selfCheck`, and the Smart Turn table by
the cache audit. `RESULT.json.determinism.scope` states which of the two cases this run was, and
`RESULT.json.determinism.parentScoredSmartTurn` records the path taken.

`extract-worst-cases.mts` flags: `--shards N` (default 8; Smart Turn is one ONNX call per cell and the
work is sharded by span across N worker processes), `--no-cache` (ignore the score cache), `--audit-cells N`
(re-score N cached cells with a fresh ONNX call and report the max deviation — the check that the cache
holds model output rather than something stale), `--no-python` (reuse an existing turn-1-mini score file),
`--determinism-check` (spawn a second process over the same inputs and compare the two result documents
field by field), `--no-courtesy` (skip the concurrency poll, recorded as *skipped* rather than as a pass),
`--smoke N` (score N spans and write nothing — a dry run of the whole path).

## How to read `worst-cases.jsonl`

Line 1 is `{"kind":"meta", …}`: the operating point, the baseline point, the views, the ranking rules and
the pinned reproduction commands — read it first, it tells you how to interpret every later line. After
that come `{"kind":"worst-case", …}` records (Smart Turn's false cutoffs, Smart Turn's missed endpoints,
then turn-1-mini's), then one `{"kind":"cross-table"}`, one `{"kind":"baseline"}`, one
`{"kind":"consistency"}` and one `{"kind":"ac7-evidence"}` line.

Each `worst-case` record carries:

- `sampleId`, `speaker`, `group`, `label` (the ground truth: `hold` = the speaker only paused, `eot` = the
  speaker really finished) and `gtLabel` in words;
- `wav`: the repository-relative path, the **measured** sha256 and byte count, and `reproduction` — the
  pinned dataset/revision/row/turn/span coordinates plus the one command that materialises exactly those
  bytes;
- `audio`: the annotation onset, the silence the grid walked, whether a digital closing tail was appended,
  and how many cells were scored;
- `observed`: which decision the policy produced, the model's fire time, the **decision event time** in ms
  from clip start, the **GT time** in ms, and the gap between them with its definition;
- `probabilityTrajectory`: the p_eot at the trigger cell, a window of neighbouring cells as
  `silenceSeconds → p_eot` pairs, and the maximum p_eot the model reached anywhere on that span. This is
  the field that answers "what was the model actually saying" — a cutoff with p_eot 0.97 is a confident
  wrong answer, a cutoff with p_eot 0.14 is the threshold being too low.

## Ranking rules (AC2 asks for an explainable severity order)

- **False cutoff** (a `hold` the policy cut): severity is `gapSeconds = (true pause length) − (the moment
  the cut landed)`, i.e. how much of the pause the speaker still had left when they were interrupted.
  Bigger is worse: the most severe case is a long real pause that was cut almost immediately. Ties break
  by longer true pause, then earlier cut, then span key — a total order, so the ranking is reproducible.
  When a hold trips both the model clause and the timeout clause, the reported cut time is the *earlier* of
  the two (the model's fire, or the timer), because that is when the cut actually happened.
- **Missed end** (an `eot` the model never crossed the threshold on inside `timeout`): severity is
  `gapSeconds = (model fire time) − timeout`, and **"never crossed the threshold at all" is Infinity and
  ranks first** — the model gave no signal and the endpoint came only from the timer. Ties break by span key.

## Consistency with P0.13 (AC5)

At the fixed point, this run's independently recomputed counts are compared against the k/n P0.13
published for the same tuple — read programmatically out of P0.13's committed `RESULT.json` frontier
(never typed in from the prose), so a changed P0.13 artifact changes the target rather than silently
passing a stale expectation. AC5 asks for the `eot-bench-en` and `merged` views specifically: those four
model/view pairs (Smart Turn 33/705 + 27/400 and 33/710 + 27/416; turn-1-mini 32/705 + 14/400 and
32/710 + 14/416, with mean latencies 0.29025 / 0.279808 and 0.366 / 0.362981) must match exactly, and the
verdict is recorded in `RESULT.json.consistency` and printed in `ERROR-REPORT.md`.

The same block carries AC1's grouping check as a comparison rather than an assertion: the number of
speaker/session groups this run re-derived from its own fetch of the pinned parquet is put next to the
count P0.13 published (`groupDistribution.groups`), because a same-sized denominator reached through a
different grouping would be a different corpus.

One honest caveat, stated rather than hidden: this run also reports the `librispeech-en-real` view, and
P0.13 **published nothing to compare it against** at this operating point — its per-view output is a
Pareto frontier, and on that degenerate view (5 holds / 16 EoT) the 0.13 row is dominated by
`threshold=0.01, actionDelay=0.5, timeout=1` (same 0/5 and 0/16, zero latency). That row is therefore
recorded as `status: "not-published"` with this run's own numbers beside it, not as a match and not as a
divergence. Treating an unavailable target as a pass is exactly the failure this check exists to prevent.

## Honest notes on method (where this deviates from the Plan's letter, and why)

1. **Corpus A audio is re-fetched by this task's own fetcher, not by `datasets/fetch-real-samples.mjs`.**
   Plan step 3 says to call/reuse that script. It writes into the shared
   `experiments/voice-turn-detection-compare/datasets/real/` path, which is a cross-task shared resource
   (a concurrent task writing there would race). `fetch-and-verify.mjs --corpus-a` instead performs the
   same two operations — the same HuggingFace rows API call and the same `ffmpeg` recipe that script
   uses — into this directory's own `data/corpus-a/`, and then does something strictly stronger than the
   original: it compares each clip's sha256 against the value recorded in the committed P0.6 manifest,
   i.e. against an independent prior run, and fails if they differ.
2. **P0.13's python scripts are byte-identical copies, not imports.** The task forbids writing to P0.13's
   landed paths; a copy plus a recorded sha256 comparison of both sides leaves those paths untouched while
   still proving the pinned revisions and the fetch recipe are P0.13's.
3. **The scoring is this task's own code.** `extract-worst-cases.mts` rebuilds the span geometry from
   `corpus.mts`'s rule and calls `protocol.mts`'s own `sweepPolicies` for the rates, so an internal
   cross-check asserts that the per-span reading and the protocol sweep produce the same counts — and the
   AC5 comparison is what proves the spans and scores are P0.13's objects, not merely similar ones.
4. **The task prose mis-quotes the parquet sha256.** Its Proposal gives
   `e475d435c8`**`69`**`3912243e8a810bf7e34a59e01e208551ce5b362c9c778b0fdc4`; the value actually pinned by
   P0.13's `fetch-eot-bench-english.py` line 38, and the one this task measured on the downloaded file, is
   `e475d435c8`**`e6939122`**`43e8a810bf7e34a59e01e208551ce5b362c9c778b0fdc4`. The script is the pinned
   authority, so that is what the fetch verifies; the discrepancy is recorded here rather than silently
   picked.

## Boundaries observed

- **No production change**: `git diff <merge-base> -- server/modules/voice-realtime/ src/modules/chat/voice-realtime/`
  is empty (recorded, with the merge-base rationale, in `RESULT.json.evidence.productionDiff`).
- **No training, no fine-tuning, no training-only weights**: both fetched artifacts are ONNX inference
  graphs, loaded by `onnxruntime` on CPU. The turn-1-mini repo's `.safetensors` (the training-side
  artifact) is recorded by hash for reference and deliberately **not** downloaded.
- **No paid API call**: egress is limited to `huggingface.co`, `datasets-server.huggingface.co`,
  `creativecommons.org` and `openslr.org`; the only environment variables this task's own code reads are
  `SMART_TURN_MODEL` (an optional local file path), `HOME` and `HF_HOME` (a cache directory) — no
  credential or token.
- **P0.14 and P0.13 untouched**: `git diff <merge-base> -- experiments/voice-turn-detection-compare/chinese-zeroshot-and-ft-readiness/`
  and `.../english-smart-turn-vs-turn1mini/` are both empty, and the P0.14 worktree is never written to.
- **Courtesy check before the heavy inference** (AC6): before the first cell is scored the run polls
  `ps` for a `run-benchmark.mts` / `run-turn1mini.py` / `full-suite-runner.js` process whose command line
  names the P0.14 worktree; if one is running it waits and re-polls (≤600 s per wait, ≤1800 s total) and
  either way records the detection times, hits, waited duration and the proceed/park decision in
  `RESULT.json.courtesyCheck`.
