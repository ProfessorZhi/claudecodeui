## 解读

1. **上一轮的正面结果没有推广开来。** 上一轮只用了一条恰好有利的消息（本轮的 c4）：c4 在 d01 上仍是 5/5 ✅，读数被复现了；但换成其他真实消息，d01 在 8 个上下文里有 5 个低于基线（基线 7/10）。
2. **「只含目标」不再带来收益（旧 8 条 −1.4pp）。** 上一轮的解释是「只要上下文给出正确拼写、没有竞争者就会有收益」，这一轮在旧 8 条上不成立。
3. **有竞争者时伤害很大，而真实对话里竞争者很常见。** 从候选池看，提到语音模块某个文件时几乎总会同时提到它的兄弟文件：`voice.routes.ts` 从来没有单独出现过；d04 的「目标加竞争者」与「只含目标」之比是 31:1。典型错误是把 d01 的目标写成 `voice.routes.ts`，或写成上下文里引用过的误识别写法 `voice.rouse.ts`（c1）。
4. **与名字无关的上下文也会带来伤害。** 「都不含」分层在旧 8 条上是 −20pp；d07 没有标识符，基线 90% ✅，加上下文后降到 62.5%，与上一轮 d07 的退化一致。
5. **编造细节 7.7%。** 上下文里的名字会被插进毫不相干的片段：c2 让 d05、n03 的指令里出现了 `ChatComposer.tsx`、`useChatComposerState.ts`、`voicePlayer.ts`。
6. **延迟不可接受。** 上下文臂 p90 为 17.7 秒，519 次里有 45 次超过当前的 20 秒超时（8.7%），最慢 64 秒；无上下文基线的 p90 是 7.6 秒，130 次里 0 次超过 20 秒。
7. **扩展 5 条是净收益，但不足以扭转结论。** 收益主要来自 n01（`ChatComposer.tsx`）；它的格子少（目标加竞争者只有 2 个组合），而且扩展集的判定口径与旧 8 条不同。

## 限制

- 每个（上下文 × 片段）组合只有 5 次；判定按分层汇总。
- c1、c7 是讨论语音实验本身的消息，引用了识别错误的写法，比一般对话更容易误导。敏感性检查（`EXCLUDE=c1,c7`，不属于预注册）：去掉这两个上下文后，规则 1（旧 8 条 −11.2pp）、规则 3（4.9%）、规则 4（p90 20.1 秒）仍不通过；规则 2 变为通过（剩余 3 个「目标加竞争者」组合的竞争者上线率为 0）。所以竞争者上线主要来自这两条自指消息，但结论不变。
- 片段是 TTS 合成，目标集中在语音模块；A1 的基础比例来自全部项目的打字输入，不是同一个总体。
- 扩展 5 条的音频（`fixtures/webm/`）已入库（登记在 `docs/experiments/README.md`）。离线重算还需要旧 8 条的本地 webm，因为 `an.mts` 经 `raw/written.mts` 导入了 `raw/omni.mts`，后者在导入时读取 `experiments/voice-gemini-paired-quality/out/webm/`（生成方法见 `raw/README.md`）。

## 附：语义核验（2026-09-24）

上面所有读数都来自机械规则（`raw/judge.mts`、`raw/judge-ext.mts` 与名字匹配）。为确认规则没有系统性误判，人工逐条阅读了 13 条片段在全部臂下的每一种不同输出（`audit-dump.mts`），把与规则不一致的判断写成 `semantic.mts`：一个「泄漏」检测器，外加 12 条逐条覆盖。泄漏检测器标出的 24 条都经过人读确认；它在第一版里把 n05 的正常改写「请确认两件事」误报为泄漏，这个特征已经删掉。

**一致率**：649 条里 609 条一致（93.8%）。分歧是单向的，规则普遍**低估了上下文的伤害**：

| 规则 → 人读 | 条数 | 主要原因 |
|---|---|---|
| ✅ → ❌ | 15 | 上下文泄漏：规则只检查必需的关键词，关键词都在就判 ✅ |
| ◐ → ❌ | 11 | 把目标写成另一个真实文件（d01 写成 `voice.routes.ts`、d02 写成被否定的 `voice.service.ts`）；上下文泄漏 |
| ✅ → ◐ | 11 | 添油加醋：「语音输入按钮」「如果没有则修复」「请排查并修复」（后者在无上下文基线里也有） |
| ❌ → ✅ | 3 | n04 的否定只是错字或多一个字（「不要区合成语音」「不要再区分」） |

**一种规则完全没有覆盖的失败：上下文泄漏。** 上下文臂 519 次里有 24 次（4.6%），无上下文基线 0 次。形态包括：把整段上下文塞进 JSON 的 `transcript` 或接在指令后面（例如「按以下方案实现语音回放功能：## 现状…」）；模型把自己当成助手续写（「Now the code.」「现在处理代码部分。」）；把上下文里的另一件事编成第二条任务（「两件事：…2. GOAL-006 卡在 close 闸上…」）；甚至用上下文整段替换掉原意（n05 被写成「对当前 dev server 的语音输入链路做一次完整的现状审计」）。

**用语义判定重算：**

| 读数 | 规则 | 人读 |
|---|---|---|
| 期望净收益（旧 8 条） | −12.5pp | −12.5pp |
| 期望净收益（扩展 5 条） | +5.6pp | **−8.3pp** |
| 全部片段 ✅ / ❌（无上下文） | 80.0% / 4.6% | 78.5% / 3.8% |
| 全部片段 ✅ / ❌（带上下文） | 72.1% / 8.1% | 68.0% / 12.7% |
| 条件第二次调用 ✅ / ❌ | 80.4% / 5.4% | 78.5% / 4.8% |
| 条件本地替换 ✅ / ❌ | 79.7% / 4.0% | 78.2% / 3.3% |

规则判为「通过」的唯一一项（扩展 5 条的净收益）在人读后也变为负值。结论不但不变，而且更强：对话上下文在两个集合上都是净伤害，并引入了一种基线里不存在的失败（泄漏）；条件使用只能把伤害降到与基线持平，没有收益。
