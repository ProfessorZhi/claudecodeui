## 已确认的决策

| # | 决策 | 含义 |
|---|---|---|
| D1 | **不限制单次使用时长** | 一次 Live Voice 开一小时是正常使用。运行时只保留**防失控的速率保护**（见 C5），不因总时长或总额结束会话。 |
| D2 | **成本异常线只作用于自动测试** | 异常线是测试里的断言（回放 / 夹具），不是运行时的限制，也不触发运行时告警或终止。具体数值可随上下文大小调整（见「成本模型」）。 |
| D3 | 保留**收尾一句**，除非能证明有更便宜的等价做法 | 实测去掉它后，后续 5 句里有 3 句被听到却没有转发（F7）。P0 验证「直接插入一条助手 `OK` 条目」是否等价且更省。 |
| D4 | **把会话上下文给模型，并如实说明这是上下文；不对「怎么用」做过多约束** | 不预设「只修正识别」「不许改写」之类规则。模型怎么用要靠**实际运行观察**来调；因此提示词与上下文模板必须能**不重启服务**地修改和对比（见「观察与调参」）。 |
| D5 | **上下文按字符数计量**，不是 token，也不是「最近 N 轮」 | 从最新往回取可读内容，直到字符预算用完。字符好度量、好测试；token 数由上游每次响应的 `usage` 在线校准并记录。 |
| D6 | **上下文只含用户在页面上看得见的「说出来的话」** | 与前端折叠规则同源：折叠的工作段（思考、工具调用、子代理、任务通知）、被隐藏的工具结果、内部生命周期行一律不进。 |
| D7 | **可用就用语义端点**（话没说完就等） | 取决于当前模型与服务是否支持；P0 验证。不支持则不做，不影响其余部分。 |
| D8 | **不为想象中的安全风险设置门槛** | 不做脱敏、保真校验、默认关闭、二次确认。系统先要能跑起来；真实出现问题再据实处理。上一版 SPEC 中的相关条目已删除。 |

## 目标

1. **成本与连接时长无关**：每句话的成本为常数，不随对话变长而上升；上下文越大越贵，但不增长。
2. **只把语音发给上游**：在 CloudCLI 一侧做 VAD，缓冲并合并相隔很短的语音，较长间隔才提交；无语音的片段不发送。
3. **一次说话 = 一次提交**：被停顿切碎的片段在发给模型之前合并，消除上游 VAD 把一句话切成多段（含识别为空的段）。
4. **模型带着会话上下文工作**：每个会话（包括换出来的新会话）开头都带一份「可读上下文」，有字符上限，不随响应次数增长。
5. **长连接可持续**：空闲时透明换一个新的上游会话，浏览器一侧不感知。
6. **可观测、可调参**：每个片段、每次响应、每次换会话都有日志与用量，能与阿里云账单对上；提示词与上下文模板可热修改，能 A/B。

## 非目标

- 不更换模型；不改 Claude Code 一侧的行为。
- 不做 TTS（语音回复）。当模型想「反问你」时怎么呈现（文字还是语音）不在本 SPEC；它仍通过 `session_send` 之外的通道需要单独设计。
- 不在 V1 做「用模型生成会话摘要」（摘要本身要花 token）；上下文用确定性截取。
- 不改变现有的合并窗口（2.5 秒）与忙等待投递逻辑；它们保留，作为兜底。

## C1 浏览器端切分（SegmentVAD）

### 输入输出

- 输入：`audioSource` 产出的 `VoiceRealtimeAudioFrame`（20 ms，Float32，已有，见 `src/modules/chat/voice-realtime/audioSource.ts`）。
- 输出：一串**语音段**，每段是 16 kHz 单声道 PCM16，附序号 `seq`、起止时间、时长。

### 参数（默认值，均可配置；数值在验收中标定）

| 参数 | 默认 | 含义 |
|---|---|---|
| `frameMs` | 20 | 判定粒度 |
| `startFrames` | 3（60 ms） | 连续这么多帧超过进入阈值才判为开始说话 |
| `preRollMs` | 300 | 段首向前回溯，避免吃掉起音 |
| `hangoverMs` | 700 | 低于退出阈值后保持这么久才算「这次停顿」 |
| `mergeGapMs` | 1,500 | 两段语音之间的静默短于此值就**合并成一段**（把句内停顿接上） |
| `commitGapMs` | 2,000 | 静默达到此值才提交这一段（略大于 `mergeGapMs`，给合并留出判定窗口） |
| `maxSegmentMs` | 20,000 | 一段的上限；到达时在最近的能量低点处强制切开 |
| `minSegmentMs` | 250 | 短于此的段视为噪声丢弃（不发送） |
| 阈值 | 自适应 | 进入/退出阈值相对噪声基线（沿用 `src/shared/voiceTrim.ts` 的 3.0 / 1.8 倍基线，基线取**滑动窗口**第 15 百分位，而不是整段） |

### 状态机

```
IDLE ──(startFrames 连续高能量)──► SPEAKING(段首 = 当前 − preRollMs)
SPEAKING ──(低能量持续 hangoverMs)──► PAUSED(记录 pauseStart)
PAUSED ──(静默 < mergeGapMs 内再次开口)──► SPEAKING   （合并：同一段继续，间隙里的静默**保留**为短静音）
PAUSED ──(静默 ≥ commitGapMs)──► COMMIT：封口，输出一个语音段 ──► IDLE
SPEAKING ──(时长 ≥ maxSegmentMs)──► 在最近低能量点 COMMIT 并立即开始下一段
```

- 合并时间隙里的静音**保留**（不拼接掉），让下游模型看到真实的停顿，也不改变语速。
- 连接断开 / 用户点 End / 静音（Mute）：已缓冲未提交的段**先提交**再处理（End 与静音都不得丢掉最后一句话）。

### 协议

浏览器 → 服务端新增帧（旧的连续 `audio` 帧继续兼容，走原有「上游服务端 VAD」路径，便于灰度）：

| 帧 | 字段 | 说明 |
|---|---|---|
| `segment_start` | `seq`, `startedAtMs` | 一个语音段开始 |
| `audio` | `audio`(base64 PCM16), `seq` | 段内的帧；带 `seq` 的 `audio` 属于该段 |
| `segment_end` | `seq`, `durationMs`, `reason`(`gap`/`max`/`end`) | 段结束，服务端据此提交 |
| `context` | `text`, `chars`, `rows` | 上下文包（见 C2）；连接建立时与每次需要换会话前发送 |

服务端 → 浏览器新增：

| 帧 | 字段 | 说明 |
|---|---|---|
| `segment_ack` | `seq`, `state`(`committed`/`dropped`), `reason?` | 段已提交给模型，或被丢弃（过短、上游不可用） |
| `rotated` | `reason`, `ms` | 信息性：上游会话已换（不需要用户操作） |

### 提交方式（需 P0 验证）

在 CloudCLI 做了切分后，上游应关闭自己的 VAD：`session.update` 里 `turn_detection: null`（手动模式），服务端在 `segment_end` 时依次发 `input_audio_buffer.commit`、`response.create`。**此前我们只在文本回合里验证过 `turn_detection: null`，音频手动提交没有验证过**，这是 P0 的第一项。若手动模式不可用，回退方案：保持服务端 VAD，但只在段内持续送帧、段与段之间送**不超过 `commitGapMs` 的真实静音**，让上游自己的 VAD 与我们的边界基本一致。

### 语义端点（D7，可用才用）

目的：话明显没说完（「把 server 里的 voice.ts 的」）时等一等，而不是按静默时长硬切。有两条实现路径，P0 看服务支持哪一条：

1. **服务端语义 VAD**：`turn_detection.type` 取语义类取值（如 `semantic_vad`），若百炼该模型接受就直接用。
2. **提示词层面的等待**：允许模型对「明显不完整」的片段**不调用工具**；后续段到达时它在同一会话里看到前后两段，再一次性转发。需要一个兜底：模型在 `holdTimeoutMs`（默认 5,000）内没有等到后续语音，服务端发一次 `response.create`（带一次性指令「把用户已经说过但还没转发的话转发」），保证不丢话。

两条都不可用则关闭，行为退回到仅靠 C1 的静默判定。

> **P0-S4 实测（2026-10-10）：两条路径都没有成立，本条按「关闭」执行。** 控制面只是回显——`semantic_vad` 与故意乱写的 `bogus_vad_type` 被回显成同一组字段（`echoDiscriminates=false`），所以「accepted」不构成证据；提示词层面的等待 2 次运行 0 次生效（`held=0/2`）。「等一等」因此只能落在 CloudCLI 侧（C1 的静默判定），不依赖上游语义端点。

## C2 上下文包（ContextPack）

### 原则（D4–D6）

- 给模型的是**会话里用户看得见的说出来的话**，并在包前面明确标注「以下是当前 Claude Code 会话的上下文」。**不附带关于如何使用的细则**；基础指令仍是「你是这个 Claude Code 会话的语音中继，把用户说的话通过 `session_send` 交给它」。使用方式靠运行观察来调（见下节）。
- 与前端一致：用页面已有的判定得到「说出来的话」，不在服务端另写一套。

### 取哪些行（规则同源）

| 行类型 | 判定（`src/modules/chat/utils/workSegments.ts` 的 `isWorkSegmentMember` 与现有可见性） | 进包 |
|---|---|---|
| 用户消息（含来自语音转写的） | 非工作行的用户行 | 进 |
| 助手回复正文 | 非工作行的助手文本 | 进 |
| 思考 | `isThinking` | 不进 |
| 工具调用与其结果 | `isToolUse`、`shouldHideToolResult` | 不进 |
| 子代理容器 | `isSubagentContainer` | 不进 |
| 任务通知 | `isTaskNotification` | 不进 |
| 内部生命周期行 | `command_lifecycle` 等 | 不进 |
| 图片 / 附件 | — | 只放占位：`[图片]`、`[文件 xxx.ts]` |
| 长代码块 | 助手正文里的围栏代码 | 保留前 `codeHeadLines`（默认 3）行 + `…（省略 N 行）` |

### 字符预算与截取（D5）

| 参数 | 默认 | 说明 |
|---|---|---|
| `contextBudgetChars` | **2,000** | 包的字符上限，**硬上限**，服务端再校验一次 |
| `rowCapChars` | 600 | 单行上限；超过取首 70% + `…` + 尾 30% |
| 取法 | 从最新往回 | 逐行加入，直到下一行放不下就停；不按轮数取 |
| 格式 | `角色：文本` 每行一条，带相对时间 | 简单文本，便于模型读与我们 diff |

换算（用于估算与告警，真实值由 `usage` 校准并记录）：中文 ≈ 0.7–1 token / 字符，英文与代码 ≈ 0.25–0.3 token / 字符；混合会话 ≈ 0.5。默认 2,000 字符 ≈ 1,000 token。

### 何时更新

- 连接建立时发一次；
- 每次**换会话前**（C3）重发最新的；
- 同一个会话**内部**不重发（不增长，也不需要）。

## C3 上游会话池与换会话（UpstreamPool）

### 为什么换会话

F1：同一会话里每次响应的读入每次多约 75 token。20 句话（40 次响应）累计约 8 万 token。换一个新会话即可把读入重置回「指令 + 工具 + 包」，且包可以刷新为最新的会话内容。

### 为什么不是「每句一个新会话」

F10：连接建立 0.2–9 秒不等，每句都新连会引入用户可感的延迟与失败面。因此：**预热待命会话 + 空闲时切换**。

### 规则

| 项 | 规则 |
|---|---|
| 触发 | 上一次响应的 `usage.input_tokens` 超过 `rotateAtTokens`（默认 `包估算 token + 450 + 600`），或会话已服务 `rotateAfterSegments` 段（默认 12） |
| 预热 | 触发阈值的 70% 时在后台新建待命会话，完成 `session.update`（指令 + 工具 + 最新上下文包） |
| 切换时机 | **仅当**：没有未提交的段、上一个响应已 `response.done`、距最近一次语音 ≥ `idleBeforeSwitchMs`（默认 1,500）。切换是把后续的段发往待命会话，随后关闭旧会话 |
| 说话中到达阈值 | 不切换；继续用旧会话直到下一个空闲点 |
| 切换失败 | 待命会话建立失败或已断开：保留活动会话，记 `ROTATE_FAILED`，下一个空闲点重试；不得中断用户的语音 |
| 无状态假设 | 切换不迁移模型历史；新会话只带指令 + 工具 + 当前上下文包 |

### 与现有重连的关系

- 现有 bridge 的「上游意外断开 → 自动重连并重新声明」保留，且复用同一个 `session.update` 构造函数（带包）。
- 一个**已提交但未收到 `response.done`** 的段，在会话切换或重连后按 `seq` 幂等重放一次（见 AC-9）。

## C4 / C5 沿用与扩展

- **投递（C4）**：2.5 秒合并窗口、会话忙时等待并并入同一条、`session_send` 单飞保护全部保留。
- **循环保险**：两次完整语音之间工具调用超过 6 次，桥不再回应（`TOOL_LOOP_GUARD`）；工具结果文案固定为「已接受，不要再调用，回复 OK」。
- **速率保护（C5）**：30 秒内估算花费超过 ¥0.015 结束连接（`SPEND_LIMIT`）。这是**防失控**（实测失控循环 ≈ ¥0.49 / 分钟），不是成本异常线（D2），不设总额上限（D1）；上下文变大后阈值随包大小线性放宽（`windowLimit = 0.015 + 0.003 × (包 token / 1000)`），环境变量可覆盖。
- **新增日志**（每段一行，带时间戳）：`segment seq=… dur=…ms merged=… reason=… sent=…frames`、`response in=… out=… cost~CNY…`、`rotate reason=… from=… to=… idle=…ms`、`context chars=… rows=… est_tokens=… measured_tokens=…`。

## 成本模型

### 变量

| 符号 | 含义 | 取值 |
|---|---|---|
| `T` | 每次响应读入的文本 token = 指令与工具（≈ 450）+ 包 | 包 2,000 字符 ≈ 1,000 token → `T ≈ 1,450` |
| `r` | 每句话的响应次数 | 2（转发 + 收尾 OK）；P0-S5 已验证插入助手 `OK` 与 `conversation.item.delete` 都可用（`input_tokens` 643→481），r=1 的**前提**成立，实际折扣幅度待 P4 与账单对账 |

## 失败模式与降级

| 失败 | 处理 |
|---|---|
| 手动提交不被上游支持 | 回退到「服务端 VAD + 段间只送短静音」；功能开关 `VOICE_REALTIME_MODE=continuous` 保持旧路径 |
| 浏览器 VAD 漏检（小声说话） | 自适应阈值；在 UI 的麦克风指示上给出电平；日志计数疑似漏检 |
| 一句话被 `maxSegmentMs` 强切 | 在能量低点切；两段的转发消息由 C4 合并 |
| 待命会话建立失败 / 变慢 | 保留活动会话，不影响说话；日志 |
| 上下文过期（用户刚切了话题） | 每次换会话时重算；同一会话内不重发。模型自己可以通过后续语音判断 |
| 语义等待后没有后续语音 | P0-S4 已确认上游不提供语义等待（控制面回声直通 `echoDiscriminates=false`、提示词等待 `held=0/2`），等待完全由 C1 在 CloudCLI 侧按静默判定；`holdTimeoutMs` 是本地计时器，超时即转发，保证不丢话 |
| 上游中途断开 | 已提交未完成的段按 `seq` 重放一次；仍失败则 `segment_ack dropped` 并告知用户 |
| 费用失控 | 沿用速率保护；日志逐段记账，可与账单逐位对上 |

## P0 结论

P0a（2026-10-10）跑了 S1–S3，P0b（同日）跑了 S4–S6。六条结论都出自**真实 DashScope 上游**的原始追踪
（`experiments/voice-realtime-segmented/p0/traces/`，含真实 `session.created` 与 `response.done` 用量），
verdict 由 `node scripts/voice-realtime-p0-record-check.mjs experiments/voice-realtime-segmented/p0/RESULT.json`
（不带 `--stage`，要求 S1–S6 全部齐全）从追踪**推导**并与 `RESULT.json` 逐字段比对——不是手写。
合计花费 ¥0.034395（上限 ¥0.05，其中 P0a ¥0.025480 + P0b ¥0.008914 ≤ ¥0.01）。
复核命令：`node scripts/voice-realtime-p0-record-check.mjs experiments/voice-realtime-segmented/p0/RESULT.json --spec`。

- S1 supported — 证据 `s1-manual-commit.json`；commits=3 session_send=2；spend ¥0.003497。`turn_detection: null` 下**音频**手动提交可用：两次尝试（1 段 / 2 段）共 3 次 `input_audio_buffer.commit` 都被接受，每次返回 `response.done`，0 个错误帧。C1 按「CloudCLI 切分 + 段尾手动 commit」推进，**不需要**回退到「服务端 VAD + 段间静音」。注意两点实测细节：(a) 上游把**同一次**函数调用以两种方言各投递一次（`response.function_call_arguments.done` 与 `response.output_item.done` 里的 `function_call`，同一 `call_id`），转发计数必须以 `call_id` 去重，否则会把一次转发读成两次；(b) 三段里有一段模型选择**不**转发（只回了文本），所以「手动提交可用」不等于「每段必转发」——这正是 C1 协议里 `session_send` 缺席分支要处理的情况。
- S2 supported — 证据 `s2-session-rotation.json`；n=6 handover=ok；spend ¥0.001506。6 次「socket open → `session.updated`」：p50=259 ms、p90=736 ms、min=130 ms、max=736 ms，明显好于 F10 记录的 0.2–9 s 上界。交接：A 答第一段期间打开并预热 B，A `response.done` 之后把第二段发给 B，B 正常给出 `response.done`（1 次 `session_send`），0 个错误帧。但同一份追踪里 `warmed_before_done=false`：A 这次答得太快（<1 s），B 的建立+预热还没完成 A 就回完了。结论是 C3 的预热必须**在段开始时就发起**、并允许「B 尚未就绪」这一状态存在（该段继续走 A 或排队），不能假设预热带内完成。
- S3 supported — 证据 `s3-context-injection.json`；forwarded=12/12；spend ¥0.020478。`instructions` = 中转规则 + 1,926 字符上下文包（共 2,480 字符），6 句 × 2 次全新会话：12/12 条响应都调用了 `session_send`，平均归一化编辑距离 0（逐字转发，未改写），带标识符的 4 条响应 4/4 命中（`MessageComponent.tsx` 与提交 SHA 原样保留），`usage.input_tokens` p50=1036、max=1042。**没有**出现「模型自己答而不转发」的形态，D4「不附加使用细则」的取向可以保留；C2 的包按 1,926 字符起步，单次响应读入约 1.04 k token、约 ¥0.0017/响应。
- S4 unsupported — 证据 `s4-semantic-endpoint.json`；echoDiscriminates=false held=0/2；spend ¥0.002214。服务端语义 VAD 的「接受」是回声直通，不可信：同一控制会话上 `semantic_vad` 与故意乱写的 `bogus_vad_type` 被**原样回显同一组字段**（`echoDiscriminates=false`，两次控制会话不发响应故 0 成本）。提示词层面的等待也没成立：2 次运行都立刻转发了未说完的片段（`held=0/2`，`forwardedImmediately=2`）。结论：语义端点两条路径都**不可用**，按「语义端点（D7）」一节回退——「等一等」只能由 C1 在 CloudCLI 侧实现，不能指望上游。
- S5 supported — 证据 `s5-history-control.json`；assistantOK=true delete=accepted input_tokens=643→481；spend ¥0.001929。助手 `OK` 条目可插入（回来的 `conversation.item.created` 带 `role: assistant`），下一段的窗口恰好 1 次转发，`conversation.item.delete` 被接受（`conversation.item.deleted`）**且**其后一次响应的 `usage.input_tokens` 从 643 降到 481——「被接受」与「真生效」是两回事，这里两者都成立。注意 `conversation.item.deleted` 本身也属 S4 那类回声陷阱（对不存在的 id 照样回），所以判据取 token 落差而非回执。结论：**不换会话即可控历史**，成本模型的 r=1 前提成立。
- S6 unsupported — 证据 `s6-cache-fields.json`；cacheFieldPresent=false discountObserved=false input_tokens=1451,1529；spend ¥0.004771。在同一段 2,000 字符前缀上跑两次响应，两份 `usage`（`input_tokens` 1451 → 1529）在**任何深度**都没有 cache 类字段（`cacheKeys=[]`，`usageKeyPaths` 已逐键记录）。结论：实时接口的用量里**没有缓存折扣**，C2 的包按全量重复计费——成本模型不能按缓存打折，`T` 就取整包 token。

## 开放问题

1. **手动提交是否支持**（P0-S1）。决定 C1 的整体形态。
2. **语义端点的服务端支持**（P0-S4，已实测关闭）：控制面的「接受」是回声直通、提示词层面的等待 0/2 生效，两条路径都不可用；等待改由 C1 在 CloudCLI 侧实现，「语义端点（D7）」一节按降级执行。
3. **平台对「文本历史」的丢弃规则**：文档只说明音频历史与轮数上限（F11）；P0-S5 已确认文本条目可被 `conversation.item.delete` 删掉且使输入 token 下降，但「函数调用、工具结果、`OK` 这类文本是否同样受 100 轮约束」仍无说明，需在 P4 长会话里观察。
4. **`conversation.item.delete` / 插入助手条目是否支持**（P0-S5，已实测支持）：两者都被接受，delete 之后 `input_tokens` 由 643 降到 481；因此**不换会话即可控历史**，每句 2 次响应的 `r` 有降到 1 的前提（实际降幅待 P4 与账单对账）。
5. **缓存**（P0-S6，已实测无折扣）：同一段 2,000 字符前缀的两份 `usage` 在任何深度都没有 cache 类字段，重复前缀按全量计费——上表的成本就是账单口径。
6. **多标签 / 多设备同时使用**：同一会话的两个浏览器连接各自持有上游会话，成本翻倍；是否限制为一个活动语音连接，待评审。
7. **模型想「反问你」时怎么呈现**：D4 放开了对用法的约束，但输出通道（文字提示 / 语音）不在本 SPEC 范围；模型此时只能通过 `session_send` 把疑问转给 Claude，或者什么都不说。观察后再定。

## 范围外的相关项（另行跟进）

- 实验脚本（`experiments/`）没有任何 token 上限；2026-10-04 的大额消耗来自那里，不是本链路。建议加「本次最多 N token」开关。
- 诊断接口的调用频率限制与 `--allow-spend`。

## 附录 C：与上一版 SPEC 的差异（2026-10-10 评审后）

| 项 | 上一版 | 本版 |
|---|---|---|
| 上下文用途 | 只修正识别，不让模型理解会话 | 如实告诉模型这是上下文，不约束用法，靠观察调（D4） |

| 模型行为约束 | 「不回答、不评论、不整理」 | 基础指令仍是中继；其余不预设 |
