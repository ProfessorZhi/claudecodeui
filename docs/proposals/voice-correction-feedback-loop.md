# 语音输入：纠正闭环与持续学习 Proposal

状态：Proposal / 待评审

关系：

- 建立在 `docs/proposals/voice-identifier-repair-and-temporal-compression.md`（确定性标识符修复，已出货为 `src/shared/identifierRepair.ts` + `projectIdentifiers.ts`）之上；本文不改它的护栏，只扩它的**词源**并补上**用户纠正 → 学习 → 复用**这条回路。

## 1. 摘要

用户（yale）的输入有三个特征：**中英混杂是常态，标识符密度高，且长尾极重**。现网的修复只认「项目文件名」，而历史显示它只能覆盖用户实际说出的标识符的一小部分；真正能覆盖的词源是**当前会话上下文**与**用户自己说过的词**。因此方案是：

1. **扩词源**：会话上下文（助手刚说过的、工具名、涉及的文件）+ 项目索引（文件、task / goal / ADR 编号、分支、脚本）+ 用户词典（纠正沉淀）。
2. **纠正要近乎零成本**：点一个词 → 候选 + 自由编辑 + 听这一段原音；发送时的**普通手改**也被学到，不需要用户额外操作。
3. **学到的立即生效**：同一份草稿里同样的错词当场全部改过来（可撤销），下一段识别结果立即应用，手机与 PC 共用同一份词典。
4. **闭环可量**：重复纠正率、自动修复被还原率、标识符存活率，三个数在本地可读。

识别后的重打分已有一轮小规模试点读数（§5.7，`experiments/voice-context-asr/RESULT-v2.md`）：**形态类错误可以静默修复，音近类（`key` → `quay`）只能下划线 + 候选**，因为音近度无法区分同音陷阱。

**目标按「对 Claude Code 的影响」重定（2026-10-06，用户的判断）**：形态类错误（`fan in`、`Cloud CLI`）和口语写法（`AC 零零二`、`provider 下划线 models`）几乎不影响 Claude Code 的后续处理，**属于可容忍错误**，不再是主战场；要消灭的是**误听成别的词 / 别的对象**的错（`key` 对 `quay`、`Cloth Jeddik` 对 `claude-fjdac`、把 task 名说成一串不相干的词）。真实流回放（§5.8）显示：形态类已能找到 74%，**误听类只有 9%**——下一步集中在它上面。

**识别引擎与架构（第五、六轮读数，§5.9）**：本地 SenseVoice 作为默认识别器——比 Omni 快约 60 倍、不上传音频、**提供词级置信度**（Omni 没有）；准确率不优于 Omni（有害错误残留 9–10% 对 6.7%），所以 Omni 保留为按需的云端「再听一遍」。**书面化改写从识别里拆出来**，放在用户确认转写之后显式触发。**候选打分用 CTC 声学似然 + 音近**，用户确认过的「听到的写法」作为**声学别名**同时进入候选打分。

先量后做：**阶段 0 只加一路被动采集（识别原文 → 自动修复后 → 最终发送文本）**，因为目前没有任何一条真实的「听错 → 改对」配对数据（见 §8）。

## 2. 证据：用户输入的特点

数据来源：`~/.claude/projects/` 下 claudecodeui / quay / quay-fleet / cantus 四个项目的会话。7,022 条 user 记录里，约 5,300 条是 quay 驱动注入的提示词（选任务、worker、各类 judge）、续接摘要、任务通知，**全部剔除**；剩下 1,718 条人写的输入，去掉粘贴块后 **1,679 条**入样（claudecodeui 1,314 / quay 292 / quay-fleet 77 / cantus 35）。脚本在 `/tmp/vk/`，不入库。

### 2.1 形态

| 指标 | 读数 |
|---|---|
| 长度（字符）p10 / p25 / **p50** / p75 / p90 | 8 / 20 / **42** / 101 / 218 |
| ≤ 10 字 / ≤ 40 字 / ≤ 80 字 / ≤ 160 字 | 12% / 48% / 69% / 86% |
| 中英混杂 / 纯中文 / 纯英文 | **71%** / 26% / 3% |
| 混杂句里拉丁字符占比（中位） | 47% |
| 一条里的中↔英切换次数（中位 / 均值 / p90） | 4 / 9 / 17 |
| 含 ≥ 1 个标识符形 token / ≥ 3 个 | **57.5%** / 22% |
| 每条标识符形 token（均值） | 3.2 |

标识符形 token 的构成（不含纯数字类杂项）：缩写 829、kebab 816（task 名、CLI、分支）、路径 / 文件名 623、camelCase / PascalCase 489、snake_case / ENV 222、编号引用（`AC-103`、`GOAL-013`）213。

### 2.2 内容

- **短指令占大头**：「检查进展。」28 次、「同意。」18、「继续。」14、「再次检查。」9、「把 3001 拉起来。」6、「创建 quay task 。」4……这类句子没有标识符，识别一般不出错，**但正是它们让「每次按键一个请求」划算与否**——与上一份 proposal 的 10 秒计费下限一致，这里不重复。
- **长句是「动作 + 对象 + 指称」**：「用 SendMessage 和会话 `archguard 架构语义映射` 讨论……」「检查 GOAL-017 之前的实现……」。对象几乎都是**刚在上文出现过**的名字。
- **最高频词本身就是生僻英文**：`quay` 单词 358 次（另有 `Quay` 17）、`needs-human` 103、`CloudCLI` 88、`fan-in` 46、`SendMessage` 44、`meta-cc`、`archguard`。它们不是词典词，ASR 没有先验。（它们**会被听错**是推断，不是对真实录音的测量，见 §8。）

### 2.3 长尾

1,394 个不同的标识符形词型，其中：

| 取头部 N 个词型 | 覆盖的出现次数 |
|---|---|
| 10 | 16.6% |
| 100 | 38.5% |
| 500 | 66.8% |
| 1000 | 85.4% |

**头部很短、尾巴很长**：一张手写的热词表覆盖不了多少，必须是「随用随长」的机制。

### 2.4 哪个词源覆盖得了（按时间顺序模拟，每个 token 只能用它之前已有的东西）

对 2,696 个标识符形 token：

| 词源 | 覆盖 |
|---|---|
| 项目索引（文件名 + task / goal / ADR 名 + 分支 + package 脚本） | **24.1%** |
| 本会话此前的助手输出 / 工具输入 / 工具结果 | **46.1%** |
| 用户在此前任意会话说过的词 | **49.6%** |
| 会话上下文 ∪ 项目索引 | 57.7% |
| 三者之并 | **72.0%** |
| 都不在 | 28.0% |

按时间十分位看，「三者之并」稳定在 58%–84%，**没有随时间单调上升**——说明用户词典不是一次性喂饱的，新名字一直在冒出来（新 task、新 goal），这是持续学习必要的原因。

读法要点：

- 现网 `projectIdentifiers.ts` 只取**文件名**；表里的 24.1% 还含了 task / goal / 分支 / 脚本，所以现网实际覆盖**低于**它。
- 会话上下文是单一最大词源，且天然符合语音场景：用户读到助手刚写的名字再念出来。
- 28% 的「都不在」里有一半是 `AC-190` 这类带数字的编号、版本号、IP、散字母；它们要靠**格式规则**（编号模板），不是词表。

## 3. 对设计的推论

| 观察 | 推论 |
|---|---|
| 71% 混杂、切换中位 4 次 | 修复必须对「一句里散落多处」成立，不能按整句判断；判据要逐 token 且可机械验证 |
| 头部短、尾部长 | 词典要从使用里长，不能靠预置 |
| 会话上下文覆盖最大 | 词源第一优先级是**正在写的这个会话**，不是静态索引 |
| 用户词典能再覆盖约一半 | 纠正只改一次，下一次必须自动对 |
| ASR 适配器不吃提示词 | 只能在文本层做；纠正对必须是「听到什么 → 想说什么」的**文本映射** |
| S1 实验：自由改写伤人，替换表 + 校验可行 | 学到的东西是**替换规则**，不是让模型重写 |
| 手机是主要设备之一 | 纠正动作必须单手可完成；词典必须跨设备 |
| 形态 / 口语写法类错误几乎不影响 Claude Code（用户判断，待 E4 校准） | 它们用确定性规则尽力而为，**不进主指标**；主指标改为「有害错误率」 |
| 回放：60% 的词在语音流里只出现一次、38% 的错误是该词第一次出现 | 学习只能压**斜率**；**水平**靠词源与规则；向用户表述时不能承诺「越用越完美」 |

## 5. 方案

### 5.1 数据流

> **识别引擎已改为本地 SenseVoice（§5.9）**：`音频 ─(VAD 切段)→ 本地 SenseVoice → {text, 每个 token 的置信度与时间}`。下面的 L0–L3 在它的输出上工作；L2c 的「标出」除音近外还使用**置信度**，候选来自**音近 + CTC 声学似然**；书面化改写不在这条链里，见 §5.9「改写拆出」。

```
音频 ─ASR→ raw ─L0 规范化→ ─L1 学到的映射→ ─L2 候选模糊匹配→ ─(L3 替换表，可选)→ shown
                                 ▲                 ▲
                         用户词典(heard→meant)   词源：会话上下文 ∪ 项目索引 ∪ 词典 canonical
shown ──用户点词 / 手改──▶ 纠正事件 ──▶ 用户词典（写入）
                                         └──▶ 立即回改本草稿里的同串
```

| 层 | 做什么 | 判据 | 成本 |
|---|---|---|---|
| L0 | 大小写、`use voice input` → `useVoiceInput`（压扁后与候选精确相等） | 已出货 | 0 |
| **L1（新）** | 用户词典里 `heard → meant` 的**精确**映射（规范化后相等） | 这对映射被用户亲手确认过，所以不设相似度阈值 | 0 |
| L2a（新） | **形态修复**：窗口与词表条目只差空格 / 连字符 / 大小写（`fan in` → `fan-in`、`Cloud CLI` → `CloudCLI`、`Work Tree` → `worktree`） | 压扁后精确相等；**静默替换**（试点 S 类修复 96%，伤害 0） | 0 |
| L2b | 与候选集做编辑距离匹配（沿用四重护栏） | 已出货；**候选集扩充**见 5.2 | 0 |
| **L2c（新）** | **音近重打分**：1–4 词窗口与词表读音比音素距离，`0.45·音近 + 0.25·项目先验 + 0.20·近期 + 0.10·用户历史`，原词作为竞争候选（softmax，T = 0.1） | **只标记 + 给候选，不静默替换**——同音陷阱（`API key`）上它必然替换（试点 6/7），见 5.7 | 0 |
| L3（可选，默认关） | 仅对 L2c 标出的窗口，让模型在**闭集**（候选编号 + 「保持原样」）里选；**机械护栏：候选必须是词表词**。**1B–7B 级模型不可自动替换**（改坏 62–74% 的正确 token，陷阱 100%）；27B 级改坏 13%，仍不达标 | 第四轮：没有一个臂满足「改坏 ≤ 2%、陷阱 ≤ 10%」；只能用于「标出供确认」 | 约 ¥0.0001（小模型）至更高（27B），p50 约 0.75–1.5 s |

L1 排在 L2 前面：用户确认过的比启发式可信。L1 与 L2 冲突（同一个 token 两个答案）时取 L1，并计入「冲突」读数。

### 5.2 词源（扩充 L2 的候选集；全是纯函数，延迟为 0）

> **按回放读数（§5.8）重排优先级**：U（用户发过的词）找到 41%、独家提供 32%；C（会话词）对 U 已有的词几乎没有独家贡献（2%），价值在**新词**；P（项目文件 / task 名）对短口述几乎无贡献（668 个靶词里 23 个，命中 1 个）。下面的编号只是列举，不是优先级。

1. **会话上下文**：当前会话最近 N 轮的助手文本、tool_use 的入参、tool_result 的头部里的标识符形 token（沿用 §2.4 的切词规则）。每个助手回合结束时增量更新。
2. **项目索引**：文件名 + 裸符号名（现有）；再加 `tasks/`、`goals/`、`adr/` 下的文件名（用户常念 `GOAL-013`、`gap-…` 这类名字）、本地分支名、`package.json` 的 scripts 与依赖。
3. **编号模板**：`AC-\d+`、`GOAL-\d+`、`ADR-\d+` 这类编号不进词表，用模板 + 项目里已存在的编号集合校验（听成 `AC 一零三` / `ac103` → `AC-103`）。
4. **用户词典的 canonical**：自己说过 / 纠正过的名字。**U 是最大也最便宜的一源：用户每条发出的消息里的标识符形 token 自动进词典（不需要任何纠正动作），安装时再从历史会话导入做冷启动。**
5. **口语模板（L2a，确定性）**：「下划线」→ `_`；`AC 零零二` → `AC-002`（前缀取自词典里已知的引用形实体，不写死）。回放里引用类 1 → 50 / 76，是最大的单项收益；但它修的是**可容忍类**，所以优先级低于误听类。

每条候选带来源标签，纠正面板里按「词典 > 会话 > 项目」排序展示。

### 5.3 纠正入口（本方案的体验核心）

目标：把「发现错词 → 改对 → 以后不再错」压到**一次点按**。

> 交互形态参考了一份外部的 `VoicePromptEditor` 示例（Lexical 实现的识别后编辑器，2026-10-06 评审）。**借用它的交互约定与 span 数据模型，不借用它的实现**，边界见本节末「借用与重写」，参考代码见 §10。

#### 5.3.1 标记：三档，不只靠颜色

标记作用在输入框里的**语音来源文字**上；其余文字不加标记。三档在形状上可区分（不依赖颜色），并带可读的无障碍名称：

| 档 | 含义 | 样式 | 点开后 |
|---|---|---|---|
| `fixed` | L2a / L1 静默修复过的 token | 淡实线下划线 | 「还原」——还原就是一条反馈：这次自动修复错了 |
| `suggest` | L2c 音近 / 低置信窗口，**有候选** | 虚线下划线 | 候选并列（当前词也在其中），点选即替换 |
| `unknown` | 标识符形、含拉丁字母 / 数字，但**没有任何候选命中**（「可能听错」） | 点线下划线 | 只有自由编辑 + 保留 + 听原音 |

- **数量上限**：按「有害概率」（置信度、候选来源强度、是否标识符形）排序，输入框内默认最多标 3 处，其余折进底栏的「还有 N 处」。试点里陷阱句平均每句 0.86 个下划线，偏高，要靠用户词典里的反例（用户把 `quay` 改回 `key`）压下去；上限只是兜底。
- **标记的理由由机械生成**，不让模型写：`词典：quay` / `会话里刚出现 SendMessage` / `低置信` / `项目分支名`，直接取自候选的来源标签（§5.2）。**不向用户显示原始置信度数值**（没有校准，§5.7 第 5 点），也不用它决定下划线强弱；下划线档位与「是否替换」是两个独立开关。
- **置信度高 ≠ 没有歧义**：同音词和项目名即使识别置信度高也可能需要确认，所以 `suggest` 的判据是「候选与音近」，不是「置信度低」。

#### 5.3.2 词级浮层（点词弹出，锚定在词旁）

不是常驻面板，不增加输入框高度；Esc / 点外部 / 换词关闭；非模态（不抢走输入框焦点之外的东西）。内容自上而下：

1. **当前词 + 理由**（一行）。
2. **候选 3–5 个**：来源标签 + 编辑距离 / 声学得分最近优先，排序「词典 > 会话 > 项目」；第一项标「建议」。**当前（原始）词始终作为一个候选出现**，选它 = 「保留原词」。
3. **自由编辑框**（预填当前词）+「替换」。
4. **▶ 听这一段**：词级回放（§5.3.5），复用 `VoiceClipButton` 的轨道与播放器，**不新建播放器**。
5. **「保留原词」是一等操作，不是「关闭」**：它产生一条显式事件（`op: 'keep'`），是同音陷阱的**反例**，写入词典条目的 `reverts`（§5.4）。

浮层里**不放**「记住」「范围」「整理」：

- 「记住（本项目 ▾）」放在选完之后的提示里（§5.3.3）。
- **「整理」是整份草稿的操作，不属于单个词**，放在底栏（§5.3.4）。（旧稿把它列在点词弹层里，已更正。）

#### 5.3.3 选定之后：同串回改与「记住」

- 提交一条纠正时，同一份草稿里规范化后相同的 `heard` 全部改掉；**与编辑器历史合并成一步**，所以一次「撤销」回到纠正前。
- 一条不抢焦点的提示（输入框下方，几秒后淡出）：「已改 3 处 `cloud cli → CloudCLI`　撤销　·　记住（本项目 ▾）」。「记住」默认对标识符形的改动打开；范围默认本项目，可升到全局。
- 弹层不再为这些加控件，保持紧凑。

#### 5.3.4 底栏（语音来源文字存在时）

```
[▶ 整段回放] [整理]                 2 处待检查 · 点词修改      [发送 ↵]
```

- `▶ 整段回放` 即现有 `VoiceClipButton`；**`整理` 紧跟其后**（D3）。
- 「N 处待检查」是进入审阅的主入口：点击跳到下一处未处理的标记，等价于 Alt+Enter；**没有未处理标记时显示「没有待检查的词」且禁用**。有未确认标记时，`整理` 仍可点，tooltip 提示「还有 N 处可能听错」（不阻止，见 §5.9）。
- 移动端：回放 / 整理收成图标，文字缩写；这一行不换行（沿用现有 composer 底栏的几何约束）。

#### 5.3.5 词级回放

- 来源：SenseVoice 的 token 时间 `t`（§5.9）聚合成 span 的 `startMs / endMs`；回放区间 = `[startMs − 200, endMs + 300]`，到点自动停；换词、关闭浮层、卸载都停止。
- **没有时间戳时回退为整段回放，并在界面上标明「整段」**；没有音频时按钮禁用并写明「原音不可用」，**绝不合成或伪造原音**。
- **时间线必须一致**：`VoiceClipButton` 有「原始 / 裁剪后」两轨，`startMs / endMs` 必须以所播放那一轨的时间线为准；不一致时回退整段，而不是播错位置。
- 客户端路径（§5.10）同样提供 token 时间，帧粒度约 60 ms，满足上述 padding。

#### 5.3.6 移动端：候选条，而不是浮层

键盘弹出后，锚定在词旁的浮层会被挤出可视区，所以移动端改为：

- 点词 → 该词高亮，**键盘上方出现一条横向候选条**（候选 chip、「保留」、「▶」、「✎ 编辑」），样式类似系统键盘的联想条，单手可点；
- 词本身很小，**主入口是底栏的「N 处待检查」**（下一处），每个交互目标 ≥ 44 px；
- 「✎ 编辑」才展开自由输入框，并把候选条换成确认行。

#### 5.3.7 键盘与无障碍

| 操作 | 键 |
|---|---|
| 跳到下一处 / 上一处未处理标记 | Alt+Enter / Alt+Shift+Enter |
| 在浮层里选候选 | 数字键 1–5，或上下键 + Enter |
| 关闭浮层、焦点回输入框 | Esc |
| 保留原词 | 浮层内 K |

- 浮层用**非模态** `role="dialog"`，带 `aria-label`（含当前词）；替换后用 `aria-live="polite"` 播报「已替换为 quay」。
- 标记在无障碍树里要有名称（「可能听错：key，有 3 个候选」），不能只靠下划线样式。

#### 5.3.8 两类学习信号（信任级别不同）

| 通道 | 事件 | 信任 | 入库 |
|---|---|---|---|
| **显式操作**（浮层 / 候选条） | `candidate`、`custom`、`keep`、`revert-auto` | **强**：用户亲手确认 | 确认一次即可进词典（§5.4）；`keep` / `revert-auto` 记为反例 |
| **直接打字**（textarea 手改） | 不产生显式事件，只有文本变化 | **弱**：发送时由 token 对齐推断 | 必须满足下面 §5.3.9 的全部条件，否则进「待确认」 |

- 显式事件是 **append-only 的操作日志**，不是最终状态：撤销**不删除**已发生的事件（避免「撤销」把负样本也抹掉），但撤销会追加一条 `undo` 事件指向它。
- 在一个**标记范围内**直接打字，视为用户已处理该标记（标记转为已确认、元数据脱离，不声称保留精确溯源）；**不对用户新打的字重新扫描歧义**。

#### 5.3.9 发送后学习（零额外操作）

用户不点浮层、直接在 textarea 手改也算数。发送时把「语音来源区间」的文本与提交时对应区间做 token 级对齐，产生纠正候选；**只自动入库满足下列全部条件的**：

- 只涉及 1–3 个相邻 token；
- 改后是标识符形，或出现在 §5.2 的任一词源里；
- 改动幅度是「纠错」而不是「重写」（长度比、公共字符比有界）。

不满足的进「待确认」，在设置页的词典管理里一键采纳或忽略；不弹窗打断发送。入库后以不抢焦点的提示告知（「学到 2 条　撤销」）。

#### 5.3.10 发送：不拦截（待决 11）

**不做模态拦截，也不做「仍按原文发送」确认**（沿用「不强制纠正」）。底栏的「N 处待检查」本身就是提示。示例里「有高风险词时拦截发送」的做法与本方案冲突，**默认不采纳**；是否在「高风险且候选来自词典 / 会话」时加一次性的软确认，见 §9 待决 11，需要用户定。

#### 5.3.11 词典管理页（设置 → 语音）

按项目 / 全局分组；列出 `heard → meant`、命中次数、反例次数、最近使用；可删、可改范围、可导入项目索引里最常用的名字。

#### 5.3.12 借用与重写

| 借用（可照搬） | 重写（按本仓库实现） |
|---|---|
| **span 数据模型**：UTF-16 偏移、end 不含、已排序且不重叠、可选 `confidence / startMs / endMs / candidates / reason`，加 `kind`（§5.3.1） | **渲染层**：不用 Lexical。composer 是原生 `<textarea>`，用「透明 textarea + 底层镜像层画下划线」（§10.3）；不替换为富文本编辑器（IME、`@` 提及、斜杠命令、粘贴 / 附件、移动端键盘都会受影响） |
| **浮层定位算法**（优先放下方，放不下放上方，夹在容器内） | 组件拆分与模块落位（按 `frontend-module-standards`），文案走 i18n，不写死中文 |
| **词级回放区间**（前 200 ms、后 300 ms、到点停） | 回放并入现有 `VoiceClipButton`，不新建播放器 |
| **交互约定**：Esc、Alt+Enter、点外部关闭、保留原词、候选里含原词 | 词典、同串回改、「记住」、整理按钮、置信度来源：示例里**没有** |
| **事件分类**（显式操作 append-only，打字只触发变化通知） | 事件进 `voiceDebug` 同一出口，并增加 `segmentId`、`candidateRank`、`candidateSource` |

### 5.4 词典（存储与作用域）

条目：`{ canonical, heard[], scope: 'global' | project, source: 'edit' | 'send-diff' | 'import', hits, reverts, lastUsedAt }`。

- 服务端按用户存（与现有 voice 设置同一层级的持久化），客户端启动时拉取并在本地缓存；写入走后端接口，手机和 PC 因此共用同一份。
- **一条映射至少被确认一次才进 L1**；一条映射被还原的次数超过命中次数 → 自动降级为「待确认」。
- **别名不只做精确替换，还做声学别名（第六轮）**：每条被确认的 `heard → canonical`，其 `heard` 写法分词后作为该 canonical 的**额外读法**进入 CTC 候选打分（取各读法的最大似然）。同一个词换一种误听写法再出现时，有害错误的前 15 位候选召回 50% → 87%（n = 30，合成语音下很可能被高估，需真实录音复核）；它没有挤占识别对的 token（排第一的仅别名候选 0 / 59）。**精确替换（L1）本身对有害错误的残留只减少约 12%**，所以别名的主要价值是喂给候选打分，不是自动改写。
- 词典条目**不含** provider 密钥，不含整句转写；`heard`、`canonical` 都是短 token，仍按「用户个人数据」处理（可导出、可清空）。
- 实现按后端 / 前端各自的模块标准落位；本文不规定文件名。

### 5.5 缩短闭环：把每一步的延迟都压到「当场可见」

| 环节 | 目标 |
|---|---|
| ASR 返回 → 修复 → 显示 | 与现网一致：同步纯函数，不增加请求，不增加延迟 |
| 点一个候选 → 草稿更新 | 一帧内（本地状态） |
| 纠正 → 同草稿内同串回改 | 同一次交互内完成 |
| 纠正 → 下一段识别生效 | 本地词典即时写入；服务端落库异步，失败不阻塞 |
| 纠正 → 另一台设备生效 | 下次拉取（打开页面 / 回前台时） |
| 助手回合结束 → 会话词源更新 | 回合结束事件触发，下一次录音即可用 |

### 5.6 度量（本地可读，进 `voiceDebug` 同一出口）

| 读数 | 含义 | 目标方向 |
|---|---|---|
| **有害错误率（主指标）** | 误听成别的词 / 对象的错误 token ÷ 标识符 token；「可容忍类」（形态、口语写法）不计入 | 持续下降；先由 E4 的判定口径校准 |
| 修正负担 | 用户改动的字符数 / 该次语音输出的字符数 | 持续下降；**降为辅助指标**（它把可容忍类也算进去） |
| **重复纠正率** | 同一 `heard→meant` 第二次被手工纠正的比例 | 学到之后趋近 0；这是闭环有没有闭上的主读数 |
| 自动修复被还原率 | L1/L2/L3 自动改动里被用户还原的比例 | 有上限（建议先定 ≤ 2%，由阶段 0 数据校准）；超限则对应层降级 |
| 标识符存活率 | `identifierFidelity`，沿用 | 在离线回放集上与基线并列报告，不只看 CER（CER 对标识符损坏失明，上一份 proposal 已证） |
| 词典命中数 / 新增数 | 学习是否在进行 | 新增随时间放缓 |

这张表里阶段 0 能从本机数据离线读出的部分（段数 / 标签数 / 手改比例 / 错词形态 / AUROC / 标记数与召回 / 自动修复被还原率），由 `scripts/voice-phase0-report.mjs` 直接从语音数据目录算出并回答「阶段 0 是否达标」：

```
node scripts/voice-phase0-report.mjs [--dir <voice-data 目录>] [--json]
```

它是**只读**的：不联网、不改记录，输出里只有计数、比例和阈值，**不含任何原文、`heard`/`final` 或音频内容**。退出码 `0` 达标（含标识符段 ≥ 100 且有标签段 ≥ 30）、`2` 未达标、`1` 读数无法得出（目录不存在 / 记录损坏）——样本不足时诚实输出 `n/a`，不凑数。「声学别名的真实增益」需要 CTC 打分管线，**不在该脚本内计算**，脚本只把它列为「需离线实验」并指向 `experiments/voice-index-loop/RESULT-v6.md`。

### 5.7 试点读数：识别之后的歧义检测（2026-10-05）

完整记录与局限见 `experiments/voice-context-asr/RESULT-v2.md`，预注册稿 `PREREG-v2.md`。**先说偏差：`PREREG-v2.md` 与脚本没有在取数前提交。** 取数前一条线已经停掉：把上下文送进 ASR（omni 上）在 A2（`5f4b7a90` / `a73c5c0d`）里已被否决，本试点只测「识别之后」。

设置：74 条合成片段（靶词 12 个，`quay` 分 /kiː/、/kweɪ/ 两种拼写发音；另有 8 条陷阱句、6 条中性句、4 条多靶句）与 20 条真实录音，经 OpenRouter 的 Qwen3-ASR 1.7B / 0.6B 转写（无上下文，约 ¥0.006），再过 D1（音素 × 词表重打分）与小模型；词表条件含「删掉靶词」「换成错项目」两个负对照。

Qwen3-ASR 1.7B、阈值 0.7（S = 只差空格 / 连字符 / 大小写，n = 26；M = 误听，n = 36）：

| 臂 | 修复 S | 修复 M | 陷阱句被替换 | 中性句被改 |
|---|---|---|---|---|
| 现网 `repairIdentifiers`（词表候选） | 54% | 6% | 0/7 | 0/7 |
| D1 音近 × 词表 | 96% | 83% | **6/7** | 0/7 |
| ministral-3b + 词表护栏 | 77% | 61% | 0/7 | 0/7 |
| **组合：L2a 形态修复 + L3 护栏** | **96%** | **69%** | 0/7 | 0/7 |

结论与对本方案的含义：

1. **词表驱动是对的，且便宜**：词表里删掉靶词、或换成错项目的词表，修复率都是 0（方法在用词表，不在编造）。
2. **形态类可以静默修复**（L2a）。现网的编辑距离修复对这一类只有 54%，对误听类只有 6%。
3. **音近类不能静默替换**：`key` 与 `quay` 音近度为 1，音素 + 先验分不开「`API key`」和 `quay`（预测过，实测 6/7 被改）。所以 L2c 的输出是**下划线 + 候选**，替换由用户点选；每一次点选就是一条 `heard → meant`，也是 5.4 词典的数据来源。
4. **小模型只能放在机械护栏之后**：`llama-3.2-1b / 3b` 的 JSON 解析率 19–50%，不可用；`ministral-3b` 解析率 99%，但不带护栏会把「服务」改成 `restart`（中性句 3/7 被改）；护栏 = 候选必须是词表词。
5. **小模型给的概率不可校准**：真 `quay` 与陷阱里 `key` 的 p(quay) 分布重叠（0.1–0.3 对 0.0–0.3），**不能用它决定下划线的强弱**；下划线与「是否替换」是两个独立开关。
6. **同音陷阱要靠用户词典里的反例学**（用户把 `quay` 改回 `key` 的次数），不是靠更好的音近度。
7. **真实录音里的直接证据**：用户的 `quay`（/kiː/）被 Qwen3-ASR 写成 `Key`（「使用 Key 的其他项目」「Key 的 skill 和 MCP」）；同时出现一个误伤形态：「Cloud Code」被 D1 改成 `claudecodeui`（词表里没有 `Claude Code`）。**词表必须包含用户常说的普通专名，否则音近匹配会把它们拉向相近的项目词。**

局限（试点 n 很小）：M 类 36、陷阱 7、中性 7，陷阱 0/7 的 Wilson 95% 上界约 35%，只能说「这一批没有误伤」；合成音频每个模板一个音色；词表只有 12 + 6 个词；音近用 CMUdict + double-metaphone 骨架，没有真正的 g2p。

### 5.8 真实流回放：标出、找到备选、自动维护、「越来越准」（2026-10-06）

完整记录见 `experiments/voice-index-loop/RESULT-v3.md`（预注册稿 `PREREG-v3.md` 在取数前提交）。把用户四个项目的真实输入（入选 468 条、凭据样式的在送出前剔除）按时间顺序回放：用 TTS 念出来、Qwen3-ASR 识别、词源只能用「当时已有」的（项目 git 快照 / 会话前 8 回合 / 此前发过的消息）。**真实文字 + 合成语音**，75% 的靶 token 被识别错，所以量的是文本层机制，不是识别器。

| 读数 | 结果 |
|---|---|
| 找到（静默修复，或标出且前 3 位备选含正确答案）：现网 → P+C+U | **0% → 43%**；形态类 **74%**，**误听类 9%** |
| 来源（找到的错误里） | U 提供 97%、独家 32%；C 提供 68%、独家 2%；**P 提供 0.5%**（668 个靶词里 23 个在项目快照里） |
| 任何词源都够不到的真新词 | 10% |
| 按形态找到 | camelCase 83%、二段 kebab 48%、缩写 43%；**编号 1%、三段以上 task 名 3%、snake_case 6%**（口语写法：`AC 零零二`、`下划线`） |
| 维护机制（晋升 / 降级 / 负例上下文 / 冲突 / 归档 / 墓碑 / 会话衰减） | 10 条断言（每条带能变红的负对照）通过；回放中 0 次不变量违反 |
| 「越来越准」 | 总负担：现网 75% → 仅词源 46.1% → **词源 + 学习 40.6%**；末 / 首三分之一比值 0.87–0.91（判据 ≤ 0.8，**不通过**） |
| 斜率为什么小 | 221 个词里 60% 只出现 1 次；**38% 的错误是该词的第一次出现**；同一个词平均 2.2 种误听写法 |
| 取数后探索（非预注册） | 口语模板（`下划线` → `_`，`AC 零零二` → `AC-002`）把总负担 46.1% → 35.9%；会话词算「先验」反而增加无关改动；「学到的误听写法」几乎无增益 |

**对本方案的含义**

1. **误听类（有害）是主战场**，现在只找到 9%。形态类与口语写法类（可容忍）用确定性规则尽力而为，不再追求。
2. **U 自动入库 + 历史导入**是最便宜、最大的一笔；**P 不是主力词源**（至少对短口述；长消息里的文件 / task 名被本轮排除了，P 的贡献可能被低估，见局限）。
3. **「越来越准」拆成两个承诺**：*水平*（词源 + 规则，几周内到位）与*斜率*（学习，较慢，受「大量词只出现一次」限制）。对用户的话是「你说过的词、助手提到的词、常见口语写法会越来越稳」，不是「越用越完美」。
4. **缺陷（取数后发现，已修）**：别名键用了丢掉中文字符的 `normKey`（`AC 零零二` 与 `AC 零零五` 撞成同一个键）；`wordPron` 遇到 `constructor` 这类词原型污染。实现时别名键必须保留 CJK。

局限：真实文字 + 合成语音；一位用户；理想用户总能发现并纠正；只入选 ≤ 160 字、不含路径的短消息；候选分桶是否漏候选未核对。

**第四轮：以「有害错误」为目标（2026-10-06，`RESULT-v4.md`，预注册 `PREREG-v4.md` 在新取数前提交）**

| 读数 | 结果 |
|---|---|
| 「可容忍」的判断是否成立 | **成立**：形态 / 口语写法类的 313 个错误里 98% 被判定器判为「同一对象 / 可从上下文恢复」；与独立盲评子代理在「可容忍 / 有害」上一致率 85%（三选一一致率只有 52%，只用二分） |
| 有害错误有多少 | 57 / 501，**占全部错误 11%、占标识符 token 8.5%**；51 个可达（U 45、C 37、P 1）；38 个识别结果含拉丁字母、19 个被写成纯汉字 |
| 能不能找回 | 放宽音近线（0.6）、每窗口 15 个候选，正确答案只在其中 **25%（14 / 57）**；**上限由候选召回决定，不是选择器** |
| 小模型闭集选择（只许回候选编号） | `ministral-3b`、`qwen-2.5-7b` 把**本来对的标识符改坏 62–74%**，`API key` 陷阱句 100% 被改成 `quay`；`qwen3.8-27b` 改坏 13%、陷阱 1/7，修好 14 个（正好是上限）；**没有一个臂通过「改坏 ≤ 2%、陷阱 ≤ 10%」** |
| P（项目文件 / task 名）在长消息里 | 切段后 461 段、1,125 个靶 token：P 提供找到的 **7%（独家 1%）**，U 提供 89%（独家 51%），C 48%（独家 6%）；任何词源都够不到的新词 38%。P 的快照只取已提交的树，7% 是下限，但不是主力 |
| 以有害错误计的收敛 | 学习让有害错误 53 → 41（约 −23%）；但无学习的臂首末比值也是 0.69，**斜率不能归因于学习**；每窗口只有 1–10 个，噪声大于信号；历史导入对有害错误无可测价值 |
| 中文谐音（探索，非预注册） | 19 个纯汉字的有害错误（`fan-in` →「翻译 / 翻印」，`OOM` →「梦 / 墓」）：汉字转拼音再近似成英文音素匹配，**`fan-in` 的 10 个全部排第一**，字母缩写类（`OOM`、`e2e`、`PM`）找不到；加上它上限约 25% → 42% |

**对本方案的修正**

1. **不追求覆盖率**：有害错误只占约 8.5% 的标识符，目标是**让这一小撮不被漏掉**——下划线 + 候选，由用户一键确认，而不是静默替换。
2. **L3（小模型）不能自动替换**：1B–7B 级模型太爱改；只能放在「标出后供确认」的位置，或用 27B 级模型并配严格的保持原样倾向，且需要 ≥ 40 条陷阱样本再定。第 5.1 表里 L3 的「只有 ministral-3b 勉强可用」作废。
3. **抬找回上限靠候选召回**：中文谐音匹配（拼音 → 音素）与字母缩写的读法，比换更强的选择器有效；在更多词上预注册后再测（目前只有 `fan-in` 一个词有证据）。
4. **U 是第一词源，P 降为补充**，不值得单独维护复杂的项目索引；历史导入只对可容忍的形态类有价值。
5. **「越来越准」对有害错误**：学习只带来约 20% 的减少；承诺应落在「你说过的词、助手提到的词会稳」，不是「越来越接近完美」。

局限（第四轮）：E4 / E5 用的是第三轮已被看过的识别文本，不是盲的；判定器是模型且偏严，三选一不可靠；陷阱句只有 7 + 7 条；仍是真实文字 + 合成语音（80% 的靶 token 被识别错，高于真实口述）；P 快照有缺陷。

### 5.9 本地识别器、置信度、CTC 候选与改写拆出（第五、六轮，2026-10-06）

记录：`experiments/voice-index-loop/RESULT-v5.md`、`RESULT-v6.md`（预注册稿 `PREREG-v5.md`、`PREREG-v6.md` 都在读数之前提交）。语料沿用 §5.8：466 段真实消息的合成语音，判定口径是「有害错误」。

**1. 引擎：本地 SenseVoice-Small（sherpa-onnx int8）对 Omni**

| | Qwen3-ASR 1.7B | SenseVoice（本地） | Omni transcript | Omni instruction（书面化） |
|---|---|---|---|---|
| 标识符逐字写对 | 25% | 21% | 32% | 34% |
| **处理后剩余有害错误（占标识符）** | 7.9% | **9.6–10.0%** | **6.7%** | 9.7% |
| 延迟 | 受网络影响 | **解码 p50 0.11–0.13 s（实时因子 0.019）** | **p50 6.5 s、p90 15.4 s** | 同左 |
| 词级置信度 | 无 | **有** | 无 | 无 |

- **结论：「更快」成立，「更准」不成立。** SenseVoice 约快 60 倍（两者不是同一种测量：本机 CPU 对网络调用），但有害错误残留比 Omni transcript 高约 3pp。
- Omni 的书面化改写把有害错误从 7.3% 升到 10.0%——改写会把一个标识符改成另一个对象。**这支持把改写拆出来**。

**2. 置信度（Omni 没有的信号）**

- 区域级 AUROC：有害错误 **0.93**、全部错误 0.86。θ = 0.6：80% 的有害错误落在低置信标记里；**只标含拉丁字母 / 数字的段**：74%，2.4 个标记 / 100 字符。θ = 0.5：62%，1.7 个。
- **「每 100 字符 1 个标记」的预算达不到**；要靠只标含拉丁字母 / 数字的段、与候选信号合用（与音近取交集会把有害错误砍一半，不划算）和用户反馈来压噪声。
- 真实录音（20 条）里你的 `quay` 被写成 `key`，置信度 0.48 / 0.41，会被标出。

**3. CTC 候选（只给候选，不自动替换）**

- 在低置信窗口上，用词表候选的 CTC 似然给候选打分：有害错误前 15 位召回 **35%**（音近 19%，**取并 42%**）；全部错误 57%（音近 44%，取并 66%）。
- **CTC 分数不能用来自动替换**：假设本来就是贪心路径，候选的似然比恒为负；放宽阈值后修好的有害错误约为 0，却开始改坏识别对的 token。
- **候选的来源与类型**（第六轮，全部有害错误）：找到的 24 个里，仅「你发过的词」9、「你发过的词 + 会话词」11、仅会话词 3、项目名 + 另两源 1，**仅项目名 0**；已删除名字（墓碑）的候选只占 0.05%（保留标记即可）。
- **规模规则**：每窗口只取 200 个候选（近期优先 → 你发过的词按次数 → 其余），召回是全量的 92%，打分耗时降到约六分之一。

**4. 引擎实现：给 sherpa-onnx 打补丁**

- 上游的 SenseVoice 路径不返回置信度（`ys_log_probs` 为空）。补丁（约 185 行，`experiments/voice-index-loop/sherpa-patch/`）让 CTC 贪心解码器返回每个 token 的对数概率，并可选导出逐帧对数 softmax 矩阵（现在用环境变量开关，上游化应改为配置项）。
- 自写前端被退役：它与 sherpa 的转写只有 63% 逐字相同。真正的原因是**这个模型对极细微的输入差别非常敏感**（波形平移 1 个采样点，约 18% 的片段文本改变）。补丁版自己确定性（150 / 150），与 pip 版只在 0.8% 的 token 上不同，且几乎全在不确定的位置。
- **部署必须使用同一份构建产物**：同一段音频在不同编译产物上可能得到略有不同的文本与置信度。

**5. 改写拆出（架构）**

```
音频 ─VAD 切段→ 本地识别（逐字、带置信度）→ 文本层（静默修复可容忍类；有害类标出 + 候选）→ 输入框（用户确认 / 纠正）
                                                                                   │ 显式触发（按钮 / 语音命令）
                                                                                   ▼
                                                              文本改写（用确认过的文本 + 会话上下文 + 用户词典；可撤销）
```

- 逐字转写即时上屏；不需要书面化的短指令（占大头）完全不走改写；改写是一次纯文本调用（便宜、可换模型），基于**用户确认后的文本**，所以识别错误不会被改写放大。
- Omni 保留为「再听一遍」的云端高质量模式，而不是默认链路。
- **触发形式（D3）：一个按钮，紧跟在现有的音频回放按钮（`VoiceClipButton`）之后**，同属「这一次语音输入」的那一组控件。
  - **何时出现 / 可用**：当前输入框里有语音来源的文字、且不在录音或识别中；有未确认的下划线时按钮仍可点，但提示「还有 N 处可能听错」（不阻止）。
  - **点了之后**：把输入框里**当前（用户确认 / 纠正后）的文本**、会话上下文（最近几个助手回合里的标识符，沿用 §5.2 的会话词）、用户词典交给文本模型，按 E 组的整理规则输出书面化指令；结果**替换输入框文字**，并出现一个「撤销」（回到改写前的文本），不覆盖语音回放；失败时保留原文并给出可行动的错误。
  - **只做替换式整理**，沿用 S1 的约束：输出里的标识符必须出现在输入文本或词表里（机械校验），不允许引入新的对象名。
  - **隐私**：这一步会把输入框文字发给文本模型（云端或本地由设置决定）；不发送音频。按钮的 tooltip 说明这一点。
  - **不自动触发**：不因「建议整理」高亮，也不在发送前插入；用户不点就原样发送。

**局限**：真实文字 + 合成语音（逐字写对只有 21–34%，远低于真实口述）；一位用户；判定器是模型；声学别名的数字（n = 30）很可能被高估；E6 的 461 段只做了前端与速度；R3 的学习读数噪声大于信号（T2 对 T1 −12%，没达到预注册的 −15%）。

### 5.10 浏览器 / 手机本地识别（D2）

目标：识别器有**两条运行路径**——服务端（自托管主机，手机经服务端使用）与**客户端本地**（浏览器 / 手机，不经网络）；两条路径输出同一种结果 `{text, tokens[{tok, p, t}]}`，文本层、候选、别名、纠正入口不区分来源。

**要先测量、尚未验证的事实**（不预设可行）：

| 项 | 要回答的问题 | 备注 |
|---|---|---|
| 运行时 | SenseVoice-Small（229 MB int8）能否在浏览器经 WASM（sherpa-onnx 的 WebAssembly 构建或 onnxruntime-web）运行？iOS Safari / Android Chrome 都要 | 我知道 sherpa-onnx 有 WASM 构建，但对 SenseVoice 与本补丁是否可用**没有验证** |
| 速度 | 手机 / 浏览器单线程 WASM 的实时因子；是否仍能随 VAD 切段即时上屏 | 服务端 4 线程 CPU 的实时因子是 0.019，客户端预计慢一个数量级，**未测** |
| 体积与首次加载 | 模型不进应用包；首次下载、校验哈希、Cache API / OPFS 缓存、进度可见 | 沿用 `voice-kit` SPEC 的模型清单与缓存约束 |
| 置信度 | 补丁（逐帧 / token 对数概率）要进 WASM 构建；客户端与服务端在**置信度 ≥ 0.85 的 token 上**是否一致 | 这个模型对编译与浮点差别敏感（§5.9），两条路径的文本与置信度**不会逐字相同**，只能要求「在确定的位置一致、差别落在不确定的位置」 |
| 内存与发热 | 手机标签页内存上限、连续使用的电量 | `voice-kit` SPEC 的移动 Web 约束全部适用 |
| 回退 | 客户端不可用 / 太慢时回退到服务端；服务端不可用时只靠客户端 | 由设备能力探测与用户设置决定 |

**对设计的约束**：

- **文本层与词典必须与识别路径无关**：别名按文本存（`heard → canonical`）；声学别名里的「读法」是**分词后的 token 序列**，不依赖具体构建产物，所以两条路径可以共用同一份词典。
- ASR 适配器的能力声明增加：`runsAt: 'server' | 'client'`、`tokenConfidence`、`tokenTimestamps`、`modelVersion / buildId`（构建产物标识，进日志，便于定位「同一段音频在两条路径上读数不同」）。
- **隐私**：客户端路径下音频不离开设备；服务端路径下音频只发往用户自托管的服务端。两种情况下音频都不进云端请求（Omni 的「再听一遍」是用户显式选择的例外，要在界面上说明）。
- 客户端路径的 CTC 候选打分（要逐帧概率）放在客户端还是服务端：逐帧矩阵很大（约 100 帧 × 25 k），默认在**识别发生的那一端**算完再传 top-K 候选，而不是传矩阵。

**立项方式**：先做一个**客户端可行性探针**（不改产品）：在一台手机和一个桌面浏览器上跑 SenseVoice-Small 的 WASM 构建，读实时因子、内存、首次加载、置信度与服务端的一致性；探针过了再进阶段 0 的客户端适配器。

**探针已执行**（2026-10-06，`docs/experiments/2026-10-06-voice-client-asr-probe.md`）。路径选 **(b) onnxruntime-web 1.30.0 + 自写前端**（(a) sherpa-onnx 官方 WASM 未采用：要 emscripten，npm 包只有 nodejs 构建，release 无浏览器 ASR 预编译产物）；前端与项目自己的 `experiments/voice-index-loop/sv/svlib.py` 逐帧核对通过（fbank 410 帧逐位相等、LFR+CMVN `max|Δ| = 1.7e-5`）后才取数。预注册先提交（`experiments/voice-client-asr-probe/PREREG.md`，commit `7ea24479`）；数据集 60 条片段（共 532.7 s），真实 Chromium 里经 `window.__probe` 逐条取。实测：

- 读数：**实时因子 p90 = 0.1375**（桌面 Chromium、单线程 SIMD、宿主不加 COOP/COEP），阈值 ≤ 1.0 —— **T1 通过**（p50 = 0.1288，max = 0.1490）。
- 读数：**`--isolated`（COOP + COEP → 4 线程）实时因子 p90 = 0.0675**，相对单线程 **2.04×**；token 序列与文本两臂**逐条相同**，多线程只改速度不改结果。
- 读数：**二次打开（模型在 Cache API）到可识别 = 1.244 s**（`--isolated` 1.692 s），阈值 ≤ 10 s —— **T2 通过**；首次加载 2.377 s（其中模型下载 0.990 s、会话创建 1.124 s），模型 239 233 841 B，sha256 `c71f0ce0…`。
- 读数：**WASM 堆峰值 = 590.2 MB**（618 856 448 B），阈值 ≤ 1.5 GB —— **T3 通过**（`--isolated` 591.3 MB）。
- 读数：**置信度一致率 = 0.9706** —— 服务端 `p ≥ 0.85` 的 1903 个 token 里，客户端**同位置（同 `t`）同 token** 的有 1847 个，阈值 ≥ 95% —— **T4 通过**。
- 读数：**文本逐字相同 46 / 60 = 0.7667**；14 条差异里 9 条只差标点、5 条是邻位同音/形近字替换（`指/只`、`the/的`、`contextwind/contextwin`）—— 与本节「两条路径不逐字相同，只要求确定的位置一致」的预期一致。
- 读数：**移动视口 390×844 实时因子 p90 = 0.1552**、**4× CPU 节流下 p90 = 0.6262**（同机同批 60 条；恰为未节流的 4.03×，说明解码是 CPU 密集且近似线性）—— 两者都未触到 1.0，布局与解码互不干扰；**真机（iOS Safari / Android Chrome）判「待外部」**，由人 yale 补测，不折算为通过。
- 读数：**负控制** —— 空数组 → 0 token（如预期）；纯静音 2 s → 模型幻觉吐 2 个 token，且 `silenceIsCachedText = false`（不在本批任何输出里）—— 「静音必空」**不成立**，记录在案，但不影响判定。
- 读数：**宿主加 COOP/COEP 的代价** —— 实时因子再降 2.04×，代价是所有子资源须过 `require-corp`、`window.opener`/弹窗 OAuth 受影响、且**没有**「隔离失败自动退回单线程」的中间态。建议先按单线程（不加头）落 —— 0.1375 已满足阈值 —— 把头作为**可选部署开关**，在长片段 / 移动端被实测证明需要时再打开。

**结论**：桌面浏览器 T1–T4 四闸全过 = **go**；移动真机待外部。本节的其余「要测量」项（体积与首次加载、内存与发热、回退）中，体积/首次加载/内存已有读数，**发热与后台挂起未测**。

先量、后做；每阶段独立可发、可回退，且**上一阶段的读数决定下一阶段做不做**。

## 8. 未验证与局限（必须读）

1. **历史是「打字」不是「说话」。** 1,679 条输入里能看到输入法痕迹（如「创建 quay task 。」句号前有空格），它们是用户**想表达的内容**的代理，不是语音识别的输出。真实口述会更长、更多口头禅与自我更正（见 `docs/experiments/2026-10-04-voice-pause-split.md`），分布会不同。
2. **目前没有任何一条真实的「听错 → 改对」配对。** `~/.cloudcli/voice-capture/` 里只有 20 个音频文件，没有转写文本，更没有用户最终发送的文本。所以「`quay` 会被听成什么」「哪些错是音近」仍缺**成体系的**测量；§5.7 只有两条真实录音里的 `Key`，作方向性证据。阶段 0 就是为此存在。
3. **覆盖率是上界、且是启发式的。** token 切分规则把带数字的词也算作标识符形，有少量噪音（版本号、IP）；「用户词典 49.6%」只说明「说过」，实际能被学到的还要乘上「曾被听错」的比例，该比例未知。
4. **会话上下文的 46.1% 偏乐观于文本场景**：用户打字时也可能复制助手输出里的名字；语音场景下这个比例可能更低（念出来要靠记忆）。但它作为「该词源值得做」的证据方向没变。
5. **泛化性**：词表规模、项目命名习惯来自这位用户的三四个项目；其他用户的分布未知。
6. **候选集扩大会抬高假阳性。** 上一份 proposal 的护栏是在文件名候选（数千个）上调出来的；加入会话与编号词源后必须重测，阶段 1 的「误报为 0」是硬判据，不是期望。
7. **§5.7 的试点读数 n 很小且主要是合成音频**，且预注册稿未在取数前提交；小模型的概率不可校准，下划线强弱不能依赖它。
8. **「可容忍」是用户的判断**；第四轮用判定器与盲评子代理核对过（二分一致率 85%，规则可容忍的错误里 98% 被判为无害），但判定器是模型、口径是「编码 agent 能否指向该对象」，不等于真实的 Claude Code。若某些形态类错误其实会让 Claude Code 指错对象（例如两个 task 名只差一个连字符），它们要从「可容忍」里划出来。
9. **本地识别器的构建产物要固定**：SenseVoice 对极细微的数值差别敏感，同一段音频在不同的编译产物上可能得到略有不同的文本与置信度；服务端必须随应用交付同一份构建（含补丁），并在升级时重测。
10. **L1 是「用户亲手确认过」的精确映射，但同一个错词形可能对应不同的正确词**（`key` → `quay`，也可能真是 `key`）。因此 L1 对短的、普通英文词形的 `heard` 要额外限制（只在标识符形上下文或项目内启用），具体阈值由阶段 0 数据定，本文不拍。

### 10.2 手改后重映射 span（取代 Lexical 节点跟踪）

用公共前缀 / 后缀找出改动区间：改动之前的 span 不变，之后的按长度差平移，**与改动区间相交的 span 视为已处理并脱离**（§5.3.8）。

```ts
export function remapSpans(oldText: string, newText: string, spans: VoiceSpan[]) {
  const max = Math.min(oldText.length, newText.length);
  let p = 0;
  while (p < max && oldText[p] === newText[p]) p++;
  let q = 0;
  while (q < max - p && oldText[oldText.length - 1 - q] === newText[newText.length - 1 - q]) q++;
  const oldEnd = oldText.length - q;
  const delta = newText.length - oldText.length;
  const kept: VoiceSpan[] = [];
  const touched: string[] = [];
  for (const s of spans) {
    if (s.end <= p) kept.push(s);
    else if (s.start >= oldEnd) kept.push({ ...s, start: s.start + delta, end: s.end + delta });
    else touched.push(s.id);
  }
  return { spans: kept, touched };
}
```

已知边界：前缀恰好落在代理对（emoji）中间时偏移会差一位，实现时要回退到码点边界。

### 10.3 镜像层：在 `<textarea>` 上画下划线

镜像 div 与 textarea 使用**相同的字体、padding、换行与宽度**，文字透明、只画下划线；textarea 在上层且背景透明；滚动位置同步。

```tsx
function segments(text: string, spans: VoiceSpan[]) {
  const out: { text: string; span?: VoiceSpan }[] = [];
  let at = 0;
  for (const s of spans) {
    if (s.start > at) out.push({ text: text.slice(at, s.start) });
    out.push({ text: text.slice(s.start, s.end), span: s });
    at = s.end;
  }
  if (at < text.length) out.push({ text: text.slice(at) });
  return out;
}

export function UnderlineMirror({ text, spans, scrollTop }: {
  text: string; spans: VoiceSpan[]; scrollTop: number;
}) {
  return (
    <div className="voice-mirror" aria-hidden style={{ transform: `translateY(${-scrollTop}px)` }}>
      {segments(text, spans).map((seg, i) =>
        seg.span
          ? <span key={i} data-span-id={seg.span.id} className={`voice-mark voice-mark-${seg.span.kind}`}>{seg.text}</span>
          : <span key={i}>{seg.text}</span>)}
      {'\n'}{/* 末尾换行，保证与 textarea 高度一致 */}
    </div>
  );
}
```

### 10.4 浮层定位（纯函数）

```ts
type Box = { left: number; top: number; width: number; height: number };

export function placePopover(anchor: Box, container: Box, panel: { width: number; height: number }) {
  const gap = 9, pad = 8;
  const below = anchor.top + anchor.height - container.top + gap;
  const above = anchor.top - container.top - panel.height - gap;
  const maxTop = container.height - panel.height - pad;
  const top = Math.max(pad, Math.min(below <= maxTop ? below : above, maxTop));
  const left = Math.max(pad, Math.min(anchor.left - container.left, container.width - panel.width - pad));
  return { left, top };
}
```

### 10.5 词级回放区间（纯函数，并入 `VoiceClipButton`）

```ts
export function clipRange(span: Pick<VoiceSpan, 'startMs' | 'endMs'>, trackDurationMs: number) {
  if (span.startMs === undefined || span.endMs === undefined) {
    return { startMs: 0, endMs: trackDurationMs, scope: 'whole' as const };
  }
  return {
    startMs: Math.max(0, span.startMs - 200),
    endMs: Math.min(trackDurationMs, span.endMs + 300),
    scope: 'span' as const,
  };
}
// 播放：player.currentTime = startMs / 1000；在 timeupdate 里 currentTime >= endMs / 1000 时 pause()
```

`scope: 'whole'` 时界面标明「整段」；时间线与所播轨不一致时也走这条回退（§5.3.5）。

### 10.6 选定之后：同串回改与一步撤销

```ts
export function applyCorrection(text: string, spans: VoiceSpan[], spanId: string, after: string) {
  const target = spans.find(s => s.id === spanId);
  if (!target) return { text, spans, changed: 0 };
  const key = (v: string) => v.trim().toLowerCase();
  const heard = key(text.slice(target.start, target.end));
  // 从右往左替换，避免前面的替换改变后面的偏移
  const hits = spans.filter(s => key(text.slice(s.start, s.end)) === heard).sort((a, b) => b.start - a.start);
  let next = text;
  for (const s of hits) next = next.slice(0, s.start) + after + next.slice(s.end);
  return { text: next, changed: hits.length /* 重算 spans：先全部 remap，再标记已处理 */ };
}
```

整个 `applyCorrection` 作为**一次**对输入框状态的写入（只推一个历史点），这样「撤销」一次回到纠正前（§5.3.3）。注意：key 比较要保留 CJK 字符（§5.8 第 4 点：丢掉中文的归一化会让 `AC 零零二` 与 `AC 零零五` 撞键）。
