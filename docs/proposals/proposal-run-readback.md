# Provider Run readback and durable terminal receipts

## Problem Statement
v1.39.0 really wires run_get through readTools.runGet, but body-table placeholder metadata obscures this. app runId is minted by chatRunRegistry, while native provider session IDs are stored by sessionsDb. The registry/events/queue relation are process-local with five-minute terminal retention. Native transcripts and audit digests do not persist the app runId. Immediate terminal reads omit results; session-latest fallback can attribute another run's answer; failed terminal frames look completed; unknown memory IDs are falsely called never issued; a busy-send UUID lookup names the newest queue entry, not this run.

## Goals
Extend the existing chatRunRegistry owner with durable receipt backing inside the existing sessions SQLite database. Persist registration before provider execution, actual native-session mapping, queue identity/state, exact assistant reference candidate and actual terminal facts. No full transcript copying. Reconstruct completed/failed/aborted terminal receipts beyond memory retention and across real processes; a prior-boot unfinished receipt remains unknown_after_restart with retrySafe=false. Live results come only from this run's events; durable text must resolve an exact stored anchor through the existing sessionsService.fetchWindowAround, never latest assistant inference. Declare real handler binding via standard Tool._meta cloudcli/handlerBound independently of workflow verification.

## Non-Goals
No new Fleet/Run database, second scheduler, model invocation, production deployment, automatic resend, or claim that an unfinished provider process survived a restart. No added polling; default snapshot/ACK paths never await settlement. Existing explicitly requested bounded legacy waits remain compatibility behavior and are not extended.

## Design
Add a shared ChatRunReceipt contract, CHAT_RUN_RECEIPTS_TABLE_SCHEMA_SQL and a repository under server/modules/database/repositories/chat-run-receipts.db.ts (new), using the same getConnection as sessionsDb. Initialize through the existing migration/DB owner. Identity is immutable by run_id/session/provider/boot/start tuple; terminal facts cannot be downgraded. The existing registry receives optional backing (factory fixtures may remain process-local); its production singleton supplies the SQLite repository. startRun persists before publishing the run or invoking providers. Critical mapping/queue/finalized-assistant/terminal changes update the receipt. Post-effect persistence failure keeps actual in-memory truth and reports process-local durability, never fabricated durable success. No store of message bodies.

Add getRunReadback/setRunQueuedInput to the registry; getRunReadback returns own event text or a persisted receipt, without mutating storage. Capture terminal success/exitCode/aborted separately from legacy UI status. Eviction closes over the exact run to avoid an older timer deleting a newer terminal run. Superseded run failures close their own writer, without killing the newer run. Busy UUID lookup passes the actual run writer through providerRuntimeService to ClaudeResidentHostDriver, selecting that round's queuedUuids instead of global newest. CLI lifecycle events are correlated by actual UUID.

MCP buildRunGet combines the current registry with its receipt projection. Known terminal facts remain readable after retention/restart; unfinished previous-boot records are errors with known session history only as explicitly un-attributed reconciliation context. Missing memory/SQLite ID is unknown_in_current_process, never proof of no execution. runId plus a conflicting session is refused. Terminal immediate reads include own text, frozen elapsed time and true failed/aborted/queue state. Exact native message windows are optional and failure never erases a known terminal receipt. Tool metadata is set on actual registration branches: placeholders false, overrides true.

## Alternatives
Using the latest assistant message or mcp_audit_log as Run authority invents attribution. A new external Run database duplicates ownership. Only increasing memory TTL loses terminal results on service restart. Persisting transcripts duplicates provider history and is unnecessary when a minimal terminal receipt plus exact reference is available.

## Open Questions
Live CLI/SDK restart survival is not established. Stable normalized/native references must be verified by real provider parsers; missing reference yields terminal-only evidence, not a guessed answer. Windows execution and paid model tests remain parent integration acceptance.

## Bounded final-result amendment
The parent explicitly requires actual result recovery for Codex without a stable history ID. Codex's real normalizer gives live items itemId but synthesizes persisted history IDs on each read, so those ids must not be guessed as native anchors. The sole owner may persist one last completed assistant SDK text with its real writer/Run/session/family association, only at the actual terminal event. Store at most 64KiB valid UTF-8, original and stored SHA-256/byte counts, explicit truncation, source live-run-writer and final/partial completeness. This is one minimal result in chat_run_receipts, not a transcript/event/tool log. Claude native references remain preferred; Codex returns the writer-bound snapshot. Failure/abort remains failure/abort and its result is partial. Missing actual SDK text stays an unavailable terminal-only result. A late assistant frame cannot rewrite a frozen terminal receipt. Existing private SQLite permissions and artifact-only test DB placement apply.

## MCP queue receipt fence
A SESSION_BUSY error may name the current run only as context; it is not a new ACK and creates no new receipt. For an MCP busy-accepted attempt without this writer's own queue UUID, return QUEUE_ACCEPTANCE_UNKNOWN with its actual registered ticket, mayHaveExecuted=true and retrySafe=false. Do not invent the newest queue entry or report accepted/queued success. Preserve the owner record for later reconciliation. Legacy interactive WebSocket degraded-UUID behavior remains unchanged.
