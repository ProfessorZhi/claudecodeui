# 语音输入：标识符修复与时间轴压缩 Proposal

状态：Proposal / 待评审

证据基础：`/data/home/yale/work/tc-verify/FINDINGS.md`（仓库外验证工装，22 个工具 / 14 份日志）。
本文所有数字均来自该工装对 Groq `whisper-large-v3-turbo` 的实测，非估算。

## 摘要

对 CloudCLI 的语音输入做两项改动，**按证据强度排序，而非按直觉排序**：

1. **标识符确定性修复（P0）**——转写结果中形似代码标识符的片段，与项目真实文件清单做匹配并还原。
   纯字符串运算，无模型、无额外 API 调用、无延迟。实测中文标识符逐字存活率 **16.7% → 75.0%**，
   CER **0.1389 → 0.1040**；英文 **77.8% → 88.9%**。
2. **度量口径变更（P0，与 1 同时）**——现有 CER 对本案最关键的失效模式**结构性失明**（见 §2.3）。
   引入「标识符逐字存活率」作为与 CER 并列的验收指标。

时间轴压缩（VAD + 停顿压缩 + WSOLA）**降级为条件触发（P2）**：它的收益完全取决于真实录音的
停顿密度（实测区间 4.3%–50.8%），而那是一个**当前无人测量过的量**。在测出它之前不应投入实现。
另一个此前未被识别的杠杆——**请求合并（P1）**——在短片段场景下的收益（30–41%）超过压缩（3–7%），
且零音频处理风险。

**本方案的核心判断是：对 CloudCLI 而言，语音输入的质量瓶颈不在音频时长，而在标识符能否被正确还原。**

## 背景与现状

### 当前语音链路

| 环节 | 位置 |
|---|---|
| 录音 | `src/modules/chat/hooks/useVoiceInput.ts`（`getUserMedia` + `MediaRecorder`，webm/opus） |
| 触发 | `src/modules/chat/composer/VoiceInputButton.tsx` → `ChatComposer.tsx:260` |
| 上传 | `transcribeVoice()` @ `src/shared/api.ts` → `POST /api/voice/transcribe` |
| 代理 | `server/modules/voice/voice.service.ts`（OpenAI 兼容 multipart **纯透传**，无项目上下文） |
| 配置 | `src/shared/voiceConfig.ts` + `VoiceSettingsTab.tsx`（用户自备 baseUrl / apiKey / sttModel） |

交互形态是 **push-to-talk**：一次按键 = 一段录音 = 一次请求。

### 计费现实：10 秒/请求下限

Groq 文档明确：`Minimum Billed Length: 10 seconds` —— **不足 10 秒仍按 10 秒计费**。批处理接口同样适用。

于是 `billed(T) = max(10, T)`。这条下限的后果是：**压缩只对超过下限的部分有效**。

| 压缩率 R | 片段须超过 | 才能省到钱 |
|---|---|---|
| 1.0（不压） | 10.0s | — |
| 0.8 | 12.5s | |
| 0.5 | 20.0s | |

在实测语料上（中位 5.9s，79% 低于 10s），**完全压缩后仍有 91% 的片段落在下限内 → 省 $0**。

> ⚠️ 这条下限**未能在本机实测**（Groq 的 `x-ratelimit-remaining-audio-seconds` 是速率限制账本，
> 按真实时长扣且滑动回填，**不反映计费**）。依据是官方文档 + 多处独立佐证。
> **上线前应由 dev tier 控制台确认**（见 §待确认问题）。

### 已验证的事实（摘要）

| 结论 | 数值 | 置信度 |
|---|---|---|
| 标识符修复收益（中文） | 存活 16.7%→75.0%，CER −3.50% | 中（n=12） |
| 标识符修复收益（英文） | 存活 77.8%→88.9%，CER −0.20% | 中（n=18） |
| 压缩安全点 | **α=0.9**，中英双语下标识符中性 | 高（跨引擎跨语言复现） |
| 压缩危险点 | **α=0.8**，中文标识符存活归零（0/12） | 高（两轮独立复现） |
| 压缩节省区间 | 4.3%（占比 0.85）– 50.8%（占比 0.45） | 高（纯算术，非采样） |
| 噪音影响 | ≥10dB 保留 99%+ 语音；5dB 崩溃 | 高（纯 DSP） |
| 请求合并 vs 压缩（短片段） | 30–41% vs 3.2% | 高（模型计算） |

### 现状的具体缺口

1. **标识符系统性损坏，且无人测量。** 中文基线下 `voice.service.ts` 常被识别为 `voice.seluis.ts`。
   这直接决定 agent 会去改哪个文件——是本案最高代价的失效。
2. **CER 看不见上述损坏。** 见 §2.3。
3. **每次按键都付一次 10 秒下限。** 短句密集使用时，下限成本远超音频本身。

## 目标与非目标

### 目标

1. 把语音转写中的代码标识符还原为项目里真实存在的名字，**不引入模型、不增加 API 调用、不增加延迟**。
2. 建立能看见标识符损坏的度量口径，并将其纳入语音链路的验收面。
3. 在**不实现任何音频处理**的前提下，先量化真实使用场景的停顿密度与片段时长分布。
4. 若（且仅若）测出的分布支持，再引入时间轴压缩，且限定在已验证的安全参数内。

### 非目标

以下项**已被本次实验排除**，不应在实现中重新引入：

- **WSOLA α ≤ 0.8**：中文标识符存活 0/12；CER +2.3%（最差 +16.2%）。已证伪。
- **以 CER 作为主验收指标**：对标识符损坏失明，会产生「指标全绿而 agent 改错文件」的假通过。
- **噪音处理链路**：VAD 在 ≥10dB 稳健，且 `useVoiceInput.ts` 已启用
  `noiseSuppression: true` + `echoCancellation: true`。无需额外工作。
- **填充词/口头禅删除**（「嗯」「呃」）：语义风险高于收益，且本案未测量。
- **prompt 偏置**：n=7 时仅回 1 个标识符，**证据不足**，不作为方案。
- **修改 `voice.service.ts` 的接口契约**：保持纯透传，修复在客户端完成。

## 推荐架构

### P0 — 标识符确定性修复

**判据来源：`GET /api/file-tree/projects/:projectId/files`（已存在，前端 `api.ts:279` 已在调用）。**
这是本方案成立的关键前提：**候选清单是免费的**，无需新增接口。

```
transcribeVoice() 返回 text
        │
        ▼
  repairIdentifiers(text, candidates)      ← 纯函数，无 IO，无模型
        │
        ▼
  填入 composer / 自动发送
```

**候选集**：文件 basename（`voice.service.ts`）**与裸符号名**（`voiceService` / `useVoiceInput`）。
裸符号名是必需的——英文听写下 `useVoiceInput` 会被识别成 `Use voice input`（无点号），
只有裸名候选能匹配。

**两遍匹配，判据不同：**

| 遍 | 目标形态 | 判据 |
|---|---|---|
| 1. 带点名字 | `voice.seluis.ts` | 编辑距离，`minScore 0.7` |
| 2. 跨词符号 | `Use voice input` | **去空格去大小写后精确相等** |

第二遍**必须**用精确判据而非相似度：`look at how` 与 `use voice input` 形状完全相同，
任何能接受后者的模糊规则都会接受前者。**词表本身即判别器，不需要阈值。**

**第一遍的四重护栏（缺一即误报）：**

1. `editDistance` 提前退出必须返回 `Infinity`，**不能返回 `cap+1`**。
   `cap+1` 是真实距离的**下界**，转成相似度即成**上界**，用上界做阈值必然误报。
   （首版正是因此把 `Recording.G` "修复"成 `tests`，CER 反升 +9.4%。）
2. 带点的名字只能匹配带点的候选，反之亦然。
3. 必须共享首三字符——识别错误发生在中后段，很少在起始。
4. `minScore = 0.7`。

**实测效果：**

| 语料 | 标识符存活 | CER |
|---|---|---|
| 中文 | 16.7% → **75.0%** | 0.1389 → **0.1040**（−3.50%） |
| 英文 | 77.8% → **88.9%** | 0.1257 → 0.1237（−0.20%） |

**未解决**：`voice.seLuis TS`（识别器把点号读成了空格）token 形状已不成立，两遍均无法还原。
若此类占比高，需要第三遍（跨词 + 带点候选的联合匹配），**但需先测量其发生率再决定**。

### P1 — 请求合并

**动机**：10 秒下限按**请求**计，而当前架构是**一次按键一次请求**，下限被反复支付。

若用户在一分钟内连续按 5 次、每次 5 秒：
- 现状：5 请求 × max(10,5) = **50 计费秒**
- 合并为 2 请求：2 × 12.5 = **25 计费秒** → 省 50%

**这与音频处理正交**，零质量风险。但**需要 UX 决策**：合并意味着延迟出字。
可选形态（待确认，见 §待确认问题）：
- (a) 连续录音模式（一次按住说多句）
- (b) 短时窗口内合并提交（牺牲首字延迟）
- (c) 仅对已知的长听写场景合并

**本方案不预设形态**，先测量真实按键间隔与时长分布再定。

### P2 — 时间轴压缩（条件触发）

> **2026-09-21 修订（人 yale）**：P2 拆成两半 —— (a) **VAD / 停顿裁剪升为当前优先级**，改由
> `docs/proposals/voice-vad-trim-before-asr.md`（GOAL-006，AC-116…AC-122）承载：只删静音、α=1、
> 不调用 WSOLA；实测账单口径中文省 25.5%、英文省 13.3%，标识符逐字存活率中性，代价是 CER +1.1% 与
> 句读 2.06→1.00。(b) **WSOLA 仍为条件触发、暂不做**：在停顿裁剪之上只再多省 2.8pp，却把句读再压到
> 0.56，而 α=0.8 在中文把标识符打到 0/12。本节下面的数字保持有效，不改写。

**触发条件：P0 落地后，实测真实录音的语音占比。**

| 实测语音占比 | 建议 |
|---|---|
| > 0.80 | **不做压缩**。收益 <13%，转 P1 |
| 0.60–0.80 | 压缩收益 20–28%，视 P1 结果决定 |
| < 0.60 | 压缩收益 32–50%，值得做 |

**若做，参数限定：**

```
α = 0.9            ← 唯一已验证的标识符中性点，绝不用 0.8
停顿 cap 表         <120ms 保留 / 120–500ms→100ms / 500–1500ms→180ms / >1500ms→300ms
VAD                能量+滞回+hangover，pre-roll 120ms / post-roll 180ms
兜底                VAD 段数为 0 或覆盖异常 → 回退发送原始音频
```

**预期的已知代价（必须同时监控）：** 句读标记塌陷（实测 2.06 → 0.56）。CER 看不见它，
但对拼进 prompt 的文本，run-on 是真实的可读性损失。

## 度量变更（P0，与修复同等重要）

### 问题

`normalize()` 删除空格与标点，于是 **`voice.service.ts` 与 `voice service ts` 归一化后完全相同**。

直接证据：某次改动把 `Use voice.Input` 修成了 `useVoiceInput`（标识符**实际被修正**），
而 CER 报告 **0.00% 变化**。

**后果：本仓库若以 CER 验收语音质量，会产生「全绿但 agent 改错文件」的假通过。**

### 新增指标

| 指标 | 定义 | 用途 |
|---|---|---|
| **标识符逐字存活率** | 参考文本中的标识符（路径 / camelCase / snake_case / flag），在转写结果中**保留标点与大小写**地逐字出现 | 主验收指标 |
| 句读标记数 | 句末标点计数 | 监控 P2 的已知代价 |
| CER | 现有口径 | 保留，但**不作为语音质量的唯一判据** |

## 测试与验收标准

### 单元测试

- `repairIdentifiers` 四重护栏逐条断言：`cap` 提前退出返回 `Infinity`（构造长度差 > cap 的用例，
  断言**不匹配**而非匹配到最近的短候选）；带点/不带点互斥；首三字符约束；`minScore` 边界。
- 两遍匹配的顺序与幂等性：`repair(repair(x)) === repair(x)`。
- 空候选集、空文本、纯中文无标识符文本 → 原样返回，零修复。

### 集成测试

- 用真实项目文件树构造候选集（**至少覆盖 `git ls-files` 全量，数千个候选**），
  断言**误报率为 0**：不含任何标识符的普通中文/英文句子，经修复后逐字不变。
  > 这是当前最大的未验证风险——工装只在 21 个候选上验证过。候选规模上三个数量级后，
  > 编辑距离匹配的误报行为**未知**，必须先在真实文件树上验证再上线。

### 浏览器验收

- 复用既有语音 E2E 骨架（`e2e/` 下的 voice 相关 spec；注意 `uiPreferences` +
  legacy `voiceConfig` 双写才能种入麦克风配置）。
- 断言：给定时长为 T 的录音，转写文本中出现的 `voice.service.ts` 等标识符
  **逐字等于**项目真实文件名。

## 分阶段实施

| 阶段 | 内容 | 前置 |
|---|---|---|
| **S0** | 度量先行：接入标识符存活率到语音链路，建立基线读数 | 无 |
| **S1** | 在**真实项目文件树**上验证修复模块的误报率（工装已有实现） | S0 |
| **S2** | 修复模块落地客户端（`useVoiceInput` 转写回调前），候选从 file-tree 接口取并缓存 | S1 零误报 |
| **S3** | 测量真实按键分布：时长、语音占比、按键间隔 | 需真实使用数据 |
| **S4** | 依 S3 结果决定 P1（请求合并）或 P2（压缩，α=0.9） | S3 |

**S0–S2 不触碰音频处理，不改变服务端契约，风险最低。**
**S3 是决定 P1/P2 的唯一输入，且只能由真实使用数据回答。**

   标识符识别可能**更差**——那会提高 P0 的价值，不改变结论方向。

## 附录：本次验证中被推翻的结论

方案的可靠性一半来自**哪些早期判断是错的**。完整记录见 `FINDINGS.md` §一，摘要：

| 曾被判定 | 实际 | 根因 |
|---|---|---|
| Groq 无计费下限 | **有 10s 下限** | 把**速率限制**账本当成了**计费**账本 |
| 关键 token 丢失 8 个 | 内容一字未失 | 中文无空格，标点成了唯一分词符 → 集合差集误报 |
| 噪音使 VAD 丢弃 37% 语音 | 是 TTS 自带静音 | 用 TTS 块全时长当真值区间 |
| 停顿压缩只贡献 0.8% | 停顿密集时占 44% | 样本是朗读语音（静音仅 10%），不是目标场景 |
| 基线只保住 16.7% 标识符 | 中文如此，**英文 77.8%** | 未做跨语言对照 |

**其中两条直接来自对本方案的质疑（样本代表性）与对指标的追问（CER 是否看得见）。**
